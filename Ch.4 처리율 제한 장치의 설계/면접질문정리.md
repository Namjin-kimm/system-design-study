# 면접 질문 정리 — 처리율 제한 장치 설계

> 본 설계 결정을 기반으로 면접관이 할 수 있는 질문과 예상 답변 정리

---

## 알고리즘

**Q1. 왜 토큰 버킷 대신 이동 윈도우 카운터를 선택했나요?**

토큰 버킷은 버킷에 토큰이 쌓여있으면 순간적인 burst를 허용합니다. 이 경우 짧은 시간에 많은 요청이 몰릴 수 있어 "정확하게 제한한다"는 요구사항과 충돌합니다. 이동 윈도우 카운터는 버스트를 허용하지 않으면서 메모리 사용량도 적고 즉시 허용/차단이 가능해 낮은 응답시간 요구사항도 충족합니다.

---

**Q2. 이동 윈도우 카운터는 근사치라고 했는데, 실제로 오차가 발생하면 어떻게 되나요?**

오차율이 약 0.003% 수준으로 실용적으로는 무시 가능한 수준입니다. 만약 완벽한 정확도가 반드시 필요한 도메인(예: 금융 거래 횟수 제한)이라면 이동 윈도우 로그를 사용하는 것이 맞지만, 그 경우 메모리 요구사항을 감수해야 합니다.

---

**Q3. 누출 버킷(Leaky Bucket)은 왜 선택하지 않았나요?**

누출 버킷은 요청을 큐에 넣고 일정 속도로 처리하기 때문에 구조상 큐 대기 시간이 발생합니다. 나중에 들어온 요청일수록 응답이 늦어지므로 "낮은 응답시간" 요구사항과 충돌합니다.

---

## 배치 위치

**Q4. API Gateway만 두면 안 되나요? 왜 미들웨어도 필요한가요?**

API Gateway는 인증 이전 단계에서 동작하기 때문에 IP 기반 제한만 가능합니다. 사용자 ID 기반 제한이나 특정 엔드포인트별 세밀한 제어(게시글 하루 10개, 댓글 하루 20개 등)는 인증 이후 사용자 정보가 있어야 가능합니다. 이 둘은 역할이 달라 함께 사용하는 것이 적합합니다.

---

**Q5. 두 레이어에 Rate Limiter를 두면 운영이 복잡해지지 않나요?**

맞습니다. 두 레이어의 규칙을 각각 관리해야 하는 복잡도가 생깁니다. 이를 완화하기 위해 규칙을 중앙 설정 저장소(예: Redis, 설정 파일)에서 관리하고 양쪽이 참조하는 구조를 가져가면 관리 부담을 줄일 수 있습니다.

---

## 저장소

**Q6. Redis에 모든 API 요청마다 접근하면 Redis가 병목이 되지 않나요?**

Redis는 인메모리 기반으로 초당 수십만 건의 요청을 처리할 수 있어 일반적인 트래픽에서는 병목이 되지 않습니다. 다만 극단적인 트래픽이라면 Redis Cluster로 수평 확장하거나, 로컬 캐시를 도입해 Redis 접근 빈도를 줄이는 방법을 고려할 수 있습니다.

---

**Q7. 동시에 여러 서버가 같은 카운터를 수정하면 정확도 문제가 생기지 않나요?**

Redis의 `INCR` 명령어는 조회와 증가를 단일 원자적 연산으로 처리합니다. 중간에 다른 연산이 끼어들 수 없기 때문에 Race Condition이 발생하지 않습니다.

---

## 장애 처리

**Q8. Fail-open을 선택했는데, Redis가 죽으면 DoS 공격에 그대로 노출되는 것 아닌가요?**

맞습니다. 그래서 Fail-open만으로는 부족하고 두 가지로 보완합니다. 첫째, 로컬 메모리 Fallback으로 서버별 임시 제한을 걸어 완전히 제한이 없는 상황을 방지합니다. 둘째, Redis 자체를 Sentinel이나 Cluster 구조로 고가용성을 확보해 장애 발생 확률 자체를 낮춥니다.

---

**Q9. 로컬 Fallback을 쓰면 서버마다 카운터가 달라지는데 어떻게 처리하나요?**

Redis 복구 즉시 로컬 카운터를 초기화하고 Redis 카운터 기준으로 돌아갑니다. Fallback 상태에서는 서버별 독립 카운팅으로 정확도가 낮아지는 것을 감수하되, 가용성을 우선시한 트레이드오프입니다.

---

## 사용자 알림

**Q10. 429 응답에 Retry-After만 넣으면 되는데 왜 X-RateLimit 헤더를 전부 넣었나요?**

`Retry-After`는 차단된 후에야 클라이언트가 상황을 인지합니다. `X-RateLimit-Remaining`을 모든 응답에 포함하면 클라이언트가 한도에 가까워질 때 스스로 요청 속도를 줄일 수 있습니다. 불필요한 429 응답 자체를 줄여 서버 부하도 감소시킬 수 있습니다.

---

## 전체 설계

**Q11. 이 설계에서 가장 큰 단일 장애 지점(SPOF)은 어디인가요?**

Redis입니다. API Gateway와 미들웨어 모두 Redis에 의존하기 때문에 Redis가 죽으면 Rate Limiting 전체가 영향을 받습니다. Sentinel/Cluster로 가용성을 높이고, 로컬 Fallback으로 완전 중단을 방지하는 것이 핵심 대응입니다.

---

**Q12. 사용자가 10배 늘어나면 이 설계에서 어디가 먼저 병목이 될까요?**

Redis가 먼저 병목이 될 가능성이 높습니다. 모든 API 요청마다 Redis에 접근하기 때문에 트래픽이 늘어나면 Redis의 처리 한계에 도달할 수 있습니다. Redis Cluster로 수평 확장하거나, 윈도우 내 첫 요청만 Redis에 기록하고 이후는 로컬 캐시를 활용하는 방식으로 Redis 접근 빈도를 줄이는 최적화를 고려할 수 있습니다.
