# Ch.10 알림 시스템 설계 — 학습 기록

## 한눈에 보기

푸시 알림·SMS·이메일 세 채널로 하루 1,600만 건을 보내는 알림 시스템을 설계하는 문제. 요구사항은 **연성 실시간(soft real-time)**, **사용자 opt-out 지원**, 그리고 무엇보다 **알림이 소실되면 안 된다**는 것이다.

이 챕터를 관통하는 사실은 하나다 — **우리는 사용자 단말에 직접 알림을 꽂을 수 없다.** 아이폰 화면에 배너를 띄우는 권한은 애플만 갖고 있다. 그래서 알림 시스템의 마지막 단계는 항상 **외부 서비스에 전송을 위임하는 HTTP 호출**이고, 이 사실이 설계의 거의 모든 것을 결정한다.

```
[서비스 1~N]
     │ ① API 호출 (appKey + signature 인증)
     ▼
[알림 서버] ──② 메타데이터·설정 조회──→ [캐시] [DB]
     │  · 검증 / 알림 설정 확인 / 전송률 제한
     │  · 알림 로그에 PENDING 기록 (아웃박스)
     ▼
[스케줄러]  ← 예약 알림·digest는 DB에 보류했다가 여기서 투입
     │ ③ 이벤트를 채널별 큐에 삽입
     ▼
[푸시 큐] [SMS 큐] [이메일 큐]        ← 채널별 분리 = 장애 격리 + 독립 스케일링
     │ ④ 꺼냄
     ▼
[작업 서버(worker)]                   ← 템플릿 렌더링 + 외부 호출 (I/O bound)
     │ ⑤ 전송 (실패 시 retry 큐 → 소진 시 DLQ)
     ▼
[APNS] [FCM] [SMS 서비스] [이메일 서비스] [JPush/MiPush …]
     │ ⑥ 전달
     ▼
[사용자 단말]
```

**핵심 축 4가지**

| 축 | 내용 |
|---|---|
| **결합 끊기** | 초안(서버 1대)의 SPOF·확장성·성능 병목을 메시지 큐로 해결. 알림 서버(CPU-bound)와 워커(I/O-bound)를 분리해 각각 독립 증설 |
| **유실 vs 중복** | 유실 불가가 절대 조건이므로 at-least-once → **중복은 필연적 부작용**. exactly-once는 원리상 불가능(두 장군 문제)하고, 알림 로그 + 멱등성으로 빈도만 낮춘다 |
| **책임 경계** | 우리가 보장하는 건 **전달(delivery)이 아니라 위임(handoff)**. 서드파티가 2xx를 준 시점(`SENT`)까지가 우리 책임이고 그 이후는 통제 밖 |
| **확장성** | 채널·서드파티·알림 종류가 늘어날 때 **고쳐야 할 곳을 최소화**한다. 설정을 컬럼→행으로, 라우팅을 exchange로, 전송을 인터페이스+구현체로 |

**반복해서 등장하는 설계 원칙**
- **큐에는 "결과물"이 아니라 "재료"를 넣는다** — 템플릿 렌더링은 워커에서 (항목 9)
- **큐는 통로지 저장소가 아니다** — 예약 알림은 DB에 두고 스케줄러가 투입 (항목 10)
- **복잡한 판단 로직은 큐 앞에, 워커는 단순 전송기로** — digest도 스케줄러가 (항목 11)
- **변경이 한 곳에만 닿게 한다** — 컬럼 대신 값, 코드 대신 설정, 구현체 추가만으로 확장 (항목 1, 6, 15)

## 🎤 발표 후보

학습하면서 "몰랐던 것 / 스터디원과 공유하고 싶은 것"으로 표시한 내용. 발표 문서 작성 시 여기서 가져온다.

- **항목 6 — 메시지 큐 기술 선택 (RabbitMQ vs Kafka vs SQS vs SNS)**
  - 책은 "메시지 큐를 쓴다"고만 하고 어떤 걸 쓸지 말하지 않음 → 직접 근거를 만들어야 했던 부분
  - at-least-once는 셋 다 보장한다는 점(브로커형도 ack 기반이라 유실 없음) — 흔한 오해
  - Kafka 운영 비용의 실체 (파티션 설계, 리밸런싱, 디스크 관리)
  - SNS를 쓰면 **작업 서버가 통째로 사라진다**는 점, 그럼에도 안 쓰는 이유(중국 JPush 등 전송 계층 통제권)
  - fan-out 패턴과 SNS+SQS 조합

- **항목 7 — 큐가 있는데 왜 DB에 또 저장하나 (알림 로그)**
  - 큐의 ack = 1차 방어선(전송 실패), 알림 로그 = 2차 방어선(조회·감사·중복 판별). 역할이 겹치지 않음
  - **Kafka는 스트림이지 조회용 저장소가 아니다** — `WHERE user_id = 123` 같은 조건 조회 불가, append-only라 상태 갱신 불가, retention 지나면 소멸
  - **Kafka의 offset은 개별 메시지 실패를 표현할 수 없다** — 각 건이 독립적으로 실패하는 알림 워크로드에 RabbitMQ의 메시지 단위 ack/nack가 맞는 가장 강한 근거
  - 아웃박스 테이블과 알림 로그를 **한 테이블(status 컬럼)로 겸하는** 설계

- **항목 8 — Exactly-Once는 원천적으로 불가능하다**
  - at-least-once vs at-most-once는 **유실이냐 중복이냐**의 양자택일. 알림은 유실 불가가 절대 조건이라 중복을 감수할 수밖에 없음
  - "응답 없음"은 **전송 실패인지 응답만 유실인지 구분 불가** (두 장군 문제)
  - "Kafka는 exactly-once 지원하지 않나?" → Kafka **내부에서만** 성립, 외부 API 호출에는 해당 없음
  - **세 겹 방어 설계**: 알림 서버 유니크 제약 + 워커 조건부 UPDATE(CAS) + 배치 회수. 그럼에도 마지막 구멍(전송 성공 후 기록 실패)은 못 막음
  - 중복 방지를 강화하면 유실 위험이 생기는 **딜레마**

- **항목 9 — 큐에는 "결과물"이 아니라 "재료"를 넣는다 (템플릿 렌더링 위치)**
  - 렌더링 작업량은 어디서 하든 같지만, **큐를 통과하는 데이터 크기가 150배 차이** (완성 HTML 30KB vs 템플릿ID+값 200B)
  - 템플릿 문구를 고쳤을 때, 큐에 밀려있던 알림에도 반영되느냐가 갈림
  - 메시지 큐 일반 원칙 — 큐는 저장소가 아니라 통로
  - 템플릿을 DB에 두면 비개발자가 수정 가능하지만 **git 버전 관리·코드 리뷰가 사라진다**는 대가

- **항목 10 — 알림 설정: 채널만으로는 부족하다 + 예약 알림 구현**
  - 책의 스키마는 채널 단위지만, 실제로는 **(알림 종류 × 채널) 2차원 매트릭스**가 필요 ("배송은 받고 마케팅은 안 받기")
  - **끌 수 없는 알림(트랜잭션 알림)** 이 존재한다 — 보안·결제·비밀번호 재설정. 법규도 광고성 정보에만 수신거부 의무를 부과
  - **같은 "어디서 할까" 질문인데 템플릿과 답이 반대** — 템플릿은 워커(데이터 크기), 설정은 알림 서버(필터링 시점)
  - **예약 알림은 큐에 미리 넣지 않는다** — DB에 두고 스케줄러가 발송 시점에 큐로. 큐는 통로지 저장소가 아니며, 미리 넣으면 취소가 불가능해짐

- **항목 11 — 전송률 제한: 4장과 목적이 정반대 + 워커를 단순하게 유지하라**
  - 4장 처리율 제한은 **시스템 보호**(inbound, 초과 시 429 거절), 이 챕터는 **사용자 보호**(outbound, 초과 시 지연·묶음)
  - 초과분을 **버리지 않고 digest로 묶어 보내는** 선택지가 알림 시스템 특유의 해법
  - **복잡한 판단 로직은 큐 앞(스케줄러)에 두고, 워커는 단순 전송기로 유지한다** — 워커는 대수를 많이 늘리는 컴포넌트라 단순해야 함
  - 예약 알림(항목 10)과 digest(항목 11)가 **같은 패턴** — `[알림 서버] → [DB 보류] → [스케줄러] → [큐] → [워커]`. 설계에 스케줄러 컴포넌트를 추가하는 근거

- **항목 12 — 재시도: 무지성 재시도 금지 + 지연 구현의 실제**
  - **모든 실패를 재시도하면 안 된다** — 400/401/무효 토큰은 몇 번 보내도 실패. 무효 토큰 반복 전송은 APNS 제재 대상이므로 재시도가 아니라 **device 행 삭제**
  - **운영 알람은 알림 시스템과 분리된 경로로** — 알림 시스템이 고장났는데 알림으로 알릴 수는 없음 (PagerDuty, Slack 웹훅 등)
  - **지연 시간의 길이가 구현 방식을 가른다** — 초~분(재시도)은 큐 지연 기능, 시간~일(예약·digest)은 DB 폴링
  - **재시도 큐 ≠ DLQ** — 재시도 큐는 "다시 시도할 것", DLQ는 "포기하고 사람이 볼 것". RabbitMQ의 DLX는 둘 다에 쓰이는 라우팅 장치라 이름이 헷갈림
  - **head-of-line blocking** — 메시지 단위 TTL을 쓰면 앞 메시지에 막혀 뒤의 만료된 메시지가 못 나감 (브로커가 큐 맨 앞만 검사)
  - **RabbitMQ가 해주는 것과 우리가 짜야 하는 것의 경계** — 횟수 기록(`x-death`)은 자동, 어느 retry 큐로 보낼지 판단은 우리 코드

> ⏸️ **최종 설계 때 다시 논의할 것**: 알림 시스템에 어떤 메시지 큐 기술이 최적인지 아직 확정하지 못함. 3단계 설계에서 재검토.

## 1. 문제 정의와 요구사항
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

알림 시스템(notification system)은 뉴스, 상품 업데이트, 이벤트 등 사용자에게 중요한 정보를 **비동기적으로** 전달하는 시스템이다. 정의 자체는 단순하다 — "사용자에게 알림을 보내는 시스템".

책은 알림을 세 **채널**로 분류한다.

| 채널 | 설명 |
|---|---|
| 모바일 푸시 알림 | iOS/안드로이드 단말 화면에 직접 뜨는 알림 |
| SMS 메시지 | 통신사 망을 타는 문자 메시지 |
| 이메일 | 이메일 수신함으로 가는 알림 |

> **채널 ≠ 단말**: "iOS / 안드로이드 / 랩톱·데스크톱"은 **단말** 축이고, "푸시 / SMS / 이메일"은 **채널** 축이다. SMS는 단말 종류와 무관하게 통신사 망을 타고, 이메일은 데스크톱 웹에서도 열린다. 채널마다 붙는 외부 서비스가 완전히 다르기 때문에 이 구분이 중요하다.

1단계 질의응답이 필요한 이유는 문제를 "거창하게" 만들기 위해서가 아니라, **각 답변이 설계의 특정 부분을 강제로 결정해버리기 때문**이다.

### 동작 원리

**면접관과의 질의응답으로 확정된 요구사항**
- 지원 채널: 푸시, SMS, 이메일 3종
- 실시간성: **연성 실시간(soft real-time)** — 가능한 빨리 전달하되, 고부하 시 약간의 지연은 허용
- 지원 단말: iOS, 안드로이드, 랩톱/데스크톱
- 알림 생성 주체: 클라이언트 앱이 만들 수도, 서버가 스케줄링할 수도 있음
- 사용자가 알림을 끌 수 있어야 함 (opt-out)
- 규모: 하루 **천만 건 푸시 + 백만 건 SMS + 5백만 건 이메일**

**각 요구사항이 강제하는 설계 결정**

| 요구사항 답변 | 강제되는 설계 결정 |
|---|---|
| 연성 실시간 | 메시지 큐로 비동기 처리 가능 (완전 실시간이었다면 큐 자체가 성립 곤란) |
| opt-out 지원 | 알림 설정 테이블 + 전송 직전 확인 절차 |
| 채널별 물량 차이 (1000만 / 100만 / 500만) | 채널별 큐 분리 + 채널별 독립 스케일링 |
| 서드파티 장애 격리 필요 | 채널별 큐 분리 (같은 결론에 다른 근거) |

또한 "알림 생성 주체가 클라이언트일 수도, 서버일 수도 있다"는 답변 때문에, 뒤 설계에서 **서비스 1~N**(과금 서비스, 쇼핑몰 배송 알림 등)이 알림 시스템을 호출하는 외부 클라이언트로 그려진다. 알림 시스템은 알림을 스스로 만드는 게 아니라, 다른 서비스의 알림 요청을 받아 **전송을 대행**하는 시스템이다.

**알림 설정 스키마 — 컬럼 방식 vs 행 방식**

opt-out 요구를 만족시키려면 설정을 채널 단위로 저장해야 한다. 두 가지 스키마가 가능하다.

```
# 컬럼 방식
user_id | push_opt_in | sms_opt_in | email_opt_in

# 행 방식 (책의 선택)
user_id  bigint
channel  varchar   # push / sms / email
opt_in   boolean
```

| 방식 | 장점 | 단점 |
|---|---|---|
| 컬럼 방식 | 한 번 조회로 전 채널 설정 획득, 타입 안정성 | 채널 추가 시 `ALTER TABLE` + 코드 수정 필요 |
| 행 방식 | 채널 추가 시 **행 하나만 추가** — 스키마 변경 불필요 | `(user_id, channel)` 복합 키 필요, 사용자당 여러 행 조회 |

채널 이름이 **컬럼 이름 안에 박혀 있으면** 그것은 데이터가 아니라 스키마의 일부가 된다. 채널 이름을 **값(데이터)으로** 내려야 확장성 요구를 만족한다.

### 실제 세계 (도구 · 제품 · 논문)
- **연성 실시간(soft real-time)**: 하드 실시간(항공 관제, 자동차 ECU 등 — 마감 시간 초과 = 시스템 실패)과 대비되는 개념. 지연이 있어도 시스템 전체가 실패로 간주되지 않는다. 대부분의 알림·메시징 시스템이 이 범주.
- 알림 시스템은 흔히 **사내 공통 인프라 서비스**로 구축되어 여러 팀(결제, 마케팅, 물류 등)이 공유한다. "서비스 1~N이 알림 시스템 API를 호출"하는 그림이 그 구조.
- SMS는 **건당 과금**이라 물량 추정이 곧 비용 추정이 된다 (푸시·이메일과 다른 성격).

### 내 말로 정리

알림 시스템은 그냥 사용자에게 알림을 보내는 시스템이다. 책에서는 안드로이드, iOS, 노트북/데스크탑 웹으로 보낼 수 있어야 하고, 완전 실시간이 아닌 조금의 지연을 허용하는 연성 실시간이다.
(→ 보완: 여기서 안드로이드/iOS/데스크톱은 **단말** 축이고, 푸시/SMS/이메일이 **채널** 축이다. 둘은 별개.)

사용자가 알림을 끌 수 있어야 한다는 건, 사용자 계정 설정값을 확인해서 이 사람이 알림을 허용했는지 안 했는지 확인하면 된다. 그런데 이 설정은 계정당 하나가 아니라 **채널 단위**로 있어야 한다 — 푸시는 받고 이메일은 안 받는 사람이 있으니까. 처음엔 `push_opt_in`, `sms_opt_in` 같은 **컬럼**으로 두려고 했는데, 그러면 알림톡 같은 채널이 추가될 때마다 컬럼이 늘어나야 한다. 그래서 **채널 타입과 허용 여부를 값으로 갖는 행**으로 저장하는 게 맞다.

하루에 알림을 얼마나 보내야 하는지를 묻는 이유는 처음엔 서버를 몇 개 둬야 할지 정하기 위해서라고 생각했는데, 그보다 먼저 결정되는 게 있었다. 모든 채널을 하나의 큐에 넣고 처리하는 게 아니라 **채널마다 큐를 최소 1개씩** 둬야 한다. 그래야 ① SMS 서드파티에 장애가 나도 이메일 알림은 정상 동작하고(장애 격리), ② 물량이 10배 차이 나는 채널별로 워커를 따로 늘릴 수 있다(독립 스케일링).

## 2. 채널별 동작 원리 — APNS · FCM · SMS · 이메일
- **유형**: 핵심 개념 + 참고문헌 [1][2][3][4]

### 무엇인가 · 왜 중요한가

알림 시스템이 다른 시스템과 근본적으로 다른 지점이 여기다. **우리가 만드는 알림 서버는 사용자 단말에 직접 알림을 꽂을 수 없다.** 아이폰 화면에 배너를 띄우는 권한은 애플만 갖고 있다. 따라서 알림 시스템의 설계는 필연적으로 **"외부 서비스에 전송을 위임하는 구조"**가 된다.

이 사실이 뒤 설계 대부분을 결정한다.

| 사실 | 강제되는 설계 |
|---|---|
| 마지막 단계가 항상 외부 HTTP 호출 | 느리고 실패 가능 → **재시도 메커니즘** 필요 |
| 외부 서비스는 통제 불가 | **장애 격리** 필요 → 채널별 큐 분리 |
| 채널마다 붙는 서비스가 다름 | **확장 가능한 구조**(서비스 추가/제거 용이) 필요 |

### 동작 원리

**① iOS 푸시 알림 — APNS**

```
[알림 제공자(Provider)] → [APNS] → [iOS 단말]
       우리 시스템        애플 서버
```

- **알림 제공자(provider)** = 우리 시스템. 요청 생성에 두 가지가 필요하다.
  - **단말 토큰(device token)**: 알림을 보낼 특정 단말을 가리키는 고유 식별자
  - **페이로드(payload)**: 알림 내용을 담은 JSON 딕셔너리

```json
{
  "aps": {
    "alert": {
      "title": "Game Request",
      "body": "Bob wants to play chess",
      "action-loc-key": "PLAY"
    },
    "badge": 5
  }
}
```

- **APNS(Apple Push Notification Service)**: 애플이 운영하는 원격 서비스. 푸시를 실제 iOS 장치로 전달.
- **iOS 단말**: 알림 수신.

**왜 반드시 APNS를 거쳐야 하는가 (배터리)**
우리 서버가 아이폰과 직접 연결을 유지하려면 앱이 항상 실행 중이어야 한다. 설치된 앱 50개가 각자 연결을 붙들면 배터리가 남아나지 않는다. 그래서 **iOS는 APNS와 단 하나의 지속 연결(persistent connection)만 유지**하고, 모든 앱의 알림이 그 파이프 하나를 공유한다. OS 차원의 배터리 효율 설계이므로 우회로가 없다.

**② 안드로이드 푸시 알림 — FCM**

```
[알림 제공자] → [FCM] → [안드로이드 단말]
```

절차는 iOS와 **완전히 동일**하고 APNS 자리에 **FCM(Firebase Cloud Messaging, 구글 운영)**이 들어갈 뿐이다. 이 대칭성 덕분에 워커에서 "어느 서비스로 보낼지"만 분기하고 나머지 로직은 공통화할 수 있다.

**③ SMS**

```
[알림 제공자] → [SMS 서비스] → [SMS 수신 단말]
```

자체 구축이 아니라 제3자 사업자를 쓴다 — **트윌리오(Twilio)** [1], **넥스모(Nexmo)** [2] (현재 Vonage에 인수). 대부분 상용이라 **건당 요금**을 낸다. → SMS 물량 추정이 곧 비용 추정.

**④ 이메일**

```
[알림 제공자] → [이메일 서비스] → [이메일 수신 단말]
```

자체 이메일 서버 구축 역량이 있어도 대부분 상용 서비스를 쓴다 — **센드그리드(Sendgrid)** [3], **메일침프(Mailchimp)** [4]. 이유는 **전송 성공률(deliverability)이 높고 데이터 분석을 제공**하기 때문.

**통합된 그림**

```
                      ┌─→ APNS ─────────→ iOS 단말
                      │
[알림 시스템] ────────┼─→ FCM ──────────→ 안드로이드 단말
                      │
                      ├─→ SMS 서비스 ───→ SMS 단말
                      │
                      └─→ 이메일 서비스 → 이메일 수신 단말

                        └──── 제3자 제공 서비스 ────┘
```

**책임 경계 (design boundary)**

```
[알림 요청] → [우리 시스템] → [APNS] → [단말] → [사용자가 봄]
             └─ 우리가 책임지는 구간 ─┘
                                  └──── 우리 통제 밖 ────┘
```

APNS 응답은 "사용자에게 도착했다"가 아니라 **"요청을 접수했다(2xx)"**일 뿐이다. 단말이 꺼져 있거나 앱이 삭제됐으면 우리는 알 수 없다.

따라서 "알림이 소실되면 안 된다"는 요구사항은 실제로는 **"우리 시스템 내부에서 유실되면 안 된다"**로 번역된다. 이것이 뒤에 나오는 **알림 로그(notification log) DB**의 존재 이유다.

> 한 줄 요약: **우리는 전달(delivery)을 보장하는 게 아니라 위임(handoff)을 보장한다.**

### 참고문헌이 인용된 이유 ([1]~[4])

넷 다 논문이 아니라 **상용 제품 링크**다. 저자가 이를 참고문헌으로 단 이유는 하나 — **"이 부분은 직접 만들지 말고 사서 쓰는 게 정답"**이라는 설계 판단의 근거를 제시하기 위해서다. SMS 게이트웨이나 이메일 인프라를 직접 구축하겠다는 건 시스템 설계 면접에서 좋은 답이 아니다.

**책이 설명하지 않은 진짜 이유 (심화)**

책은 "전송 성공률이 높고 분석 서비스를 제공한다" 한 줄로 끝내지만, 핵심은 **"빨리 만들 수 있으니 산다"가 아니라 "돈과 시간으로도 못 만드는 자산을 빌린다"**는 것이다.

- **이메일 — IP 평판(reputation)**: 자체 SMTP로 보내면 Gmail·Outlook이 스팸함으로 보낸다. 발신 IP 평판은 **몇 주~몇 달의 정상 발송 누적 이력**으로만 생기며 즉시 구매가 불가능하다.
- **SMS — 통신사 계약망**: 문자를 보내려면 **각 나라 통신사와 개별 계약**이 필요하다. 글로벌 커버리지는 사실상 신규 진입이 불가능하다. Twilio는 그 계약망을 이미 보유하고 있다.

**발신 평판은 어떻게 판정되는가** (수신 측이 발신 IP·도메인 단위로 점수화)

| 신호 | 내용 |
|---|---|
| 스팸 신고율 | 가장 치명적. 0.3% 초과 시 위험 신호 |
| 바운스율 | 없는 주소로 계속 발송 = 리스트 관리 부실의 증거 |
| 스팸트랩(spam trap) | 수신 측이 심어둔 미끼 주소. 적중 시 목록 구매 정황 |
| 인증 통과 | SPF / DKIM / DMARC — 도메인이 해당 서버에 발송을 허가했는지 |
| 발송량 패턴 | 새 IP가 갑자기 대량 발송 → 즉시 차단. **IP 워밍업** 필요 |
| 수신자 참여도 | 열람하는가, 즉시 삭제하는가 |

Gmail은 **Google Postmaster Tools**로 도메인 평판을 확인할 수 있게 공개하고 있다.

### 실제 세계 (도구 · 제품 · 논문)
- **APNS 인증**: 과거 인증서(.p12) 기반 → 현재는 **토큰 기반(JWT, .p8 키)** 권장. 만료가 없고 모든 앱에 하나의 키 사용 가능.
- **FCM은 중국에서 사용 불가** (구글 서비스 차단) → JPush(极光推送), PushY 등 대체 서비스 필요.
- **AWS SNS / Amazon Pinpoint**: 여러 채널을 한 API로 묶은 상위 추상화 서비스. 이 챕터에서 설계하는 시스템의 상용 버전에 가깝다.
- **단말 토큰은 영구적이지 않다**: 앱 재설치, OS 업데이트, 장기 미사용 시 갱신될 수 있다. APNS/FCM은 "이 토큰은 무효"라는 응답을 주고, 우리 쪽에서 DB를 정리해야 한다.

### 내 말로 정리

핸드폰이 계속 알림을 받기 위해서 모든 어플과 계속 연결을 맺고 있으면 배터리가 엄청 빨리 닳기 때문에 그럴 수 없으므로, 애플과 안드로이드에서 제공하는 알림 서비스(APNS/FCM)를 통해서만 알림 발송 요청을 할 수 있다.

"알림이 소실되면 안 된다"는 요구사항을 만족하기 위해서는 우리 서비스에서 사용자에게 알림을 보낸 이력이 존재해야 한다.
(→ 보완: 그 이력이 보장하는 범위가 **책임 경계**다. 우리는 APNS가 접수할 때까지만 책임질 수 있고, 그 이후 단말에 실제로 떴는지는 통제 밖이다. 즉 "전달 보장"이 아니라 "위임 보장".)

SMS와 이메일을 서드파티로 쓰는 이유는, 처음엔 그냥 "직접 만드는 데 시간 쏟느니 잘 만들어진 서비스를 돈 주고 쓰는 것"이라고 생각했다. 그런데 그것만이면 돈과 인력이 충분하면 직접 만들면 된다는 얘기가 된다. 진짜 이유는 **돈으로도 못 사는 것**이 있어서다 — 이메일은 몇 달간 쌓아야 생기는 **발신 IP 평판**, SMS는 **각 나라 통신사와의 개별 계약망**. 발신 평판은 스팸 신고율, 바운스율, 스팸트랩 적중, SPF/DKIM/DMARC 인증 통과 여부 등을 수신 측(Gmail 등)이 IP·도메인 단위로 점수화해서 판정한다.

## 3. 연락처 정보 수집 절차 (user / device 데이터 모델)
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

APNS에 요청을 보내려면 **단말 토큰**이, SMS는 **전화번호**가, 이메일은 **이메일 주소**가 필요하다. 이 정보를 **누가·언제·어떻게 모아 어디에 저장할 것인가**를 정하지 않으면 알림 시스템은 시작조차 못 한다.

또한 이 데이터는 **모든 알림 전송의 hot path**에 있다. 하루 1600만 건을 보낸다면 이 조회가 1600만 번 발생한다 → 뒤 설계에서 **캐시를 붙이는 대상 1순위**가 되는 이유.

### 동작 원리

수집 시점은 **사용자가 앱을 설치하거나 처음 계정을 등록할 때**다. API 서버가 정보를 수집해 DB에 저장한다.

```
[사용자 앱 설치 / 회원가입] → [API 서버] → [DB에 연락처 정보 저장]
```

**책이 제시하는 테이블 구조**

```
user                                device
─────────────────────────           ──────────────────────────
user_id           bigint  (PK)      id                bigint  (PK)
email             varchar           device_token      varchar
country_code      integer           user_id           bigint  (FK)
phone_number      integer           last_logged_in_at timestamp
created_at        timestamp
```

**핵심 설계 결정: user와 device 분리 (1:N)**
한 사용자가 여러 단말을 가질 수 있고, **알림은 그 모든 단말에 전송되어야 한다.** 아이폰과 아이패드를 함께 쓰는 사용자에게 한쪽만 가면 안 된다. 하나의 테이블로 합치면 사용자당 단말 1개만 가능하도록 강제하는 꼴이 된다.

반면 이메일·전화번호는 user 테이블에 둔다(사람당 하나로 가정). 실무에서는 이것도 1:N으로 분리하는 경우가 많다.

**각 컬럼의 존재 이유**

| 컬럼 | 이유 |
|---|---|
| `country_code` (전화번호와 분리) | 국가별 SMS 사업자가 다르고(중국은 Twilio 사용 불가 등), 국가별 요금·규제·발송 가능 시간대가 다르다. 번호에 통째로 넣으면 "한국 사용자에게만 발송" 같은 질의가 어려워진다 |
| `last_logged_in_at` (device) | 단말 토큰은 영구적이지 않다. 장기 미로그인 단말에 계속 푸시하면 낭비이고 APNS가 무효 토큰 응답을 준다 → **휴면 단말 판별·정리**용 |

### 책 설계의 허점 (발표용 포인트)

**`phone_number integer`** — 전화번호를 정수로 저장하는 것은 실무에서 명백한 실수다.

- `010-1234-5678`의 **앞자리 0이 소실**된다
- 국제번호는 `int` 범위(약 21억)를 초과한다
- 전화번호는 **연산 대상이 아니라 식별자**다

→ 전화번호·우편번호처럼 "숫자로 생겼지만 숫자가 아닌 것"은 **`varchar`** 로 저장하는 것이 원칙.

### 캐시 관점 — 무엇을 캐시할지 정하는 기준

캐시 대상은 "조회가 많다"만으로 정해지지 않는다. 두 조건이 함께 성립해야 한다.

```
읽기 빈도:  하루 1600만 번            (매우 높음)
쓰기 빈도:  전화번호·이메일 변경은 몇 년에 한 번  (거의 없음)
```

**읽기는 폭발적이고 쓰기는 거의 없다** = 교과서적인 캐시 프로필.

다만 성격이 다른 컬럼이 둘 있다.

| 컬럼 | 성격 | stale 되었을 때 |
|---|---|---|
| `last_logged_in_at` | 쓰기가 가장 잦음 (로그인마다 갱신) | 통계만 부정확, **기능은 정상** |
| `device_token` | 앱 재설치·OS 업데이트 시 변경 | **알림이 죽은 주소로 발송 → 전달 실패** |

→ 단말 토큰은 갱신 시 **캐시 즉시 무효화** 또는 짧은 TTL이 필요하다.

> **캐시 여부는 읽기/쓰기 비율만이 아니라, stale 데이터의 실패 비용으로도 결정된다.**

### 실제 세계 (도구 · 제품 · 논문)
- **단말 토큰 갱신 처리**: 앱은 실행마다 OS로부터 토큰을 받아 서버로 보낸다. 저장 로직은 INSERT가 아니라 **UPSERT**여야 하고 `device_token`에 유니크 인덱스가 필요하다. 아니면 같은 단말이 중복 저장된다.
- **개인정보 보호**: 전화번호·이메일은 개인정보로 국내법상 **암호화 저장**이 요구된다. GDPR 적용 지역은 **삭제 요청 시 완전 삭제** 절차도 필요.
- **E.164 표기법**: 국제 전화번호 표준 형식(`+821012345678`). Twilio 등 대부분의 SMS API가 요구한다.
- **실무의 1:N 확장**: 이메일도 복수 등록하는 서비스가 많아 `user_email`, `user_phone` 테이블로 분리하고 `is_primary`, `is_verified` 플래그를 두는 경우가 흔하다.

### 내 말로 정리

user와 device 테이블을 분리하는 이유는 하나의 유저가 여러 개 device를 가지고 있을 수 있기 때문이다. 하나로 합치면 유저당 하나의 기기만 가질 수 있게 강제하는 꼴이 된다. 하나의 유저의 기기가 여러 대이면 그 기기에 다 알림이 가야 한다.

연락처 데이터를 캐시하는 이유는 알림을 보낼 때마다 연락처를 조회하면 조회 비용이 많이 들어가므로 캐시하는 게 성능상 좋기 때문이다.
(→ 보완: 조회가 많다는 것만으로는 부족하고, **쓰기가 거의 없다**는 조건이 함께 성립해야 캐시 대상이 된다. 그리고 `last_logged_in_at`은 쓰기가 잦지만 stale 해도 기능은 멀쩡한 반면, `device_token`은 stale 되면 알림 자체가 실패한다 — **stale 데이터의 실패 비용**도 기준이 된다.)

## 4. 개략적 설계 초안과 문제점 (SPOF · 확장성 · 성능 병목)
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

책은 여기서 **일부러 나쁜 설계를 먼저 보여준다.** 실수가 아니라 의도된 서술 방식이다.

처음부터 완성형 아키텍처를 그리면 "왜 그렇게 했냐"는 질문에 답할 수 없다. **단순한 초안 → 문제점 진단 → 개선** 순서를 밟아야 최종 설계의 모든 컴포넌트가 **어떤 문제를 풀기 위해 존재하는지** 설명할 수 있다.

→ 이 항목의 진짜 학습 목표는 초안 자체가 아니라 **"문제를 진단하는 어휘"** 를 갖추는 것.

### 동작 원리

**초안 구조**

```
[서비스 1]  ┐
[서비스 2]  ┼→ [알림 시스템]  →  [제3자 서비스]  →  [단말]
   ...      │    (서버 1대)       APNS/FCM/SMS/Email
[서비스 N]  ┘
```

| 컴포넌트 | 설명 |
|---|---|
| 서비스 1~N | 알림을 요청하는 주체. 마이크로서비스 / **크론잡** / 분산 시스템 컴포넌트. 예: 납기일을 알리는 **과금 서비스**, 배송 알림을 보내는 **쇼핑몰 웹사이트** |
| 알림 시스템 | 전송/수신 처리의 핵심. **우선 서버 1대로 가정**. ① 서비스 1~N에 알림 전송 API 제공 ② 제3자에 전달할 **페이로드 생성** |
| 제3자 서비스 | 실제 전달 담당. **확장성**(새 서비스 추가/제거 용이)과 **시장별 가용성**(FCM은 중국 사용 불가 → JPush, PushY 필요)을 유의 |
| 단말 | iOS / 안드로이드 / SMS / 이메일 수신처 |

### 세 가지 문제 — 서로 다른 층위, 서로 다른 해결책

**① SPOF (Single-Point-Of-Failure) — 가용성 문제**

알림 서버가 하나뿐이면 그 서버가 죽는 순간 **전체 서비스가 죽는다.** SPOF = "그것 하나가 실패하면 시스템 전체가 실패하는 지점".

**② 규모 확장성 문제**

한 대가 모든 것(API 수신, DB 조회, 캐시, 페이로드 생성, 외부 호출)을 처리하므로 **DB·캐시 등 중요 컴포넌트를 개별적으로 늘릴 수 없다.**

이것은 단순한 "용량 부족"이 아니라 **두 겹의 문제**다.

- **자원 낭비**: 실제 병목은 컴포넌트마다 다르게 온다. CPU만 부족한데 서버를 통째로 늘려야 한다.
- **수평 확장 자체가 불가능**: 상태(데이터)가 서버에 붙어 있기 때문이다.

```
[서버 A: 앱 + DB + 캐시]        ← 부하가 몰림
      ↓ 서버 한 대를 추가하면?
[서버 A: 앱 + DB(데이터 1~50만) + 캐시]
[서버 B: 앱 + DB(비어있음)      + 캐시]   ← 데이터가 없다!
```

서버 B는 A의 데이터를 모른다. B로 간 요청은 조회에 실패한다. 서버를 늘려도 확장이 안 되고 오히려 **데이터가 쪼개져 시스템이 깨진다.**

해결: DB·캐시를 **밖으로 분리**한다.

```
[앱 서버 A] ┐
[앱 서버 B] ┼→ [공유 DB]  [공유 캐시]
[앱 서버 C] ┘
```

앱 서버가 데이터를 갖지 않으면(= **무상태, stateless**) 몇 대든 늘릴 수 있고, DB가 병목이면 DB만 따로 증설·샤딩할 수 있다. 이것이 **"개별적으로 늘린다"** 의 의미다.

**③ 성능 병목**

저자의 표현: *"알림을 처리하고 보내는 것은 자원을 많이 필요로 하는 작업일 수 있다."* 두 가지 예시:
- **HTML 페이지 생성** (이메일 본문 렌더링) — CPU 사용
- **제3자 서비스 응답 대기** — 진짜 문제

APNS에 HTTP 요청을 보내고 응답을 기다리는 동안 그 스레드는 **아무 일도 안 하면서 붙잡혀 있다.**

```
스레드 200개, 요청당 200ms 대기
→ 초당 처리량 = 200 / 0.2초 = 1,000건/초

하루 1,600만 건 ÷ 86,400초 ≈ 185건/초 (평균)
→ 평균은 버티지만, 피크나 APNS 지연 시 즉시 무너짐
```

APNS 응답이 2초로 느려지면 처리량은 100건/초로 폭락하고 요청이 쌓이며 서버가 죽는다. 즉 **통제할 수 없는 외부 서비스의 지연이 우리 서버를 죽인다.**

### 세 문제 → 세 해결책 (개선안 예고)

| 문제 | 층위 | 해결 방향 |
|---|---|---|
| SPOF | 가용성 | 알림 서버 **다중화** + 자동 수평 확장 |
| 규모 확장성 | 확장성 | DB·캐시를 주 서버에서 **분리** |
| 성능 병목 | 성능 | **메시지 큐**로 컴포넌트 결합을 끊고 비동기화 |

책이 개선안에서 제시하는 세 방향이 정확히 이 표다. **각 개선이 어떤 문제에 대응하는지** 짝지어 기억할 것.

### 컴포넌트 간 결합을 끊는다는 것의 의미 (심화)

여기서 **컴포넌트** = **알림 서버**와 **작업 서버(worker)**. 초안에서는 이 둘이 한 몸이라 구분조차 없다.

```
# 동기 (초안)
[서비스] → [알림 서버] ────────────→ [APNS]
              └── 응답 올 때까지 대기 ──┘

# 큐를 끼운 후
[서비스] → [알림 서버] → [큐] → [작업 서버] → [APNS]
              ↑                    ↑
        큐에 넣고 바로 응답      여기서만 대기
```

결합을 끊으면 단순히 빨라지는 것이 아니라 **세 가지**를 얻는다.

| 얻는 것 | 의미 |
|---|---|
| **시간적 분리(temporal decoupling)** | 작업 서버가 전부 죽어도 알림 서버는 계속 요청을 받아 큐에 쌓는다. 워커 복구 후 밀린 것을 처리. 초안이라면 그 시간의 요청은 **전부 유실** |
| **속도 차이 흡수 (버퍼)** | 요청이 평소 10배로 쏟아져도 큐가 받아두고 워커가 자기 속도로 소비한다. 큐가 없으면 서버가 그 자리에서 터진다 |
| **독립적 확장·배포** | 이메일만 밀리면 이메일 워커만 증설. 워커 재배포 중에도 알림 서버는 정상 동작 |

핵심은 첫 번째다. 결합을 끊는 이유는 속도 때문만이 아니라 **한쪽의 장애가 다른 쪽으로 번지지 않게 하기 위해서**다. 항목 1의 "채널별 큐 분리 = 장애 격리"가 **수평 방향**이라면, 이것은 같은 원리의 **수직 방향**(알림 서버 ↔ 워커) 적용이다.

### 실제 세계 (도구 · 제품 · 논문)
- **SPOF 제거의 정석**: 무상태(stateless) 서버 + 로드밸런서 + 오토스케일링. 알림 서버가 무상태여야 아무 서버나 요청을 받을 수 있다.
- **"자원을 많이 필요로 하는 작업"의 정체**: 대부분 **I/O bound**(외부 응답 대기)다. 해결책은 CPU 증설이 아니라 **비동기화** — 메시지 큐를 쓰는 근본 이유.
- **JPush(极光推送) / PushY**: 중국 시장 대체 푸시 서비스. FCM이 막힌 이유는 구글 서비스 전반이 차단되어 있기 때문.

### 내 말로 정리

**① SPOF**: 알림 시스템의 서버, 즉 우리가 관리하는 알림 요청을 받는 서버가 하나라면, 이 서버가 죽어버리면 모든 알림 요청을 받을 수가 없고 결국 이 서버 하나 때문에 알림 기능을 수행할 수가 없다. 그래서 이 서버를 다중화하고, 요청 양에 따라서 오토 스케일링 될 수 있게 해야 한다.

**② 규모 확장성**: 처음엔 "서버 용량이 한정되어 있어서"라고 생각했는데 그게 아니었다. DB가 서버 안에 같이 들어있으면 서버를 한 대 더 붙여도 **새 서버에는 데이터가 없어서** 조회가 실패한다. 즉 확장이 안 되는 게 아니라 오히려 데이터가 쪼개져서 시스템이 깨진다. 그래서 DB·캐시를 밖으로 빼서 앱 서버를 무상태로 만들어야 몇 대든 늘릴 수 있고, DB가 병목이면 DB만 따로 증설할 수 있다.

**③ 성능 병목**: 알림 작업은 결국 최종적으로 서드파티에 요청을 보내고 응답을 기다려야 하기 때문에, 서드파티의 성능에 의해 알림 성능 자체가 좌지우지될 수 있다. 이걸 동기적으로 진행하면 그 응답 대기시간만큼 전체 작업 속도가 영향을 받는다. 그러므로 비동기로 작업해야 한다.
(→ 보완: 결합을 끊는 이유는 속도만이 아니다. 큐를 끼우면 ① 워커가 죽어도 알림 서버는 계속 요청을 받아 큐에 쌓고(시간적 분리), ② 트래픽 폭증을 큐가 흡수하며(버퍼), ③ 워커만 따로 늘리거나 재배포할 수 있다(독립 확장). 즉 **한쪽의 장애가 다른 쪽으로 번지지 않게 하는 것**이 핵심이다.)

## 5. 개선된 설계 — 메시지 큐 기반 아키텍처
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

항목 4에서 진단한 세 문제를 실제로 푸는 단계. 이 아키텍처가 이 챕터의 **최종 답안 뼈대**이며, 뒤에 나오는 모든 상세 설계(재시도, 템플릿, 모니터링 등)는 여기에 부품을 덧붙이는 것에 불과하다.

**개선 방향 3가지** (책)
- 데이터베이스와 캐시를 알림 시스템의 주 서버에서 **분리**한다
- 알림 서버를 **증설**하고 자동으로 수평적 규모 확장이 이루어지게 한다
- **메시지 큐**를 이용해 시스템 컴포넌트 사이의 강한 결합을 끊는다

### 동작 원리

**전체 구조**

```
[서비스 1~N]
     │ ① API 호출
     ▼
[알림 서버] ──② 메타데이터 조회──→ [캐시] [DB]
     │
     │ ③ 이벤트를 채널별 큐에 삽입
     ▼
[푸시 큐] [SMS 큐] [이메일 큐]
     │ ④ 꺼냄
     ▼
[작업 서버(worker)]
     │ ⑤ 전송
     ▼
[APNS] [FCM] [SMS 서비스] [이메일 서비스]
     │ ⑥ 전달
     ▼
[사용자 단말]
```

**알림 서버의 네 가지 기능 — 순서가 중요하다**

| 순서 | 기능 | 왜 여기서 하는가 |
|---|---|---|
| 1 | **알림 전송 API** | 스팸 방지를 위해 **사내 서비스 또는 인증된 클라이언트만** 호출 가능 |
| 2 | **알림 검증(validation)** | 이메일 주소·전화번호 등 기본 검증 |
| 3 | **DB/캐시 질의** | 알림에 포함시킬 데이터(사용자 정보, 단말 토큰, 설정) 조회 |
| 4 | **알림 전송** | 알림 데이터를 **메시지 큐에 삽입**. 하나 이상의 큐를 쓰므로 병렬 처리 가능 |

검증과 조회는 **큐에 넣기 전에** 수행한다. 잘못된 주소를 큐에 넣으면 워커가 꺼내서 외부 API를 호출하고 실패하고 재시도까지 하게 된다. 문 앞에서 걸러내는 것(**fail fast**)이 훨씬 싸다.

**API 예제** (책 그대로)

```
POST https://api.example.com/v/sms/send
```
```json
{
  "to": [{ "user_id": 123456 }],
  "from": { "email": "from_address@example.com" },
  "subject": "Hello, World!",
  "content": [
    { "type": "text/plain", "value": "Hello, World!" }
  ]
}
```

> **책 설계에 대한 비판적 시각**: `/v1/sms/send`는 URL에 **동사(`send`)** 가 들어 있다. REST 원칙(리소스 중심, 동사 금지)으로는 `POST /v1/notifications` 쪽이 맞다. 다만 "알림 발송"처럼 상태 변경보다 **행위(action)** 성격이 강한 API는 실무에서 동사형을 쓰기도 한다(Slack `chat.postMessage` 등). 발표에서 이 트레이드오프를 언급할 만하다.

**나머지 컴포넌트**

| 컴포넌트 | 역할 |
|---|---|
| 캐시 | 사용자 정보, 단말 정보, **알림 템플릿** 캐시 |
| 데이터베이스 | 사용자, 알림, 설정 등 저장 |
| 메시지 큐 | ① 컴포넌트 간 **의존성 제거** ② 다량 알림 대비 **버퍼**. **알림 종류별 별도 큐** → 제3자 하나에 장애가 나도 다른 채널은 정상 동작 |
| 작업 서버(workers) | 큐에서 알림을 꺼내 제3자 서비스로 전달. **외부 응답을 기다리는 유일한 지점** |

**전체 흐름 (6단계)**

1. API를 호출하여 알림 서버로 알림을 보낸다
2. 알림 서버가 사용자 정보·단말 토큰·알림 설정 같은 메타데이터를 캐시나 DB에서 가져온다
3. 알림 서버가 알림에 맞는 **이벤트를 만들어 해당 큐에 넣는다** (iOS 푸시 이벤트 → iOS 푸시 큐)
4. 작업 서버가 큐에서 알림 이벤트를 꺼낸다
5. 작업 서버가 알림을 제3자 서비스로 보낸다
6. 제3자 서비스가 사용자 단말로 알림을 전송한다

**앞의 세 문제를 어떻게 푸는가**

| 초안의 문제 | 개선안의 대응 |
|---|---|
| SPOF | 알림 서버 다중화 + 오토스케일링 (무상태이므로 가능) |
| 규모 확장성 | DB·캐시를 밖으로 분리 → 각각 독립 증설 |
| 성능 병목 | 큐로 알림 서버와 워커를 분리 → 알림 서버는 즉시 응답, 대기는 워커만 |

**대기 지점을 워커로 몰아넣어 얻는 것 — 성능 성격의 분리**

| | 알림 서버 | 작업 서버 |
|---|---|---|
| 하는 일 | 검증, DB 조회, 큐 삽입 | 외부 API 호출 후 대기 |
| 성격 | **CPU-bound** (수 ms) | **I/O-bound** (수백 ms) |
| 증설 판단 기준 | 들어오는 요청 수(QPS) | 큐에 쌓인 양 + 외부 응답 지연 |

한 몸일 때는 "서버가 느리다"는 뭉뚱그린 신호뿐이지만, 분리하면 **"큐가 쌓인다 → 워커를 늘려라"** 처럼 원인과 대응이 1:1로 연결된다. (→ 항목 14 큐 모니터링과 직결)

### 실제 세계 (도구 · 제품 · 논문)
- **알림 서버의 응답은 "접수 완료"**: 의미상 **HTTP 202 Accepted**가 맞다. 200 OK는 "처리 완료"를 함의하므로 부정확하다.
- **API 인증**: 책은 "사내 서비스 또는 인증된 클라이언트만"이라고만 한다. 실무에서는 서비스별 API Key, mTLS, 내부망 격리 등을 쓴다.
- **"큐 자체가 새로운 SPOF 아닌가?"** — 발표에서 나올 만한 반문. 실무 메시지 큐는 자체적으로 **클러스터·복제**를 수행한다(Kafka replication factor, RabbitMQ quorum queue). 큐를 다중화하지 않으면 병목을 옮긴 것에 불과하다.

### 내 말로 정리

검증을 큐에 넣기 전에 하는 이유는, 검증되지 않은 이메일이나 연락처 등을 큐에 넣어버리면 존재하지 않는 연락처로 알림 보내는 것을 시도하게 되는 비효율적 과정을 거쳐야 하기 때문이다.

외부 응답을 기다리는 지점은 **워커** 하나다. 본래 메시지 큐로 컴포넌트를 분리하지 않으면 동기 작업이 되고 서드파티가 응답을 보낼 때까지 작업은 대기해야 한다. 그런데 메시지 큐를 도입함으로써 알림 서버는 일단 요청이 접수됐다는 응답만 클라이언트에 보내면 되고, 실제 작업은 큐에 쌓이고 워커가 그 큐에서 작업을 꺼내서 진행하면 된다.
(→ 보완: 부수 효과로 두 컴포넌트의 **성능 성격이 분리**된다. 알림 서버는 CPU-bound, 워커는 I/O-bound라서 증설 판단 기준도 달라진다 — "큐가 쌓인다 → 워커를 늘린다"처럼 원인과 대응이 1:1로 연결된다.)

## 6. 메시지 큐 기술 — Kafka vs RabbitMQ vs SQS 🎤
- **유형**: 관련 심화 + 참고문헌 [7]

### 무엇인가 · 왜 중요한가

책은 "메시지 큐를 쓴다"고만 하고 **어떤 큐를 쓸지는 말하지 않는다.** 발표에서 "메시지 큐를 씁니다"라고만 하면 "어떤 거요? 왜요?"가 따라온다.

그리고 이건 취향 문제가 아니다. **큐 종류에 따라 재시도·중복 방지·유실 방지 설계가 통째로 달라진다.**

### 동작 원리

**두 가지 근본적으로 다른 모델**

```
# ① 브로커형 (RabbitMQ, ActiveMQ, SQS)
[생산자] → [큐: A B C] → [소비자]
                ↓ ack 받으면
           [큐: B C]      ← A는 사라짐
```
우체통에 가깝다. 편지를 꺼내가면 통에서 없어진다.

```
# ② 로그형 (Kafka, Pulsar)
[생산자] → [로그: A B C D E ...]  (append-only, 삭제 안 함)
                  ↑        ↑
            소비자1     소비자2
            (offset=1)  (offset=3)
```
방송 녹화본에 가깝다. 여러 명이 각자 다른 지점을 보고, 되감기도 된다.

**핵심 오해 정정 — "브로커형은 소비하면 사라진다"는 부정확하다**

정확히는 **"ack를 받으면 사라진다."**

```
1. 워커가 메시지를 가져감
   → 큐에서 삭제 X, "처리 중(unacked)" 상태. 다른 워커에겐 안 보임
2-a. 워커가 처리 성공 → ack → 이때 비로소 삭제
2-b. 워커가 죽음/타임아웃 → ack 없음 → 자동으로 큐에 복귀 → 다른 워커가 재처리
```

- **RabbitMQ**: 워커 연결이 끊기면 unacked 메시지를 자동 requeue
- **SQS**: `visibility timeout`(기본 30초) 내 삭제 요청이 없으면 다시 보이게 됨

→ **at-least-once는 브로커형도 보장한다.** "유실되면 안 되니까 Kafka"는 성립하지 않는 논거.

**로그형의 진짜 차별점**: 실패 건이 아니라 **이미 성공한 것까지 되감아 재생**할 수 있다는 것.
(예: 템플릿 버그로 어제 보낸 알림 전체를 다시 보내야 할 때)

**셋 비교**

| | **RabbitMQ** | **Kafka** | **AWS SQS** |
|---|---|---|---|
| 모델 | 브로커형 | 로그형 | 브로커형 (완전관리형) |
| 처리량 | 만~수만/초 | **수십만~백만/초** | 사실상 무제한 |
| 메시지 보존 | ack 시 삭제 | **기간 설정 (기본 7일)** | 최대 14일 |
| 재처리 | 실패 건만 (DLQ) | **offset 되감기로 전체 가능** | 실패 건만 (DLQ) |
| 순서 보장 | 큐 단위 | 파티션 단위 | FIFO 큐만 |
| 라우팅 | **강력** (exchange) | 단순 (토픽/파티션) | 없음 (SNS 필요) |
| 지연 메시지 | 플러그인/TTL | 기본 미지원 | **기본 지원 (15분)** |
| 운영 부담 | 중간 | **높음** | **없음** |
| DLQ | 지원 | 직접 구현 | **기본 지원** |

**처리량은 선택 기준이 아니다**

```
하루 1,600만 건 ÷ 86,400초 ≈ 185건/초 (평균)
피크를 5배로 잡아도 ≈ 1,000건/초
```
이 정도는 셋 다 여유롭다. Kafka를 "처리량 때문에" 고르는 건 이 규모에선 근거가 약하다.

**Kafka 운영 부담의 실체**

| 항목 | RabbitMQ | Kafka |
|---|---|---|
| 파티션 설계 | 개념 없음 | **미리 파티션 수 결정 필요.** 파티션 수 = 동시 소비자 상한. 늘릴 순 있어도 **줄일 수 없고**, 늘리면 키 기반 순서가 깨짐 |
| 소비자 추가 | 워커 프로세스 하나 더 띄우면 끝 | **리밸런싱 발생** — 재할당 동안 그룹 전체 소비 중단(stop-the-world) |
| 브로커 증설 | 노드 추가로 대체로 끝 | **파티션 재배치를 수동 수행**(`kafka-reassign-partitions`). 데이터가 실제 이동 |
| 디스크 | 소비되면 사라져 안정적 | **retention 기간만큼 계속 쌓임.** 용량 계획 실패 시 브로커 사망 |
| 유실 방지 설정 | ack 모드만 켜면 됨 | `acks`, `min.insync.replicas`, `replication.factor`, `unclean.leader.election` 조합을 정확히 이해해야. 잘못 잡으면 조용히 유실 |
| 감시 지표 | 큐 깊이 위주 | consumer lag, under-replicated partitions, ISR shrink, controller 상태 등 다수 |

> **RabbitMQ는 "큐를 만든다"가 끝, Kafka는 "분산 스토리지 클러스터를 운영한다"에 가깝다.**

**SQS vs RabbitMQ — 결정적 차이는 "서버가 있느냐"**

```
# RabbitMQ = 내가 서버를 운영한다
- VM에 설치, 클러스터 3노드 구성
- 메모리·디스크 임계치 감시 (한계 도달 시 생산자 차단됨)
- 노드 장애 복구, quorum queue 설정
- 버전 업그레이드, 보안 패치, 백업, 온콜

# SQS = 큐가 그냥 API로 존재한다
- 큐 하나 생성. 끝. 서버 없음.
- 용량 계획 불필요, 장애 대응·패치·백업 전부 AWS 책임
```

**대략적 비용 비교** (결정적이지 않음)
```
1,600만 건/일 × 30일 = 4.8억 건/월
큐 요청은 건당 send + receive + delete ≈ 3회 → 약 14억 요청
SQS Standard $0.40/백만 요청 → 약 $560/월
RabbitMQ 3노드 (t3.medium 급) → 약 $100~150/월 + 운영 인건비
```
→ 서버 비용만 보면 RabbitMQ가 싸지만 **운영 인건비를 넣으면 역전**된다.

**fan-out과 SNS**

**fan-out** = 하나의 입력을 여러 곳으로 복제해 뿌리는 패턴 (부채가 펼쳐지는 모양).

```
        ┌→ [푸시 큐]
[입력] ─┼→ [이메일 큐]      ← fan-out
        └→ [SMS 큐]
```
반대말은 **fan-in**(여러 입력이 한 곳으로 모임). RabbitMQ에는 실제로 `fanout` 타입 exchange가 있다.

**SNS(Simple Notification Service)** = AWS의 발행-구독(pub/sub) 서비스. 토픽에 한 번 publish하면 모든 구독자(SQS 큐, Lambda, HTTP, 이메일, SMS)에게 복사본이 간다.

```
                    ┌─ 구독 →[SQS 푸시 큐]   → 푸시 워커
[알림 서버] → [SNS 토픽] ─ 구독 →[SQS 이메일 큐] → 이메일 워커
                    └─ 구독 →[SQS SMS 큐]    → SMS 워커
        (한 번만 publish)
```

→ **RabbitMQ의 exchange 역할을 AWS에서는 SNS가 대신한다.** "SQS는 라우팅이 없다"가 아니라 "SQS 단독으로는 없고 SNS를 앞에 세워야 한다"가 정확한 표현.

**exchange 라우팅이 왜 중요한가 — 채널 추가 시 고칠 곳**

```
# SQS 단독: 큐들이 완전히 독립적
알림 서버 → SQS(푸시 큐)에 넣기    ← 호출 1
         → SQS(이메일 큐)에 넣기  ← 호출 2
  "어느 큐들에 넣을지"를 알림 서버가 전부 알아야 함
  → 채널 추가 시 알림 서버 코드 수정 + 배포

# RabbitMQ exchange: 분배를 exchange가 담당
알림 서버 → exchange에 한 번 publish (routing key: "payment.completed")
              ↓ 바인딩 규칙에 따라 자동 분배
         [푸시 큐] [이메일 큐]
  → 채널 추가 시 바인딩 규칙만 추가, 알림 서버 코드 무변경
```

항목 1에서 알림 설정을 컬럼이 아니라 행으로 뺐던 것과 같은 사고방식 — **채널이 늘어날 때 고쳐야 할 곳을 최소화한다.**

**SNS로 알림 시스템을 대체할 수 있는가**

| 기능 | SNS |
|---|---|
| 단말 토큰 관리 | ⭕ 플랫폼 엔드포인트로 APNS/FCM 토큰 대신 관리 |
| 채널별 fan-out | ⭕ 구독 기반 |
| 구독자별 필터링 | ⭕ 메시지 속성 기반 filter policy |
| 재시도 / DLQ | ⭕ delivery retry policy |
| SMS opt-out | △ `STOP` 문자 자동 처리 — **법적 규제 대응 수준**, 채널별 세밀 설정은 불가 |
| 알림 템플릿 | ❌ 완성된 본문을 넘겨야 함 |
| 사용자별 채널 설정 | ❌ |
| 전송률 제한 (사용자당) | ❌ 계정 단위 한도만 존재 |
| 이벤트 추적 (열람·클릭) | ❌ CloudWatch 전송 성공/실패까지만 |
| 알림 이력 DB | ❌ |

> **주의**: ❌ 항목은 RabbitMQ를 써도 **똑같이 우리가 구현해야 하는 것**이다. 따라서 이 표는 "SNS만으로 알림 시스템이 끝나는가"에 대한 답이지, **SNS vs RabbitMQ 선택 기준이 아니다.**

**SNS vs RabbitMQ의 진짜 비교 축 — 전송 계층을 얼마나 위임하는가**

```
# RabbitMQ 선택
[알림 서버] → [RabbitMQ] → [작업 서버] → [APNS/FCM/Twilio/Sendgrid]
                              ↑ 이걸 우리가 직접 구현
                    (APNS 인증, FCM 연동, Twilio SDK, 에러 코드 해석...)

# SNS 선택
[알림 서버] → [SNS] → [APNS/FCM/SMS/Email]
                 ↑ 작업 서버가 통째로 사라짐
```

| 상황 | SNS | RabbitMQ + 직접 워커 |
|---|---|---|
| **중국 시장** (JPush/PushY) | **불가.** APNS/FCM/Baidu 정도만 지원 | 아무 서비스나 호출 가능 |
| 서드파티 교체 | 제한적 | 자유 |
| 재시도 정책 세밀 제어 | SNS 정책 범위 내 | 완전 제어 |
| 서드파티 응답 상세 로깅 | CloudWatch 수준 | 원하는 만큼 |
| AWS 밖 운영 | 불가 | 가능 |
| **워커 개발 비용** | **없음** | 채널마다 구현 필요 |

> **선택 기준: 전송 계층을 통제할 필요가 있는가?**
> - 없다 (AWS 안, 표준 채널만, 빠른 구축) → **SNS**
> - 있다 (지역별 대체 서비스, 서드파티 교체, 세밀한 재시도) → **RabbitMQ + 직접 워커**

책의 설계는 명시적으로 **제3자 서비스 교체 가능성(확장성)** 과 **FCM이 중국에서 불가 → JPush 필요**를 요구사항으로 든다. → **SNS로는 이 요구를 만족시킬 수 없다.**

### 참고문헌 [7]이 인용된 이유

> **Key metrics for RabbitMQ monitoring** — datadoghq.com/blog/rabbitmq-monitoring

저자는 이 글을 **"큐 모니터링" 절**에서 인용한다. "큐에 쌓인 알림 개수가 중요 메트릭"이라는 주장의 근거를 대기 위해서다. (저자가 암묵적으로 RabbitMQ를 상정했음을 보여주는 단서이기도 하다.)

| 메트릭 | 의미 |
|---|---|
| **Queue depth (ready messages)** | 대기 중인 메시지 수. **계속 늘면 워커가 못 따라간다는 신호** — 책이 강조한 그 지표 |
| **Unacknowledged messages** | 워커가 가져갔지만 ack 안 한 것. 많으면 워커가 처리 중 멈춤 |
| **Publish rate vs Deliver rate** | 생산 속도 > 소비 속도면 무한정 쌓임 |
| **Consumer utilization** | 워커가 노는 비율. 낮으면 큐가 못 먹여주는 것 |
| **Node memory/disk alarm** | RabbitMQ는 메모리 한계 도달 시 **생산자를 차단**(flow control) |

마지막 항목이 중요하다 — **큐는 무한 버퍼가 아니다.** 워커가 멈춘 채 계속 쌓이면 큐가 터지고, 결국 알림 서버까지 막힌다.

### 실제 세계 (도구 · 제품 · 논문)
- **Kafka의 Zookeeper 제거**: 최근 버전은 **KRaft 모드**로 Zookeeper 없이 동작. 운영 부담이 이전보다 감소.
- **RabbitMQ Quorum Queue**: Raft 합의 기반 복제 큐. 기존 mirrored queue를 대체하며 노드 장애 시에도 메시지 유실 없음 → "큐가 SPOF 아니냐"에 대한 답.
- **국내 실무**: 카카오·네이버·쿠팡 모두 Kafka를 대규모 사용. 다만 알림 하나 때문이 아니라 **전사 이벤트 버스**로 쓰기 때문. 알림만 놓고 보면 과할 수 있다.
- **Redis를 큐로**: 소규모에선 Redis List/Stream을 쓰기도 하나 **영속성 보장이 약해** 알림 유실 방지 요구와 충돌한다.
- **Amazon Pinpoint**: SNS 상위 서비스로 템플릿·세그먼트·캠페인·분석까지 제공. 이 챕터가 만들려는 것에 가장 가깝지만 마케팅 캠페인 중심이라 트랜잭션 알림에는 과한 편.

### 내 말로 정리

브로커형은 큐에 쌓인 데이터를 워커가 소비하면 그대로 사라지고, 로그형은 그 데이터를 일정 기간 동안 유지한다는 차이가 있다.
(→ 보완: 정확히는 **ack를 받으면** 사라진다. 워커가 처리하다 죽으면 ack가 안 가서 메시지가 큐로 되돌아온다. 그래서 **브로커형도 at-least-once를 보장한다.** 로그형의 진짜 차별점은 유실 방지가 아니라 **이미 성공한 것까지 되감아 재생**할 수 있다는 것.)

카프카를 쓰는 대기업도 로그성 데이터를 그렇게 오래 가져가지 않는다(길어야 1~2주). 그러니 "추후 생길 분석 파이프라인에 흘려주려고 카프카를 쓴다"는 건 설득력이 약하다.

모든 기술이 at-least-once를 지원한다면, 운영 비용이 큰 카프카보다는 **RabbitMQ**를 쓰겠다.

**선택 근거 3가지**
1. 이 규모(피크 1,000건/초)에 Kafka의 고처리량은 불필요하고 운영 부담만 크다
2. 필요한 건 실패 건 재시도·DLQ인데 RabbitMQ가 기본 제공한다
3. exchange 라우팅으로 채널 추가 시 알림 서버 코드 변경 없이 확장 가능하다

**"AWS면 SQS가 낫지 않냐"에 대한 답**: 비즈니스 로직(템플릿·설정·제한·로그)은 어느 쪽이든 우리가 구현해야 하므로 비교 기준이 아니다. 진짜 차이는 **전송 계층 통제권**이다. SNS를 쓰면 작업 서버가 통째로 사라지는 큰 이점이 있지만, 이 설계는 **중국 시장 JPush 같은 지역별 대체 서비스와 서드파티 교체 가능성**을 요구사항으로 두고 있어 SNS로는 만족시킬 수 없다.

> ⏸️ 다만 최종 확정은 보류. 3단계 설계에서 재논의.

## 7. 안정성 — 데이터 손실 방지 (알림 로그) 🎤
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

저자가 이 챕터에서 가장 강한 어조로 말하는 요구사항.

> *"알림 전송 시스템의 가장 중요한 요구사항 가운데 하나는 **어떤 상황에서도 알림이 소실되면 안 된다**는 것이다. 알림이 지연되거나 순서가 틀려도 괜찮지만, 사라지면 곤란하다."*

이 한 문장에 **완화 조건 둘 + 절대 조건 하나**가 들어 있다. 분리해서 읽어야 한다.

| | 조건 | 설계에 주는 자유/제약 |
|---|---|---|
| 완화 | **지연 허용** | 비동기 처리 가능 (항목 1의 연성 실시간) |
| 완화 | **순서 뒤바뀜 허용** | 워커를 몇 대든 병렬로 돌려도 됨. FIFO 큐의 처리량 제약을 안 받음 |
| 절대 | **유실 불가** | 알림 로그 DB + 재시도 메커니즘 필요 |

**"순서가 틀려도 괜찮다"가 큰 완화인 이유**: 순서를 보장하려면 같은 사용자의 알림을 반드시 한 워커가 순차 처리해야 하고 병렬성이 급감한다. SQS FIFO 큐의 처리량이 Standard보다 훨씬 낮은 이유가 이것. 이 요구가 빠졌기 때문에 워커를 자유롭게 늘릴 수 있다.

### 동작 원리

책의 해법: ① 알림 데이터를 **DB에 보관**, ② **재시도 메커니즘** 구현. 구체적으로는 **알림 로그(notification log) DB** 유지.

**큐가 이미 ack로 유실을 막는데 왜 DB에 또 저장하나**

항목 6에서 브로커형 큐도 at-least-once를 보장한다고 했다. 그럼에도 알림 로그가 필요한 이유는 큐가 **못 하는 일**이 있기 때문.

| 큐가 못 하는 것 | 알림 로그가 하는 것 |
|---|---|
| 소비된 메시지는 소멸 → **이력 조회 불가** | "이 사용자에게 어제 알림 갔나?" 조회 가능 |
| 큐 자체 장애 시 유실 가능 | 큐 밖에 사본 존재 |
| 사용자 문의 대응 불가 | *"저 알림 못 받았는데요"* → 로그로 확인 |
| 중복 판별 불가 | 이벤트 ID 기록으로 중복 탐지 (항목 8) |
| 재처리 소스 없음 | 실패 건을 골라 재투입 |

> **큐의 ack = 1차 방어선(전송 실패 대비), 알림 로그 = 2차 방어선(감사·복구·중복 판별).** 역할이 겹치는 게 아니라 다르다.

**알림 로그의 상태 전이**

```
PENDING  ─ 알림 서버가 요청을 받아 DB에 기록 (아직 큐 삽입 전)
   ↓
QUEUED   ─ 큐에 삽입 완료
   ↓
SENT     ─ 워커가 제3자에게 전달, 2xx 응답 수신   ← 우리가 알 수 있는 마지막 상태
   ↓
FAILED   ─ 재시도 소진 후 실패 (DLQ로)
```

항목 2의 **책임 경계**가 여기서 스키마로 드러난다. `DELIVERED`(실제 도달)나 `READ`(열람)는 **우리가 알 수 없다.** 웹훅으로 서드파티가 알려주는 경우에만 채울 수 있다.

**상태를 두면 얻는 것 — 배치 보정**

```
"1시간 넘게 QUEUED 상태인 알림" 을 주기적으로 조회
  → 워커가 처리하다 죽었거나 큐에서 유실된 것
  → 자동 재투입 또는 알람
```

큐의 ack로도 못 잡는 구멍을 메운다. 예: 워커가 ack를 보낸 **직후** 죽어서 실제 전송은 안 된 경우, 큐는 정상 처리로 알고 지운다. 로그가 없으면 영영 모른다.

### 트레이드오프

**① 로그 기록이 hot path에 들어간다**

| 방식 | 장점 | 단점 |
|---|---|---|
| 동기 기록 | 확실함 | 느림. INSERT 실패 시 요청 자체를 거절해야 함 |
| 비동기 기록 | 빠름 | 기록 전 서버가 죽으면 흔적 없음 → **유실 불가 요구와 충돌** |

유실이 절대 조건이면 **큐에 넣기 전 동기 기록**이 맞다. 순서가 중요하다.
```
① DB에 PENDING 기록  →  ② 큐에 삽입  →  ③ QUEUED로 갱신
```
반대로 하면(큐 먼저) 큐에는 있는데 DB엔 없는 알림이 생긴다.

**② 저장 비용**
```
하루 1,600만 건 × 365일 = 58억 건/년
행 하나에 200바이트로 잡아도 → 약 1.2TB/년
```
영구 보관은 비현실적. 보통 **최근 30~90일은 hot 스토리지, 이후는 S3 등 cold 스토리지로 아카이빙**하거나 삭제.

### Kafka는 알림 로그를 대체할 수 있는가 (심화)

**Kafka는 어디에 저장하는가** — 내가 지정한 DB 테이블이 아니라 **브로커 서버의 로컬 디스크에 자체 파일 형식**으로 저장한다.

```
/kafka-logs/
  push-notification-0/            ← 토픽명-파티션번호
    00000000000000000000.log         ← 메시지가 append되는 실제 파일
    00000000000000000000.index       ← offset → 파일 위치 매핑
    00000000000512034829.log         ← 세그먼트가 차면 새 파일
```

메시지를 **파일 끝에 덧붙이기만** 한다(append-only). DB처럼 인덱스를 만들거나 수정하지 않는다. 그래서 빠르다.

**그런데 이 구조 때문에 알림 로그를 대체할 수 없다.**

| 필요한 것 | Kafka로 가능한가 |
|---|---|
| **조건 조회** — "user_id=123이 어제 받은 알림" | **❌** offset 순차 읽기만 가능. `WHERE` 절이 없다. 찾으려면 전체 스캔 |
| **상태 갱신** — "이 알림이 SENT됐다" 표시 | **❌** append-only라 기존 메시지 수정 불가 |
| **장기 보관** | **❌** retention 지나면 삭제 (기본 7일) |

> **Kafka는 흘려보내는 파이프(스트림)이지, 찾아보는 저장소가 아니다.** 사용자가 "저 알림 못 받았는데요" 하고 문의하면 Kafka로는 답할 수 없다.

→ **Kafka를 쓰더라도 알림 로그 DB는 여전히 필요하다.** 다만 역할 분담이 달라진다.
```
RabbitMQ 선택 시:  알림 로그 DB가 이력 + 상태 + 재처리 소스 전부 담당
Kafka 선택 시:     재처리는 Kafka(offset 되감기), 조회·상태는 여전히 DB
```

### Kafka의 재처리 원리와 한계 (심화)

**offset 관리**: 컨슈머 그룹별로 "어디까지 읽었는지"를 `__consumer_offsets` 내부 토픽에 저장한다.

```
로그:     [0] [1] [2] [3] [4] [5] [6] ...
                          ↑
              컨슈머 그룹 "push-worker" 의 offset = 4 → 다음에 4번부터 읽음
```

재처리 = 이 offset을 되돌리는 것.
```bash
kafka-consumer-groups --reset-offsets --to-datetime 2026-08-13T15:00:00 ...
kafka-consumer-groups --reset-offsets --to-earliest ...
```

**치명적 한계 — offset은 개별 메시지 실패를 표현할 수 없다**

offset은 **순차적인 하나의 숫자**다.
```
로그:  [0] [1] [2] [3] [4]
        ✓   ✓   ✗   ✓   ✓      ← 2번만 실패

offset을 2로 되돌리면? → 2,3,4 전부 재전송 (3,4는 이미 성공했는데!)
offset을 5로 커밋하면? → 2번 실패가 그냥 묻힘
```

**RabbitMQ는 이게 된다.** 메시지마다 개별 ack/nack가 있어 2번만 nack하면 2번만 큐로 돌아가고 3,4는 완료 처리된다.

> **각 건이 독립적으로 실패할 수 있는 알림 워크로드에는 RabbitMQ의 메시지 단위 ack가 훨씬 자연스럽다.** — 항목 6의 RabbitMQ 선택 근거 중 가장 강한 것일 수 있음.

**Kafka에서의 알림 재시도 — retry topic 패턴**

offset 되감기를 쓰지 않고 실패 건만 다른 토픽으로 옮겨 담는다.
```
[main topic] → 워커 → 전송 실패
                        ↓ 실패 건만 별도 토픽으로 produce
                  [retry-5m topic]  → 5분 뒤 재소비 → 실패
                        ↓
                  [retry-30m topic] → 30분 뒤 재소비 → 실패
                        ↓
                  [DLQ topic] → 사람이 확인
```
사실상 RabbitMQ가 기본 제공하는 것을 토픽 여러 개로 직접 구현하는 것.

**offset 되감기는 대량 사고 복구용** (예: 템플릿 오타로 어제 오후 3시부터의 알림 50만 건 재발송). 이때도 **이미 성공한 것까지 무차별 재전송**되므로, 워커가 재처리 시 **알림 로그 DB를 조회해 "이미 SENT면 스킵"** 필터링이 필요하다.

**재처리 시 원본 메시지가 어디 있는가 — 이것이 핵심 차이**

```
# 개별 전송 실패 재시도 → 둘 다 DB 조회 불필요 (워커가 본문을 들고 있음)

# 대량 사고 복구
RabbitMQ: ack된 메시지는 소멸 → 원본이 없음
   [알림 로그 DB] ──조회──→ 다시 큐에 발행    ← DB가 유일한 원본 소스 (필수)

Kafka: retention 내라면 원본이 로그에 그대로 존재
   [Kafka 로그] ──offset 되감기──→ 재생        ← DB 없이 원본 재생 가능
   [알림 로그 DB] ──조회──→ "이미 SENT면 스킵"  ← 중복 필터로만 사용
```

단, retention(7일)이 지나면 Kafka도 결국 DB에서 읽어야 한다. **Kafka의 재생 이점은 retention 기간 안에서만 유효하다.**

| 상황 | RabbitMQ | Kafka |
|---|---|---|
| 개별 전송 실패 | **nack → 자동 requeue** | retry topic 직접 구현 |
| 재시도 소진 | **DLQ (기본 제공)** | DLQ topic 직접 구현 |
| 대량 사고 복구 | 알림 로그 DB에서 재투입 | offset 되감기 (+ DB로 중복 필터) |

### 아웃박스 테이블과 알림 로그의 관계

목적은 다르지만 **한 테이블로 겸할 수 있다.**

| | 아웃박스 | 알림 로그 |
|---|---|---|
| 목적 | 큐 발행 보장 (이중 기록 문제 해결) | 이력·상태·감사 |
| 수명 | 발행되면 역할 끝 (삭제 가능) | 장기 보관 (30~90일) |

실무에서 흔한 방식 — 하나의 `notification` 테이블에 `status` 컬럼을 두고 둘 다 겸하게 한다.

```sql
notification
  id, user_id, channel, payload, event_id, status, created_at, sent_at

-- 아웃박스 역할: status='PENDING' 인 것을 relay가 읽어 큐에 발행 → 'QUEUED'로 갱신
-- 알림 로그 역할: status 이력을 보관, 조회·감사·중복판별에 사용
```

테이블 하나로 **발행 보장 + 이력 관리 + 중복 판별(event_id) + 재처리 소스**를 모두 커버.

### 실제 세계 (도구 · 제품 · 논문)
- **Transactional Outbox 패턴**: DB와 큐는 별개 시스템이라 한 트랜잭션에 묶을 수 없다. 일단 DB의 outbox 테이블에만 쓰고 별도 프로세스가 읽어 큐에 넣는다. **이중 기록(dual write) 문제**의 정석 해법.
- **Dead Letter Queue (DLQ)**: 재시도를 소진한 메시지를 버리지 않고 모아두는 별도 큐. 나중에 원인 분석 후 수동 재처리. (항목 11)
- **웹훅 기반 상태 보강**: Sendgrid·Twilio는 `delivered`, `bounced`, `opened` 이벤트를 웹훅으로 전달한다. 이를 받으면 `SENT` 이후 상태도 채울 수 있다. 단 **APNS/FCM은 개별 전달 결과를 알려주지 않는다.**

### 내 말로 정리

브로커 큐를 사용하게 되면 ack 응답이 오면 해당 작업은 사라지므로 이력을 관리할 수 없다. 그래서 우리 알림 서버에서 **아웃박스 패턴**을 적용해서 테이블로 알림 이력을 관리할 수 있다.

Kafka를 쓰면 알림 로그가 필요 없지 않냐고 생각했는데 아니었다. Kafka는 브로커 서버의 로컬 디스크에 append-only 파일로 저장하는 거라, `WHERE user_id = 123` 같은 **조건 조회가 안 되고 상태 갱신도 안 된다.** 즉 **Kafka는 스트림이지 조회용 저장소가 아니다.** 그래서 Kafka를 써도 알림 로그 DB는 필요하다.

**"순서가 틀려도 괜찮다"** 는 **병렬로 실행해도 된다는 자유**를 준다. 유저의 알림 순서를 보장해야 한다면 한 유저의 알림은 하나의 큐/파티션에만 순서대로 쌓여야 하는데, 그럴 필요가 없으니 아무 큐에나 쌓이면 되고 그걸 병렬 처리해도 된다.

Kafka 재처리도 결국 아웃박스 테이블을 조회해서 다시 큐에 쌓는 것 아니냐고 생각했는데, 경우가 갈린다. **개별 실패 재시도는 둘 다 DB를 안 본다**(워커가 본문을 들고 있음). **대량 복구 때** RabbitMQ는 ack된 메시지가 사라져서 **DB가 유일한 원본 소스**지만, Kafka는 retention 내라면 원본이 로그에 남아 있어 되감기만으로 재생되고 DB는 중복 필터로만 쓰인다. 다만 retention이 지나면 Kafka도 DB를 봐야 하므로 결국 수렴한다.

## 8. 안정성 — 중복 전송 방지 & Exactly-Once Delivery 불가능성 🎤
- **유형**: 핵심 개념 + 참고문헌 [5]

### 무엇인가 · 왜 중요한가

항목 7에서 "유실을 막기 위해 at-least-once로 재시도한다"고 했다. 여기엔 **필연적인 대가**가 따른다.

```
at-least-once (최소 한 번)  →  유실은 없지만 중복이 생긴다
at-most-once  (최대 한 번)  →  중복은 없지만 유실이 생긴다
```

둘 중 하나를 골라야 하고, 알림 시스템은 "유실 불가"가 절대 조건이므로 **at-least-once를 선택할 수밖에 없다.** 즉 **중복은 설계상 필연적으로 따라오는 부작용**이다.

책의 진술도 솔직하다.

> *"같은 알림이 여러 번 반복되는 것을 **완전히 막는 것은 가능하지 않다.** 대부분의 경우 알림은 딱 한 번만 전송되겠지만, 분산 시스템의 특성상 가끔은 같은 알림이 중복되어 전송되기도 할 것이다."*

→ 목표는 **제거가 아니라 빈도 감소**.

책이 제시하는 방법: *"보내야 할 알림이 도착하면 그 **이벤트 ID를 검사**하여 이전에 본 적이 있는 이벤트인지 살핀다. 중복된 이벤트라면 버리고, 그렇지 않으면 알림을 발송한다."*

### 참고문헌 [5]가 인용된 이유

> **"You Cannot Have Exactly-Once Delivery"** — bravenewgeek.com

**"완전히 막을 수 없다"는 주장에 이론적 근거를 대기 위해서**다. 구현을 못해서가 아니라 **분산 시스템의 근본 한계**다.

워커가 APNS에 요청을 보냈는데 **응답이 오지 않는다.** 이때 워커는 두 상황을 구분할 수 없다.

```
상황 A: 요청이 APNS에 도달 안 함        → 재시도해야 함 (안 하면 유실)
상황 B: APNS는 처리했는데 응답만 유실됨  → 재시도하면 안 됨 (하면 중복)

워커가 보는 것: 둘 다 "응답 없음" — 구분 불가능
```

선택지는 둘뿐이다. **재시도하면 중복 위험, 안 하면 유실 위험.** 중간은 없다. 이것이 **두 장군 문제(Two Generals' Problem)** — 네트워크로 연결된 두 주체가 메시지 전달을 100% 확신할 수 없다는 증명된 결과다.

> **"Kafka는 exactly-once를 지원한다던데?"** → Kafka의 exactly-once는 **Kafka 내부(consume → process → produce)에서만** 성립한다. 외부 시스템인 APNS로 나가는 순간 보장이 깨진다. 알림 시스템의 마지막 단계는 항상 외부 호출이므로 해당 사항이 없다.

> 정밀하게는 서드파티라서가 아니라 **네트워크 경계가 있으면** 어디서나 생기는 문제다. 다만 알림 시스템은 마지막 단계가 항상 외부 호출이라 피할 방법이 없다.

### 동작 원리 — 멱등성(idempotency)

완전 제거가 불가능하니 **중복이 와도 결과가 같도록** 만드는 것이 현실적 해법이다.

```
멱등하다 = 같은 연산을 여러 번 해도 결과가 한 번 한 것과 같다
f(x) = f(f(x)) = f(f(f(x)))
```

구현은 **이벤트 ID + 중복 검사**.
```
1. 알림 요청에 고유한 event_id 부여 (또는 호출자가 제공)
2. 처리 전 "이 event_id를 이미 처리했는가?" 확인
3. 있으면 버림(skip), 없으면 처리 후 기록
```

`notification` 테이블에 `event_id` 컬럼 + **유니크 제약**을 걸면 중복 INSERT가 DB 레벨에서 막힌다.

### 워커란 무엇인가 (구체화)

**워커는 별도로 배포된 애플리케이션(프로세스)** 이다. 클래스 하나가 아니라 자기 `main()`을 가진 독립 실행 단위.

```
[서버 A: 알림 서버]          [서버 B: 워커]
 Spring Boot 앱               Spring Boot 앱
 @RestController              @RabbitListener
 HTTP 요청을 받음     ──큐──→  큐를 구독해 메시지를 꺼냄
 포트 8080 열려있음            포트 안 열려있음 (HTTP 안 받음)
```

별도 배포인 이유: 항목 5의 "워커만 독립적으로 늘린다". 같은 프로세스면 알림 서버 3대 / 워커 20대 같은 조절이 불가능하다.

두 서버는 **같은 DB를 공유**한다.
```
[알림 서버] ──┐
              ├──→ [notification 테이블]  (event_id 유니크 인덱스)
[워커]      ──┘
```

### 어디서 중복 검사를 할 것인가 (설계 결정)

```
[호출자] ──①──→ [알림 서버] ──②──→ [큐] ──③──→ [워커] ──④──→ [APNS]

① 호출자가 같은 요청을 두 번 보냄     → 알림 서버에서만 막을 수 있음
③ 큐가 같은 메시지를 두 번 배달       → 워커에서만 막을 수 있음
   (ack 유실로 requeue된 경우)
④ APNS 응답 유실로 재시도            → 어디서도 못 막음 (원천적 한계)
```

**알림 서버 검사는 ①을, 워커 검사는 ③을 막는다. 서로 다른 구멍이라 겹치지 않는다.** 실무에서는 ③이 훨씬 흔하다(at-least-once 큐는 원래 재배달을 함).

| 위치 | 장점 | 단점 |
|---|---|---|
| **알림 서버** (큐 넣기 전) | 중복이 큐에 안 들어감 — 자원 절약 | 큐→워커 구간 중복은 못 막음 |
| **워커** (전송 직전) | 실제 전송 직전이라 가장 확실 | 중복 메시지가 큐를 이미 차지함 |
| **양쪽 다** | 가장 안전 | 조회 비용 2배 |

책은 "보내야 할 알림이 도착하면"이라고만 해서 위치가 모호하다. → **발표에서 명확히 하면 좋은 포인트.**

### 최종 설계 — 세 겹 방어

**① 알림 서버: `event_id` 유니크 제약**

```java
@RestController
class NotificationController {
    @PostMapping("/v1/notifications")
    ResponseEntity<?> send(@RequestBody NotificationRequest req) {
        if (notificationRepository.existsByEventId(req.eventId())) {
            return ResponseEntity.ok("이미 처리됨");   // 큐에 안 넣고 버림
        }
        notificationRepository.save(new Notification(req, PENDING));
        queue.publish(req);
        return ResponseEntity.accepted().build();
    }
}
```

**② 워커: 조건부 UPDATE로 선점 (compare-and-swap)**

그냥 UPDATE하면 두 워커가 동시에 들어왔을 때 **둘 다 성공**한다.

```sql
-- 위험: 두 워커 모두 성공하고 둘 다 전송함
UPDATE notification SET status = 'SENDING' WHERE event_id = ?

-- 안전: 조건을 붙이고 영향받은 행 수를 확인
UPDATE notification SET status = 'SENDING'
WHERE event_id = ? AND status = 'QUEUED'      ← 이 조건이 핵심
```

```java
@RabbitListener(queues = "push-queue")
void handle(NotificationMessage msg) {
    int updated = repository.markSending(msg.eventId());
    if (updated == 0) {
        return;   // 다른 워커가 이미 선점 (status가 이미 QUEUED가 아님)
    }
    apnsClient.send(msg);
}
```

`WHERE status = 'QUEUED'` 덕분에 먼저 도착한 워커만 1행을 바꾸고 나중 워커는 0행이 된다. DB의 행 잠금이 원자성을 보장한다. 이 패턴이 **compare-and-swap(CAS)**.

> 대안: `try { insert } catch (DuplicateKeyException) { return; }` — 유니크 제약을 원자적 잠금으로 쓰는 방식. **핵심은 "검사 → 전송 → 기록"이 아니라 "선점 → 전송" 순서**라는 것. 검사와 기록 사이의 틈(race condition)을 없애야 한다.

**③ 배치: 오래된 SENDING 회수**

②의 대가로 새로운 문제가 생긴다.
```
워커가 SENDING으로 바꿈 → 전송하다가 워커가 죽음
→ status는 영원히 SENDING
→ 다른 워커가 와도 WHERE status='QUEUED' 에 안 걸려 못 가져감
→ 이 알림은 영영 안 나감   ← 중복을 막으려다 유실을 만듦
```

항목 7의 배치 보정으로 해결한다.
```sql
-- "5분 넘게 SENDING 상태인 것" = 워커 사망으로 간주하고 회수
UPDATE notification SET status = 'QUEUED'
WHERE status = 'SENDING' AND updated_at < NOW() - INTERVAL 5 MINUTE
```

단, **워커가 실제로는 전송에 성공했는데 기록만 못 하고 죽었다면 중복이 나간다.** 결국 exactly-once로 못 가고 at-least-once에 머문다 — 참고문헌 [5]가 말한 그대로.

**세 겹 방어 요약**

| 위치 | 방법 | 막는 것 |
|---|---|---|
| 알림 서버 | `event_id` 유니크 제약 → 중복 INSERT 차단 | 호출자의 중복 요청 |
| 워커 | 조건부 UPDATE로 `SENDING` 선점 → 1행일 때만 전송 | 큐의 재배달 |
| 배치 | 오래된 `SENDING` 회수 | 워커 사망으로 인한 유실 |

**그래도 exactly-once는 아니다.** 마지막 구멍(전송 성공 후 기록 실패)은 원리상 못 막는다. 이를 인정하고 "빈도를 낮췄다"고 말하는 것이 정확하다.

### 실제 세계 (도구 · 제품 · 논문)
- **Stripe의 `Idempotency-Key`**: 결제 API 표준 패턴. 클라이언트가 헤더에 UUID를 넣어 보내면 서버가 같은 키의 요청에 이전 결과를 그대로 반환한다. 알림 API에도 그대로 적용 가능.
- **Redis 기반 dedup**: `SETNX event_id 1 EX 86400` — 24시간 TTL로 원자적 선점. DB보다 훨씬 빠르지만 Redis 재시작 시 유실 위험.
- **사용자 체감 관점의 완화**: 기술적으로 못 막은 중복도 클라이언트에서 **같은 알림 ID면 하나만 표시**하면 사용자는 못 느낀다. APNS의 `collapse_id`, FCM의 `collapse_key`는 같은 키의 알림을 단말에서 최신 것으로 대체해준다.

### 내 말로 정리

**exactly-once가 불가능한 이유**: 서드파티가 존재하면 알림을 보내고 성공했다는 응답이 와야 하는데 오지 않는 상황이 발생할 수 있다. 그러면 메시지 큐 입장에서는 이게 알림이 발송은 됐는데 응답만 오지 않은 건지, 아니면 알림 발송 자체가 실패한 건지 알 수 없으므로 어쩔 수 없이 다시 요청을 보내야 한다. 그렇기 때문에 exactly-once를 완전히 보장할 수는 없다.
(→ 보완: 서드파티라서가 아니라 **네트워크 경계**가 있으면 어디서나 생기는 문제다. 두 장군 문제.)

**중복 검사 위치**: 둘 다 하면 된다. 알림 서버에서는 `event_id`에 유니크 제약을 걸어서 중복 INSERT를 막고, 워커에서는 먼저 테이블을 '처리중'으로 UPDATE하고 알림 발송 로직을 시작하면 된다.
(→ 보완: 워커의 UPDATE는 반드시 **조건부**여야 한다. `WHERE status = 'QUEUED'`를 붙이고 영향받은 행 수가 1일 때만 전송해야, 동시에 들어온 두 워커 중 하나만 통과한다. 그리고 SENDING 상태로 바꾼 뒤 워커가 죽으면 그 알림이 영영 안 나가므로, 오래된 SENDING을 회수하는 배치가 추가로 필요하다.)

## 9. 알림 템플릿 🎤
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

책의 설명은 짧지만, 이건 **알림 시스템을 SNS 같은 전송 파이프와 구분 짓는 핵심 기능**이다. 항목 6에서 "SNS는 템플릿이 없다"고 했던 그 부분 — 우리가 직접 만들어야 하는 비즈니스 로직이다.

> 대형 알림 시스템은 하루에도 수백만 건 이상의 알림을 처리한다. 그런데 그 **알림 메시지 대부분은 형식이 비슷하다.**

템플릿은 이 유사성을 이용해 메시지를 처음부터 다시 만들 필요 없게 해주는 틀이다. 인자(parameter)·스타일·추적 링크(tracking link)만 바꿔 끼우면 사전 지정 형식대로 알림이 만들어진다.

**책의 예제**
```
본문:
여러분이 꿈꿔온 그 상품을 우리가 준비했습니다.
[item_name]이 다시 입고되었습니다! [date]까지만 주문 가능합니다!

타이틀(CTA: Call to Action):
지금 [item_name]을 주문 또는 예약하세요!
```

> **CTA(Call to Action)** = 마케팅 용어로 "사용자가 하길 원하는 행동을 유도하는 문구". "지금 주문하세요", "앱에서 확인하기" 등.

**얻는 것**

| 이점 | 의미 |
|---|---|
| 형식 일관성 | 모든 알림이 같은 톤·구조 유지 |
| 오류 가능성 감소 | 매번 문자열을 조립하지 않으니 오타·누락 감소 |
| 작성 시간 단축 | 새 알림은 값만 채우면 됨 |
| **(책에 없음) 비개발자 수정 가능** | 템플릿이 코드에 있으면 문구 하나 바꾸는 데 개발자 수정 + 배포 필요. DB에 있으면 마케팅팀이 어드민에서 직접 고치고 즉시 반영 — **실무에서 템플릿을 도입하는 가장 현실적인 동기** |

### 동작 원리 — 렌더링 위치 (설계 결정)

책은 "캐시에 알림 템플릿을 저장한다"고만 언급한다. 실제 설계에서는 **어디서 렌더링할지**를 정해야 한다.

```
# 알림 서버에서 렌더링
[알림 서버: 템플릿 + 값 → 완성 본문] → [큐: 완성 본문] → [워커: 그대로 전송]

# 워커에서 렌더링
[알림 서버: 템플릿ID + 값] → [큐: 템플릿ID + 값] → [워커: 조립 → 전송]
```

**렌더링 작업량 자체는 어디서 하든 같다.** 차이는 **큐를 통과하는 데이터가 무엇이냐**다.

```json
// 알림 서버 렌더링 → 큐에 완성본
{
  "user_id": 123456, "channel": "email",
  "subject": "에어팟 재입고 알림",
  "body": "<html><head><style>...</style></head><body><table width='600'>
           <h1>여러분이 꿈꿔온 그 상품을 우리가 준비했습니다.</h1>
           ... (HTML 이메일 본문 전체) ... </body></html>"
}
→ 약 30KB

// 워커 렌더링 → 큐에 재료만
{
  "user_id": 123456, "channel": "email",
  "template_id": 42,
  "params": { "item_name": "에어팟 프로 2세대", "date": "2026-08-20" }
}
→ 약 200바이트
```

**150배 차이.** 하루 이메일 500만 건으로 계산하면:
```
알림 서버 렌더링: 500만 × 30KB = 150GB 가 큐를 통과
워커 렌더링:      500만 × 200B =   1GB 가 큐를 통과
```
큐는 메시지를 디스크에 쓰고 네트워크로 나르고 워커에게 배달한다. 그 부담이 150배 차이 난다. 항목 6의 **SQS 256KB 메시지 크기 제한**에도 걸릴 수 있다.

**실무에서 더 중요한 차이**
```
[템플릿 문구에 오타 발견 → 수정]

알림 서버 렌더링: 이미 큐에 쌓인 100만 건은 옛 문구가 박혀 있음 → 그대로 나감
워커 렌더링:      큐에는 template_id만 → 꺼낼 때 새 템플릿을 읽음 → 수정 반영
```

| | 알림 서버 렌더링 | 워커 렌더링 |
|---|---|---|
| 큐 메시지 크기 | **큼** | **작음** |
| CPU 부하 위치 | 알림 서버 (hot path) | 워커 |
| 재시도 시 | 저장된 본문 그대로 재전송 | 재조립 필요 |
| 템플릿 수정 시 | 큐에 있던 건 옛 문구 | **큐에 있던 것도 새 문구 적용** |

> **큐에는 "결과물"이 아니라 "재료"를 넣는다.** 결과물은 소비하는 쪽에서 만든다.
> 알림 시스템만의 원칙이 아니라 메시지 큐 일반 지침 — **큐는 저장소가 아니라 통로**다.

항목 4의 "HTML 페이지를 만드는 일은 시간이 많이 걸린다"와도 맞물린다. 알림 서버는 가볍게 유지하고 무거운 일은 뒤로 넘긴다.

### 템플릿 저장 방식

HTML 본문을 통째로 TEXT 컬럼에 저장하는 것이 가장 흔하다.

```sql
notification_template
─────────────────────────────────────────
id            bigint
template_key  varchar   -- 'item_restock', 'order_shipped'
channel       varchar   -- push / sms / email
locale        varchar   -- ko / en / ja
subject       varchar   -- 제목 (이메일용)
body          text      -- ← HTML 통째로
version       int
created_at    timestamp

UNIQUE (template_key, channel, locale, version)
```

```html
<!-- body 컬럼에 그대로 들어가는 내용 -->
<html><body>
  <h1>{{item_name}}이 다시 입고되었습니다!</h1>
  <p>{{date}}까지만 주문 가능합니다.</p>
</body></html>
```

MySQL 기준 `TEXT`는 64KB, 더 크면 `MEDIUMTEXT`(16MB). HTML 이메일은 수십 KB라 충분하다.

**`(template_key, channel, locale)` 3중 키인 이유**: 같은 "재입고 알림"이라도 SMS는 90자 텍스트, 이메일은 HTML, 언어별로 다른 문구가 필요하다.

**저장 위치 트레이드오프**

| 저장 위치 | 장점 | 단점 |
|---|---|---|
| **DB** | 어드민 수정 → 즉시 반영, 배포 불필요 | **git 버전 관리 안 됨.** 코드 리뷰 없이 오타가 프로덕션 직행. 이력 추적하려면 별도 테이블 필요 |
| **코드/리소스 파일** | git 이력·코드 리뷰·롤백이 자연스러움 | 문구 하나 바꾸는 데 배포 필요 |
| **S3 등 외부 스토리지** | 대용량 유리, 버저닝 활용 가능 | 조회 지연, 캐시 필수 |

실무 절충: **DB 저장 + 승인 프로세스 + `version` 컬럼 이력 관리.** 마케팅팀이 수정해도 바로 나가지 않고 검토 후 활성화.

**캐시 무효화 주의**: 템플릿은 캐시에 올리는데(항목 3의 캐시 조건에 부합 — 읽기 많고 쓰기 거의 없음), 어드민에서 수정해도 캐시가 그대로면 옛 문구가 계속 나간다. 수정 시 캐시 삭제 또는 짧은 TTL 필요.

**알림 로그에 템플릿 버전 기록**: `template_id`, `version`을 함께 남기면 "이 알림 왜 이렇게 나갔지?"를 사후 추적할 수 있다.

### 실제 세계 (도구 · 제품 · 논문)
- **템플릿 엔진**: Java는 Thymeleaf·FreeMarker·Handlebars. 이메일은 **MJML**(반응형 HTML 이메일 전용)이 많이 쓰인다.
- **다국어(i18n)**: 실무에서 반드시 걸리는 문제. 템플릿을 `(template_id, locale)` 조합으로 관리해야 한다.
- **채널별 템플릿 분리**: SMS 90자 제한 vs 이메일 HTML — `(template_id, channel, locale)` 3중 키 관리.
- **Sendgrid Dynamic Templates**: 템플릿 관리 UI와 버전 관리를 제공. 이메일만 쓴다면 직접 만들 필요가 없을 수도 있다.

### 내 말로 정리

템플릿을 쓰는 이유는 반복되는 문구를 효율적으로 사용하고 필요한 데이터만 그때그때 바꿔 끼기 위해서다.
(→ 보완: 여기에 **비개발자가 문구를 바꿀 수 있게 된다**는 점을 더하면 훨씬 설득력이 생긴다.)

렌더링 위치는 처음엔 "결국 HTML 렌더링은 어디서 하든 똑같은 것 아니냐"고 생각했는데, 렌더링 **작업량**은 같지만 **큐를 통과하는 데이터 크기**가 달라진다. 완성된 HTML을 큐에 넣으면 30KB, 템플릿 ID와 값만 넣으면 200B로 150배 차이가 난다. 게다가 템플릿 문구를 고쳤을 때 큐에 밀려 있던 알림에도 반영되려면 워커에서 렌더링해야 한다. 그래서 **당연히 워커에서 렌더링**하는 게 맞다.

DB에 템플릿을 둔다는 건 HTML 문서를 통째로 TEXT 컬럼에 저장한다는 뜻이다.

## 10. 알림 설정 (opt-out) 🎤
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

> 사용자는 이미 너무 많은 알림을 받고 있어서 **쉽게 피곤함을 느낀다.** 따라서 많은 웹사이트와 앱에서는 사용자가 알림 설정을 상세히 조정할 수 있도록 하고 있다.

책이 제시하는 테이블:
```
user_id  bigInt
channel  varchar   # 알림이 전송될 채널. 푸시 알림, 이메일, SMS 등
opt_in   boolean   # 해당 채널로 알림을 받을 것인지의 여부
```

> 이와 같은 설정을 도입한 뒤에는 **특정 종류의 알림을 보내기 전에 반드시 해당 사용자가 해당 알림을 켜 두었는지 확인해야 한다.**

(이 스키마의 컬럼 방식 vs 행 방식 비교는 **항목 1**에서 이미 도출했다.)

### 동작 원리

**① 채널 단위만으로는 부족하다 — 2차원 매트릭스가 필요**

사용자가 실제로 원하는 것: *"배송 알림은 받고 싶은데 마케팅 알림은 안 받고 싶다."* 둘 다 푸시 채널이라 **채널 단위 설정으로는 표현할 수 없다.**

```sql
notification_setting
  user_id            bigint
  notification_type  varchar   -- 'marketing', 'shipping', 'security'
  channel            varchar   -- push / sms / email
  opt_in             boolean

  PRIMARY KEY (user_id, notification_type, channel)
```

**(알림 종류 × 채널) 2차원 매트릭스**

|  | 푸시 | SMS | 이메일 |
|---|---|---|---|
| 마케팅 | ❌ | ❌ | ✅ |
| 배송 | ✅ | ✅ | ❌ |
| 보안 | ✅ | ✅ | ✅ |

항목 1에서 컬럼 → 행으로 바꾼 것과 같은 사고방식의 연장. 축이 늘어나도 스키마 변경 없이 행만 추가하면 된다.

**② 끌 수 없는 알림이 있다 — 트랜잭션 알림**

```
✅ 끌 수 있어야 함: 마케팅, 추천, 이벤트 알림
❌ 꺼서는 안 됨:   보안 알림(새 기기 로그인), 결제 완료, 비밀번호 재설정
```

후자를 **트랜잭션 알림(transactional notification)** 이라 한다. 사용자가 요청한 행위의 결과를 알리는 것이라 끄면 오히려 사용자가 피해를 본다. 관련 법규(미국 CAN-SPAM, 국내 정보통신망법)도 **광고성 정보에만 수신거부 의무**를 부과하고 거래 관련 고지는 예외로 둔다.

```sql
notification_type
  type_key      varchar   -- 'marketing', 'shipping', 'security'
  is_mandatory  boolean   -- true면 opt-out 불가
```

**③ 어디서 확인할 것인가**

| | 알림 서버에서 확인 | 워커에서 확인 |
|---|---|---|
| 자원 효율 | **좋음** — 꺼진 알림이 큐에 안 들어감 | 나쁨 — 버릴 걸 큐에 넣고 워커가 꺼냄 |
| 최신성 | 나쁨 — 큐에 있는 동안 사용자가 끄면 그대로 나감 | **좋음** — 전송 직전 최신 설정 반영 |

**판단 기준은 "사용자 불만"이 아니라 "큐 체류 시간"** 으로 잡는 것이 명확하다.
```
큐 체류 시간이 수 초  → 끈 직후 알림이 갈 확률 거의 0 → 알림 서버 확인만으로 충분
큐 체류 시간이 수 시간 → 그 사이 설정 변경 여지 큼 → 워커 재확인 필요
```

체류 시간이 길어지는 경우: **백로그**(서드파티 장애·트래픽 폭증 — 항목 6의 queue depth 지표), **예약 알림**.

> **항목 9의 템플릿과 정반대 결론이 나오는 지점.** 같은 "어디서 할까" 질문인데 기준이 다르기 때문 — 템플릿은 **데이터 크기**가 지배적, 설정은 **필터링 시점**이 지배적.

| 확인/조립 대상 | 어디서 | 이유 |
|---|---|---|
| 템플릿 렌더링 | **워커** | 큐 메시지 크기 + 문구 수정 반영 |
| 알림 설정 확인 | **알림 서버** | 자원 효율 — 버릴 것을 큐에 넣지 않음 |

### 예약 알림은 어떻게 구현하는가 (심화)

즉시/예약 구분은 필드 하나로 한다.
```sql
notification
  scheduled_at  timestamp NULL   -- NULL이면 즉시, 값이 있으면 그 시각에 발송
```

**구현 방식 두 가지**

```
# ① 큐에 미리 넣고 지연 배달
[알림 서버] → [큐: 3일 뒤 배달] → (3일 대기) → [워커]
  - RabbitMQ: delayed message exchange 플러그인
  - SQS: DelaySeconds — 최대 15분. 3일 예약은 불가능

# ② DB에 두고 시간이 되면 큐에 넣기  ← 표준
[알림 서버] → [DB에 scheduled_at 기록]
                     ↓
              [스케줄러가 1분마다 조회]
              WHERE scheduled_at <= NOW() AND status = 'PENDING'
                     ↓
                   [큐] → [워커]
```

**②가 표준인 이유** — 항목 9의 원칙과 동일하다. **큐는 통로지 저장소가 아니다.** 3일치를 큐에 쌓으면:
- 큐가 계속 부풀어 오르고
- **예약 취소가 불가능하다** (큐에 들어간 메시지는 골라서 뺄 수 없음)
- 큐 장애 시 3일치가 통째로 소실

DB에 두면 취소는 `status = 'CANCELLED'` UPDATE면 끝.

**여기서 나오는 결론**: ②로 구현하면 예약 알림도 **발송 시점에야 큐에 들어간다.** 큐 체류 시간이 즉시 알림과 같아지고, 스케줄러가 큐에 넣을 때 설정을 확인하면 그 시점이 이미 최신이다.

```
[알림 서버] → [DB 대기] → [스케줄러: ★여기서 설정 확인★] → [큐] → [워커]
                              발송 직전 시점이므로 최신
```

> **큐에 넣는 시점에 설정을 확인한다.** 즉시 알림은 알림 서버가, 예약 알림은 스케줄러가 그 역할을 한다.

| 알림 종류 | 큐에 넣는 주체 | 설정 확인 시점 |
|---|---|---|
| 즉시 알림 | 알림 서버 | 알림 서버가 큐에 넣기 전 |
| 예약 알림 | 스케줄러 (DB 폴링) | 스케줄러가 큐에 넣기 전 |

→ 워커 재확인이 필요한 경우는 **큐가 백로그로 밀렸을 때** 하나만 남는다. 이는 정상 상태가 아니라 장애 상황이므로, 처음부터 대비할지는 판단의 영역.

### 실제 세계 (도구 · 제품 · 논문)
- **법적 요구(국내)**: 정보통신망법상 광고성 정보 전송에는 **사전 동의(opt-in)** 가 필요하고, **야간(21시~08시) 전송에는 별도 동의**가 필요하다. 실무 설정 테이블에 `night_push_opt_in` 같은 컬럼이 따로 붙는 이유.
- **SMS의 `STOP`**: 사용자가 SMS에 `STOP`을 회신하면 Twilio·SNS가 자동으로 수신거부 처리한다. **우리 DB와 별개로 서드파티가 관리**하므로 "우리 설정은 opt-in인데 실제로는 안 나가는" 상황이 생긴다. 서드파티의 수신거부 웹훅을 받아 우리 DB에도 반영해야 한다.
- **알림 피로(notification fatigue)**: 책이 말한 "쉽게 피곤함을 느낀다"는 측정 가능한 지표다. 과도한 알림은 사용자가 **채널 자체를 꺼버리게** 만들고, 그러면 정말 중요한 알림도 못 보낸다 → 다음 항목(전송률 제한)의 동기.

### 내 말로 정리

채널 단위 설정만으로 부족한 이유는, 사용자가 특정 마케팅 알림은 안 받고 싶고 그 외에 배송 알림이나 주문 알림은 받고 싶을 수 있기 때문이다. 단순히 채널로만 구분하면 안 된다.

설정 확인 위치는 효율성을 따지면 **알림 서버**에서 확인하는 게 맞다. 불필요한 작업을 큐에 넣을 필요가 없으니까. 이미 큐에 알림 작업이 들어가 있는 와중에 알림을 거부하면 그 알림은 발송돼서 사용자가 불만을 느낄 수도 있지만, 어차피 그 후의 알림은 가지 않으니 큰 문제가 아니다. 사용자 불만이 너무 많아지면 그때 워커에서도 확인하는 로직을 넣으면 된다.
(→ 보완: 판단 기준을 "불만"이 아니라 **"큐 체류 시간"** 으로 잡으면 더 명확하다. 그리고 예약 알림을 DB에 두고 스케줄러가 발송 시점에 큐로 넣는 방식을 쓰면, 예약 알림의 체류 시간 문제 자체가 사라진다. 결국 **"큐에 넣는 시점에 확인한다"** 로 정리된다.)

## 11. 전송률 제한 (rate limiting) 🎤
- **유형**: 핵심 개념 + 관련 심화

### 무엇인가 · 왜 중요한가

책의 설명은 세 문장뿐이다.

> 사용자에게 너무 많은 알림을 보내지 않도록 하는 한 가지 방법은, 한 사용자가 받을 수 있는 **알림의 빈도를 제한**하는 것이다. 이것이 중요한 이유는, 알림을 너무 많이 보내기 시작하면 **사용자가 알림 기능을 아예 꺼 버릴 수도 있기 때문**이다.

짧지만 핵심 통찰이 있다 — **전송률 제한의 목적이 시스템 보호가 아니라 사용자 보호**라는 점.

### 4장의 처리율 제한과의 대비

| | **4장의 처리율 제한** | **이 챕터의 전송률 제한** |
|---|---|---|
| 목적 | **시스템 보호** — 과부하·DDoS 방어 | **사용자 보호** — 알림 피로 방지 |
| 제한 대상 | 들어오는 요청 (inbound) | 나가는 알림 (outbound) |
| 기준 | IP, API 키, 클라이언트 | **수신자(user_id)** |
| 초과 시 | **429 반환하고 거절** | 버리거나, **지연시키거나, 묶어서 보냄** |
| 시간 단위 | 초·분 | **시간·일** |

**"초과 시 어떻게 하느냐"가 가장 큰 차이.** API 요청은 거절하면 클라이언트가 재시도하면 그만이지만, 알림을 버리면 사용자가 정보를 영영 못 받는다.

```
① 버림(drop)      — 마케팅 알림처럼 놓쳐도 되는 것
② 지연(delay)     — 다음 시간대로 미룸
③ 묶음(digest)    — "안 읽은 알림 5건" 처럼 하나로 합쳐서 보냄   ← 알림 시스템 특유의 해법
```

③이 슬랙·페이스북이 "지금 놓친 알림들" 이메일을 보내는 방식이다.

### 동작 원리

**알고리즘 선택** (4장에서 배운 것들을 재사용)

| 알고리즘 | 알림에 적합한가 |
|---|---|
| **토큰 버킷** | ⭕ 적합. "하루 10건, 단 몰아서 3건까지 허용" 같은 버스트 허용이 자연스러움 |
| 고정 윈도 카운터 | △ 경계 문제 — 23:59에 10건, 00:01에 10건 가능 |
| 슬라이딩 윈도 로그 | ⭕ 정확하나 사용자마다 타임스탬프 목록 저장 → 메모리 부담 |
| 누출 버킷 | ⭕ 일정 속도로 흘려보내므로 **지연(delay) 방식**과 잘 맞음 |

알림은 "정확히 10건"이 아니라 "대략 하루 10건 넘지 않게"가 목적이므로 **토큰 버킷**이 무난하다.

**제한 축 선택**

```
① 사용자당 전체:        "한 사용자에게 하루 20건까지"
② 사용자 × 채널:        "푸시는 하루 10건, 이메일은 5건"
③ 사용자 × 알림 종류:   "마케팅은 하루 3건, 배송은 무제한"   ← 가장 합리적
```

③인 이유는 항목 10과 같다 — **트랜잭션 알림에는 제한을 걸면 안 된다.** 결제 완료나 보안 알림이 "오늘 한도 초과"로 안 나가면 사고다.

```
마케팅 알림:  하루 3건 제한
배송 알림:    제한 없음 (주문을 10개 하면 10번 가야 함)
보안 알림:    제한 없음 (절대)
```

**카운터 저장 — Redis가 사실상 표준**

```
INCR user:123:marketing:20260814              ← 원자적 증가
EXPIRE user:123:marketing:20260814 86400      ← 자동 만료
```

- **원자적 연산**: 여러 알림 서버가 동시에 증가시켜도 정확 (항목 8의 race condition과 같은 문제)
- **TTL**: 날짜가 바뀌면 자동 소멸 — 별도 정리 작업 불필요
- **빠름**: hot path에 있으므로 DB로는 부담

**검사 위치**: 항목 10과 같이 **알림 서버(큐에 넣는 시점)**. 한도 초과분을 큐에 넣어봐야 버릴 것이므로.

> **주의 — 카운터와 실제 전송의 불일치**
> ```
> 알림 서버에서 카운터 증가 → 큐 → 워커 전송 실패 → 재시도 소진 → 최종 실패
>                                        ↑
>                       카운터는 올라갔는데 실제로는 안 나감
> ```
> 엄밀히는 전송 성공 시점에 올려야 하지만, 그러면 워커에서 증가시켜야 하고 큐에 이미 들어간 것들 때문에 한도를 넘길 수 있다. 실무에서는 대체로 **알림 서버에서 증가시키고 이 오차를 감수**한다.

### digest(묶어 보내기)를 어떻게 구현하는가 — 워커를 단순하게 유지하라

**워커에 묶는 로직을 넣으면 안 된다.** 워커는 큐에서 메시지를 **하나씩** 꺼내는 구조라 "20건을 모아 하나로 합친다"가 구조적으로 어색하다. 꺼낸 20건이 같은 사용자 것인지도 알 수 없다.

**항목 10의 예약 알림과 똑같은 구조를 쓴다.**

```
[알림 서버]
   ↓ 한도 초과 판정
[DB에 status = 'HELD' 로 보류]      ← 큐에 안 넣음
   ↓
[digest 스케줄러가 주기적으로 조회]
   WHERE status = 'HELD' GROUP BY user_id
   ↓ 사용자별로 묶어 알림 하나 생성
   "새 알림 20건이 있습니다"
   ↓
[큐] → [워커: 그냥 전송]
```

**워커는 여전히 단순하다** — 큐에서 하나 꺼내 하나 보낼 뿐. 묶는 로직은 큐 **앞단**에 있다.

> **복잡한 판단 로직은 큐 앞에 두고, 워커는 단순 전송기로 유지한다.**

이유는 항목 5에서 나왔다 — 워커는 **I/O bound라 대수를 많이 늘리는 컴포넌트**다. 복잡한 로직이 들어가면 20대에 배포할 때마다 위험이 커지고, 상태를 갖게 되면 병렬 처리도 어려워진다.

**항목 10의 예약 알림과 항목 11의 digest는 같은 패턴이다.**

```
[알림 서버] → [DB에 보류] → [스케줄러] → [큐] → [워커]
                              ↑
              예약: 시간이 되면 투입
              digest: 모아서 하나로 만들어 투입
```

즉 **"큐에 언제 넣을지 결정하는 계층"** 이 하나 더 있는 셈이며, 이것이 설계에 **스케줄러 컴포넌트**를 추가하는 근거다. (최종 설계 그릴 때 누락 주의)

**상태 확장**: `notification` 테이블이 아웃박스 + 알림 로그 + **보류함** 역할까지 겸하게 되고, `status`에 `HELD`가 추가된다.
```
PENDING → QUEUED → SENT
    ↓
  HELD → (digest로 묶임) → QUEUED → SENT
```

### 실제 세계 (도구 · 제품 · 논문)
- **APNS/FCM 자체의 제한**: 서드파티도 나름의 제한을 건다. FCM은 프로젝트당 초당 요청 수 제한이 있고 APNS도 과도한 요청 시 429를 반환한다. → **우리가 거는 제한(사용자 보호)과 서드파티가 거는 제한(시스템 보호)이 별개로 존재**한다.
- **Do Not Disturb 시간대**: 항목 10의 야간 전송 규제와 엮인다. 단순 횟수 제한이 아니라 **"밤 9시~아침 8시엔 마케팅 알림 발송 자체를 금지"** 하는 시간 기반 제한이 실무에선 더 중요할 수 있다.
- **Digest/Batching**: 링크드인·페이스북은 개별 알림을 즉시 보내지 않고 일정 시간 모았다가 "새 소식 12건"으로 묶어 보낸다. 전송 비용과 알림 피로를 동시에 줄이지만 구현이 복잡해진다.

### 내 말로 정리

4장의 처리율 제한은 서버에 과부하가 걸리지 않게 제한하는 것이고, 이건 고객을 대상으로 **고객이 피로하지 않게** 하기 위한 처리율 제한이다. 그래서 꼭 필요한 알림(구매, 배송 등 고객이 거부 여부를 선택할 수 없는 알림)을 제외하고, 그 외의 알림은 하루 제한이나 시간 제한을 걸 수 있게 하는 것이다.

제한 축은 **알림 종류**가 가장 맞다. 꼭 필요한 정보를 전달해야 하는 알림은 제한하면 안 되고, 그 외의 마케팅성 알림을 제한해서 사용자의 피로를 낮추는 게 좋다. 특정 시간 이후에 한꺼번에 "새 알림 20건" 이런 식으로 묶어서 보내는 게 좋을 것 같다. 이것에 대해서는 아웃박스 테이블이 무조건 필수일 것 같다.
(→ 보완: 묶는 로직을 **워커에 넣으면 안 된다.** 워커는 큐에서 하나씩 꺼내는 구조라 묶기가 어색하다. 대신 항목 10의 예약 알림과 같은 구조로 — DB에 `HELD`로 보류하고 **digest 스케줄러**가 사용자별로 묶어 큐에 투입한다. 원칙: **복잡한 판단 로직은 큐 앞에, 워커는 단순 전송기로.**)

## 12. 재시도 메커니즘 🎤
- **유형**: 핵심 개념 + 관련 심화

### 무엇인가 · 왜 중요한가

항목 7에서 "유실 불가"를 위해 재시도가 필요하다고 했고, 항목 8에서 "재시도 때문에 중복이 생긴다"고 했다. 그 재시도를 **실제로 어떻게 구현하느냐**가 이 항목이다.

책의 설명은 한 문장뿐이다.

> 제3자 서비스가 알림 전송에 실패하면, 해당 알림을 **재시도 전용 큐**에 넣는다. 같은 문제가 계속해서 발생하면 **개발자에게 통지한다(alert)**.

여기에 두 가지 결정이 담겨 있다.
1. 실패한 알림을 **원래 큐가 아닌 별도 큐**로 보낸다
2. 무한 재시도가 아니라, 어느 시점엔 **사람에게 넘긴다**

### 용어 정리 — 재시도 큐 ≠ DLQ

```
[메인 큐] → 실패 → [재시도 큐] → 대기 후 메인 큐로 복귀 → 다시 시도
                        ↓ 5회 소진
                    [DLQ] → 여기서 멈춤. 사람이 확인.
```

- **재시도 큐**: 잠깐 쉬었다가 **다시 시도할** 메시지
- **DLQ(Dead Letter Queue)**: 포기하고 **사람이 봐야 할** 메시지

헷갈리는 이유는 RabbitMQ의 **DLX(Dead Letter Exchange)** 라는 기능 이름 때문이다. DLX는 "이 큐에서 메시지가 죽으면 어디로 보낼지"를 정하는 **라우팅 장치**일 뿐이고, 두 용도로 모두 쓰인다.

```
재시도 구현:  retry 큐에서 TTL 만료 → DLX → 메인 큐로 복귀
DLQ 구현:     메인 큐에서 최대 재시도 초과 → DLX → DLQ에 주차
```

### 동작 원리

**왜 원래 큐가 아니라 재시도 전용 큐인가**

```
[큐: A B C D E ...] ← 정상 알림들이 대기 중
   ↑ 실패한 A를 다시 넣으면

문제 1: A가 즉시 재시도됨 → 서드파티가 여전히 다운 → 또 실패 → 무한 루프
문제 2: A가 계속 자원을 잡아먹어 정상 알림 B C D가 밀림
```

서드파티가 다운됐다면 **시간을 두고 기다려야** 하는데, 원래 큐에 넣으면 그 통제가 안 된다.

> 재시도 큐로 보내는 건 "여러 번 시도한 끝에"가 아니라 **첫 실패부터**다. 워커 안에서 즉시 3번 돌려봐야 소용없다(서드파티가 다운됐으면 3번 다 실패). 시간을 벌려면 큐 밖으로 내보내야 한다.

**지수 백오프(exponential backoff)**

```
1차 실패 → 1초 후 재시도
2차 실패 → 2초 후
3차 실패 → 4초 후
4차 실패 → 8초 후
5차 실패 → 16초 후
→ 소진 시 DLQ로
```

간격을 두 배씩 늘리는 이유는 **장애 난 서드파티에게 회복할 시간을 주기 위해서**다. 다운된 서버에 요청을 계속 퍼부으면 오히려 회복을 방해한다(**thundering herd**).

**지터(jitter)**

```
백오프만 있으면: 1000건이 동시에 실패 → 전부 정확히 1초 후 재시도 → 또 동시에 몰림
지터를 더하면:   각자 0.5~1.5초 사이 랜덤 → 부하 분산
```

`대기시간 = min(최대값, 기본값 × 2^시도횟수) × (0.5 + random())`

**언제 재시도하면 안 되는가**

```
✅ 재시도해야 함 (일시적 오류)
   - 타임아웃, 연결 실패
   - 500 Internal Server Error
   - 429 Too Many Requests (서드파티 제한)
   - 503 Service Unavailable

❌ 재시도하면 안 됨 (영구적 오류)
   - 400 Bad Request (페이로드가 잘못됨 — 몇 번 보내도 똑같음)
   - 401/403 (인증 실패 — 키를 고쳐야 함)
   - 무효한 단말 토큰 (앱이 삭제됨 — 영원히 실패)
```

무효 토큰을 계속 재시도하는 건 자원 낭비일 뿐 아니라 **APNS가 과도한 무효 토큰 전송자를 제재**하기도 한다. → 무효 토큰 응답을 받으면 **재시도가 아니라 DB에서 device 행을 삭제**해야 한다 (항목 3의 토큰 정리).

**DLQ와 "개발자에게 통지"**

```
[원래 큐] → 실패 → [재시도 큐] → 5회 소진 → [DLQ]
                                              ↓
                                    개발자 알림 + 수동 분석
```

DLQ의 존재 이유는 **"버리지 않기 위해서"** — 항목 7의 "유실 불가" 요구와 이어진다. 통지 조건: DLQ에 N건 이상 적재, 특정 채널 실패율 임계치 초과, 같은 오류 코드 반복 등.

> **재귀적 문제**: 알림 시스템이 고장났는데 개발자에게 어떻게 알리나? 알림 시스템으로 알리면 그것도 실패할 수 있다. → **운영 알람은 알림 시스템과 완전히 분리된 경로**(PagerDuty, Slack 웹훅, 별도 모니터링 SaaS)를 써야 한다.

### RabbitMQ에서 지연을 구현하는 방법 (심화)

**전제: RabbitMQ의 TTL은 Redis와 무관하다.** 브로커가 자체 제공하는 기능이다.

메시지는 문자열이 아니라 **본문 + 메타데이터** 묶음이며, 브로커 프로세스의 메모리(+디스크)에 객체로 존재한다.
```
메시지 하나
├─ body (본문)        : {"user_id":123, "template_id":42, ...}
├─ properties (속성)  : content-type, delivery-mode, expiration, ...
└─ headers (헤더)     : x-retry-count: 3, x-death: [...]
```

TTL 동작:
```
1. 큐 선언 시 x-message-ttl = 30000 (30초) 설정
2. 메시지가 그 큐에 들어옴 → 브로커가 진입 시각 기록 (10:00:00)
3. 만료 시각 계산 = 10:00:30
4. 만료되면 브로커가 큐에서 제거
5. DLX가 설정돼 있으면 그리로 라우팅, 없으면 폐기
```

| | Redis | RabbitMQ |
|---|---|---|
| TTL 대상 | 키(key) | 메시지(message) |
| 만료되면 | **삭제만** 됨 | 삭제되거나 **DLX로 이동** |
| 만료 감지 | 접근 시 + 백그라운드 샘플링 | **큐 맨 앞 메시지만 검사** |
| 목적 | 캐시 자동 정리 | 지연 배달, 오래된 메시지 폐기 |

**"만료되면 다른 곳으로 보낼 수 있다"** 가 RabbitMQ만의 특징이고, 그래서 지연 배달 트릭이 가능하다.

**방식 ① TTL + DLX (플러그인 없음)**

```java
Map<String, Object> args = new HashMap<>();
args.put("x-message-ttl", 30000);                      // 30초 후 만료
args.put("x-dead-letter-exchange", "main-exchange");   // 만료되면 여기로
args.put("x-dead-letter-routing-key", "push");
channel.queueDeclare("retry-30s", true, false, false, args);
```

이게 전부다. **이 큐에는 소비자를 붙이지 않는다.** 메시지가 30초 앉아 있다가 만료되면 브로커가 자동으로 `main-exchange`로 옮긴다. 우리가 짤 코드는 없고 큐 선언 설정 한 번뿐.

```
[워커: 전송 실패] → retry-30s 큐에 publish
                        ↓ (소비자 없음, 그냥 대기)
                        ↓ 30초 경과 → TTL 만료
                        ↓ 브로커가 자동으로 DLX로 이동
                   [main-exchange] → [원래 큐] → [워커 재시도]
```

**head-of-line blocking — 메시지 단위 TTL을 쓸 때만 발생하는 문제**

전제: retry 큐를 **하나만** 만들고 메시지마다 다른 `x-expiration`을 주는 경우.

```
10:00:00  알림 A가 4번째 실패 → 60초 지연 → x-expiration=60000 으로 publish
10:00:01  알림 B가 1번째 실패 →  1초 지연 → x-expiration=1000  으로 publish

retry 큐:  [ A ]  [ B ]      ← 큐는 FIFO, 들어온 순서대로 줄 섬
            ↑맨앞   ↑뒤
      만료예정      만료예정
      10:01:00     10:00:02

10:00:02  → B는 지금 만료돼야 함. 그런데 브로커는 맨 앞(A)만 검사
             A는 아직 58초 남음 → "만료된 것 없음" → B는 갇힘 ❌
10:01:00  → A 만료 → 나감. 이제 B가 맨 앞 → 그제서야 나감

결과: B는 1초 뒤 재시도돼야 했는데 실제로는 60초 뒤 재시도됨
```

**브로커가 맨 앞만 검사하는 이유**: 큐는 **들어온 순서**로 정렬돼 있지 **만료 시각 순**이 아니다. 만료된 걸 다 찾으려면 매번 큐 전체를 훑어야 하는데(O(n)) 메시지가 100만 건이면 감당이 안 된다. 그래서 **게으른 방식(lazy expiration)** 을 쓴다. RabbitMQ 공식 문서에 명시된 동작.

**큐 단위 TTL은 왜 괜찮은가**: 모든 메시지가 같은 TTL이라 **들어온 순서 = 만료 순서**가 자동 보장된다.
```
retry-30s 큐 (모두 TTL 30초):
[A: 10:00:00 진입 → 10:00:30 만료]  [B: 10:00:01 진입 → 10:00:31 만료]
맨 앞만 검사해도 순서가 딱 맞음 ✅
```

**방식 ② delayed message exchange 플러그인**

플러그인은 TTL+DLX를 개선하는 게 아니라 **완전히 대체**한다. **retry 큐 자체가 없어진다.**

```
■ TTL + DLX 방식
[워커: 실패] → publish → [retry-30s 큐]  ← 메시지가 큐 안에 실제로 들어가 있음
                              ↓ 30초 후 TTL 만료 → DLX
                         [메인 큐] → [워커]

■ 플러그인 방식
[워커: 실패] → publish (header: x-delay=30000) → [지연 exchange]
                                                       │
                                    메시지가 exchange 안에 붙잡혀 있음
                                    (아직 어떤 큐에도 안 들어감)
                                                       ↓ 30초 후
                                                  [메인 큐] → [워커]
```

**핵심 차이는 "메시지가 어디서 기다리느냐"** 다.
- TTL+DLX: **큐 안에서** 대기 → FIFO라 앞뒤 순서에 갇힘
- 플러그인: **exchange 안에서** 대기 → 큐가 아니라 순서 제약 없음. 내부적으로 **만료 시각 순 정렬 저장소**를 사용

```java
// TTL + DLX: 재시도 횟수에 맞는 큐를 골라 보냄
String retryQueue = "retry-" + RETRY_DELAYS[retryCount] + "s";
channel.basicPublish("", retryQueue, null, body);

// 플러그인: 큐는 하나, 지연 시간만 헤더로 지정
Map<String, Object> headers = Map.of("x-delay", 1000 * RETRY_DELAYS[retryCount]);
channel.basicPublish("delayed-exchange", "push", propsWith(headers), body);
```

**세 방식 비교**

| 방식 | 구조 | head-of-line 문제 |
|---|---|---|
| retry 큐 1개 + 메시지별 TTL | 큐 하나에 서로 다른 TTL 섞임 | **발생** ❌ |
| retry 큐 여러 개 + 큐별 TTL | `retry-1s`, `retry-2s`... 각 큐 안은 TTL 동일 | 없음 ✅ |
| delayed message exchange 플러그인 | retry 큐 자체가 없음 | 없음 ✅ |

| | 큐 여러 개 | 플러그인 |
|---|---|---|
| 설치 | 불필요 (기본 기능) | **플러그인 설치 필요** |
| 큐 개수 | 백오프 단계만큼 (5단계면 5개) | 1개 |
| 지연 시간 | **미리 정한 값만** | 임의 값 자유롭게 |
| 지터 | 넣기 어려움 | 가능 |
| 운영 | 큐가 늘어 모니터링 대상 증가 | 지연 메시지가 브로커 메모리 점유 |

**지터 가능 여부 정리**

| 상황 | 지터 |
|---|---|
| 큐 단위 TTL (retry 큐 여러 개) | **진짜 지터는 불가** — 지연값이 큐마다 고정 |
| 위 방식 + 큐를 촘촘히 만들고 랜덤 선택 | **흉내 가능** — `retry-25s`/`retry-30s`/`retry-35s` 중 랜덤 |
| 메시지 단위 TTL | 값은 자유롭지만 head-of-line 때문에 **신뢰 불가** |
| delayed message exchange 플러그인 | **완전히 가능** — `x-delay`에 랜덤값 |

→ RabbitMQ에서 제대로 된 지터를 쓰려면 **플러그인이 사실상 필수**.

### RabbitMQ가 해주는 것 vs 우리가 짜야 하는 것

| | RabbitMQ | 우리 코드 |
|---|---|---|
| TTL 만료 감지 | ✅ | |
| 만료 시 DLX로 이동 | ✅ | |
| **재시도 횟수 기록** | ✅ `x-death` 헤더에 자동 누적 | |
| 몇 번째인지 판단 | | ✅ 헤더를 읽어야 함 |
| 어느 retry 큐로 보낼지 결정 | | ✅ |
| 최대 초과 시 DLQ로 보내기 | | ✅ |

**RabbitMQ가 자동으로 붙여주는 `x-death` 헤더** — 메시지가 DLX를 거칠 때마다 이력이 쌓인다.
```json
"x-death": [
  { "count": 3, "reason": "expired", "queue": "retry-2s", "time": "..." }
]
```
→ **횟수 세는 일은 안 해도 되고, 읽어서 판단하는 일만 우리 몫.**

```java
@RabbitListener(queues = "push-queue")
void handle(Message message) {
    try {
        apnsClient.send(message);
    } catch (RetryableException e) {
        int retryCount = readDeathCount(message);      // x-death에서 읽기

        if (retryCount >= MAX_RETRY) {
            rabbitTemplate.send("dlq", message);       // 포기
            alerting.notifyDeveloper(message);         // 개발자 통지 (알림 시스템 아닌 경로로)
            return;
        }
        String retryQueue = "retry-" + RETRY_DELAYS[retryCount] + "s";
        rabbitTemplate.send(retryQueue, message);      // 다음 단계 큐로
    }
}
```

> `1 << n` 은 왼쪽 시프트로 `2^n`이다 (`1<<0=1`, `1<<1=2`, `1<<2=4`, `1<<3=8`). 비트를 왼쪽으로 밀 때마다 자릿값이 두 배가 되므로 2를 곱하는 효과. 다만 가독성을 위해 `RETRY_DELAYS = {1,2,4,8,16}` 배열로 두는 편이 낫다 — 간격 조정 시 배열만 고치면 된다.

### 지연 구현 방식은 지연 시간의 길이가 가른다

```
지연이 초~분 단위 (재시도)   → 큐의 지연 기능
지연이 시간~일 단위 (예약)   → DB 폴링
```

**긴 지연이 DB로 가야 하는 이유**
- SQS `DelaySeconds`는 최대 15분 — 애초에 불가능
- 큐에 3일치를 쌓으면 큐가 저장소가 됨 (항목 9의 원칙 위반)
- **취소 불가** — 큐에 들어간 메시지는 골라서 뺄 수 없음
- 조회 불가 — "이 사용자의 예약 알림 목록"을 못 봄

반대로 짧은 지연을 DB 폴링으로 하면 낭비다. 1초 지연을 위해 스케줄러가 1초마다 DB를 긁는 건 비효율적.

| 용도 | 지연 | 구현 |
|---|---|---|
| 재시도 | 1초~수 분 | 큐 지연 기능 (TTL+DLX, 플러그인, SQS DelaySeconds) |
| 예약 알림 | 시간~일 | DB `scheduled_at` + 스케줄러 폴링 |
| digest | 수 시간 | DB `HELD` + digest 스케줄러 (항목 11) |

### 실제 세계 (도구 · 제품 · 논문)
- **서킷 브레이커(Circuit Breaker)**: 재시도보다 한 단계 위의 방어. 특정 서드파티의 실패율이 임계치를 넘으면 **아예 호출을 중단하고 즉시 실패 처리**한다. 죽은 서비스에 요청을 보내며 워커 스레드를 낭비하지 않기 위함. Java는 **Resilience4j**가 표준이고, 회복되면 조금씩 호출을 재개(half-open)한다.
- **APNS의 무효 토큰 응답**: `410 Unregistered` 또는 `400 BadDeviceToken`. FCM은 `UNREGISTERED`. 받으면 재시도가 아니라 토큰 삭제.
- **재시도 횟수와 지연의 트레이드오프**: 많이 재시도하면 성공률은 오르지만 큐가 밀리고 사용자는 한참 뒤에 받는다. "3일 뒤 도착한 배송 알림"은 없느니만 못하다. → **알림 종류별로 다른 재시도 정책**(보안은 끈질기게, 마케팅은 한 번 실패하면 포기).

### 내 말로 정리

실패한 알림을 별도 재시도 큐로 보내는 이유는, 기존 큐들에 쌓여 있는 다른 작업들을 방해하지 않기 위해서다. 그래야 기존의 알림 서비스가 방해받지 않는다.
(→ 보완: 첫 실패부터 바로 재시도 큐로 보낸다. 워커 안에서 즉시 여러 번 돌려봐야 서드파티가 다운됐으면 다 실패하므로 의미가 없다.)

모든 실패를 재시도하면 안 되는 이유는, 애초에 payload가 잘못됐거나 토큰이 만료된 작업인데 재시도해봤자 의미가 없기 때문이다. 서드파티의 에러로 인한 타임아웃이나 503 같은 에러가 아닌 이상 무지성으로 재시도하면 안 된다.

**RabbitMQ 지연 구현 정리**: 큐 단위 TTL을 안 건다는 전제 하에 retry 큐를 하나만 만들고 그 안에 메시지별 TTL을 걸면 head-of-line blocking이 발생한다. 이건 ① retry 큐를 여러 개 만들고 큐마다 TTL을 다르게 하거나, ② delayed message exchange 플러그인을 쓰면 해결된다. 그래서 RabbitMQ에서 지터를 제대로 쓰려면 플러그인이 필요하다.

재시도 횟수에 따라 적절한 retry 큐로 보내는 건 **RabbitMQ가 해주지 않고 우리가 코드로 짜야 한다.** 다만 횟수 기록은 `x-death` 헤더에 자동으로 쌓이므로 읽어서 판단만 하면 된다.

## 13. 푸시 알림과 보안 (appKey / appSecret)
- **유형**: 핵심 개념 + 참고문헌 [6]

### 무엇인가 · 왜 중요한가

항목 5에서 알림 서버의 첫 기능이 **"스팸 방지를 위해 사내 서비스 또는 인증된 클라이언트만 이용 가능"** 이라고 했다. 그 인증을 **어떻게** 하느냐가 이 항목이다.

인증이 없으면 누구나 **우리 앱 이름으로 사용자에게 알림을 보낼 수 있다.** 피싱 메시지가 우리 앱 아이콘을 달고 뜬다 — 단순 스팸이 아니라 브랜드 신뢰 문제.

> iOS와 안드로이드 앱의 경우, 알림 전송 API는 **appKey와 appSecret**을 사용하여 보안을 유지한다. 따라서 **인증된(authenticated) 혹은 승인된(verified) 클라이언트만** 해당 API를 사용하여 알림을 보낼 수 있다.

### 동작 원리

**appKey / appSecret = ID와 비밀번호의 서버 버전**

```
appKey    = 공개 식별자 (누가 요청하는가)
appSecret = 비밀 값     (진짜 그 주체가 맞는가)

1. 서비스(예: 과금 서비스)를 알림 시스템에 등록 → appKey, appSecret 발급
2. 알림 요청 시 검증 정보를 함께 전송
3. 알림 서버가 검증 → 통과해야 큐로
```

**중요: appKey/appSecret은 "사용자"가 아니라 "서비스"를 식별한다.**
```
사용자 인증 (일반적인 로그인):  이 사람이 누구인가
서비스 인증 (appKey/Secret):   이 요청을 보낸 시스템이 무엇인가
```
항목 4의 "서비스 1~N"(과금 서비스, 쇼핑몰)이 각자 자기 키를 갖는다.

**appSecret을 그대로 보내면 안 된다 — HMAC 서명**

HTTP 헤더에 appSecret을 그대로 실으면 탈취 시 그대로 도용된다. 실제로는 **appSecret으로 서명(signature)을 만들어 보낸다.**

```
1. 요청 본문 + 타임스탬프를 appSecret으로 HMAC 해싱 → signature 생성
2. 전송하는 것: appKey + timestamp + signature   (appSecret은 전송 안 함)
3. 서버는 저장된 appSecret으로 같은 계산을 해서 signature 비교
```

**핵심 — appSecret 자체를 해시하는 게 아니다.**

```
❌ signature = hash(appSecret)
✅ signature = HMAC(key = appSecret, message = 요청본문 + timestamp)
```

`hash(appSecret)`은 **항상 같은 값**이라 한 번 훔치면 계속 재사용 가능하다 — appSecret을 그냥 보내는 것과 차이가 없다. 요청 내용과 타임스탬프를 섞어야 **요청마다 signature가 달라진다.**

```
10:00:00에 "user 123에게 알림" → signature = a3f9...
10:00:01에 "user 456에게 알림" → signature = 7c2e...   ← 완전히 다름
```

HMAC은 **단방향**이라 signature에서 appSecret을 역산할 수 없다. 서버는 자기가 가진 appSecret으로 같은 계산을 해서 **결과가 같은지 비교**한다.

| 위협 | 어떻게 막히나 |
|---|---|
| appSecret 탈취 | 네트워크를 타지 않으므로 애초에 노출 안 됨 |
| 요청 변조 | 본문이 바뀌면 signature가 안 맞음 |
| 재전송 공격(replay attack) | 타임스탬프가 오래되면(예: 5분 초과) 거부 |

AWS의 서명 방식(**SigV4**)이 정확히 이 구조다.

### 책이 다루지 않은 것 — 보안의 세 층위

책의 설명은 인증 한 층에 그친다. 실제로는 최소 세 층위가 필요하다.

| 층위 | 질문 | 수단 |
|---|---|---|
| **인증(Authentication)** | 누가 요청했는가 | appKey/appSecret, mTLS |
| **인가(Authorization)** | 그 주체가 이걸 할 권한이 있는가 | 서비스별 권한 범위 |
| **입력 검증** | 요청 내용이 안전한가 | 페이로드 검증, 수신자 검증 |

**인가가 빠지면**
```
마케팅 서비스가 유효한 appKey를 갖고 있음
→ 그런데 "보안 알림" 템플릿으로 알림을 보낼 수 있다면?
→ "귀하의 계정에 이상 로그인이 감지되었습니다" 라는 피싱 알림 발송 가능
```

```sql
service_permission
  app_key            varchar
  notification_type  varchar   -- 이 서비스가 보낼 수 있는 알림 종류
  channel            varchar   -- 사용 가능한 채널
```

**입력 검증에서 놓치기 쉬운 것 — 수신자 지정 권한**
```
쇼핑몰 서비스가 "user_id = 아무나"로 알림을 보낼 수 있다면?
→ 자기 고객이 아닌 사람에게도 알림 발송 가능
```

### 서드파티 인증 키 관리

우리 API를 보호하는 것과 별개로, **우리가 서드파티에 인증할 때 쓰는 키**도 관리해야 한다.

```
APNS     : .p8 인증 키 (JWT 서명용)
FCM      : 서비스 계정 JSON
Twilio   : Account SID + Auth Token
Sendgrid : API Key
```

유출되면 **제3자가 우리 앱 이름으로 알림을 보낼 수 있다.** 코드·설정 파일 하드코딩 금지. **비밀 관리 시스템**(AWS Secrets Manager, HashiCorp Vault, K8s Secret)에 저장하고 주기적으로 교체(rotation)해야 한다.

### 참고문헌 [6]이 인용된 이유

> **Security in Push Notifications** — IBM Cloud 문서

"appKey/appSecret으로 보안을 유지한다"는 한 줄을 뒷받침하기 위해 달았다. 다만 이 문서는 IBM의 특정 제품(Mobile Push Notifications 서비스) 사용 가이드라 일반적 보안 원리를 다루는 문헌은 아니다. → 이 항목은 참고문헌보다 **일반적인 API 보안 지식으로 보강하는 편이 낫다.**

### 실제 세계 (도구 · 제품 · 논문)
- **mTLS(상호 TLS)**: 사내 서비스 간 통신에서 API 키보다 강력. 클라이언트도 인증서를 제시해야 연결이 성립한다. 키 유출 걱정이 없지만 인증서 관리 부담이 있다.
- **내부망 격리**: 알림 API를 외부에서 접근 불가능하게 두는 것. 항목 5의 "사내 서비스만"이 이걸 의미할 수도 있다. 다만 사내 서비스가 침해당하면 무방비이므로 인증을 생략할 근거는 못 된다.
- **페이로드 크기 제한**: APNS 4KB, FCM 4KB. 초과하면 서드파티가 거부하므로 우리 쪽에서 미리 검증해야 한다 — 항목 5의 "알림 검증"에 포함.
- **개인정보 노출**: 푸시 알림 본문은 **잠금 화면에 표시**된다. "홍길동님의 결제 금액 50만원"을 그대로 넣으면 옆 사람이 본다. 민감한 내용은 "새 메시지가 도착했습니다" 정도로만 보내고 앱을 열어야 볼 수 있게 하는 것이 원칙.

### 내 말로 정리

인증이 없으면 인증되지 않은 다른 서버가 우리 알림 서버를 통해서 알림을 보내는 것이 가능해진다.
(→ 보완: 발표에서는 **"우리 앱 이름으로 피싱 알림이 뜬다"** 까지 붙이면 심각성이 와닿는다.)

appSecret을 그대로 보내지 않는 이유는 노출될 수 있기 때문이다. 그래서 appSecret을 해시한 값을 보내고(단방향 해시), `appKey + timestamp + signature`를 같이 보내서 서버에서도 appKey에 해당하는 appSecret을 조회해 시그니처 값을 만들어 비교하는 방식을 사용한다.
(→ 보완: **appSecret 자체를 해시하는 게 아니라, appSecret을 열쇠로 써서 "요청 본문 + timestamp"를 해시**한다. `hash(appSecret)`은 항상 같은 값이라 한 번 훔치면 재사용되므로 의미가 없다. 요청 내용을 섞어야 요청마다 signature가 달라지고, 내용 변조·재전송까지 막을 수 있다.)

## 14. 큐 모니터링과 이벤트 추적
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가

책이 인접해서 다루지만 **목적도 대상도 완전히 다르다.**

| | **큐 모니터링** | **이벤트 추적** |
|---|---|---|
| 보는 사람 | 개발자·운영자 | 기획자·마케터·데이터 분석가 |
| 질문 | "시스템이 건강한가?" | "사용자가 알림에 반응하는가?" |
| 대상 | 인프라 지표 | 사용자 행동 |
| 대응 | 워커 증설, 장애 대응 | 알림 문구·타이밍 개선 |

### ① 큐 모니터링

> 알림 시스템을 모니터링할 때 중요한 메트릭 하나는 **큐에 쌓인 알림의 개수**이다. 이 수가 너무 크면 **작업 서버들이 이벤트를 빠르게 처리하고 있지 못하다**는 뜻이다. 그런 경우에는 **작업 서버를 증설**하는 게 바람직할 것이다.

항목 5와 직결된다 — 알림 서버와 워커를 분리했기 때문에 **"큐가 쌓인다 → 워커를 늘려라"** 라는 명확한 신호를 얻는다. 한 몸이었다면 "서버가 느리다"는 뭉뚱그린 정보뿐이었을 것이다.

| 메트릭 | 의미하는 것 |
|---|---|
| **Queue depth** | 대기 중인 메시지 수 — 계속 늘면 워커 부족 |
| **Unacked messages** | 워커가 가져갔는데 ack 안 함 — 워커가 처리 중 멈춤 |
| **Publish rate vs Deliver rate** | 생산 > 소비면 무한정 쌓임 |
| **Consumer utilization** | 워커가 노는 비율 — 낮으면 큐가 못 먹여줌 |
| **Node memory/disk alarm** | 한계 도달 시 생산자 차단(flow control) |

**큐 깊이는 절대값만 보면 안 된다**
```
큐 깊이가 10,000건이다 → 이게 문제인가?

평소 처리 속도가 1,000건/초라면 → 10초면 소진 → 정상
평소 처리 속도가 10건/초라면    → 1000초(17분) → 심각
```
절대값보다 **추세와 소진 예상 시간**이 중요하다. 실무 알람은 "깊이 > 10000"이 아니라 **"깊이가 10분 연속 증가"** 또는 **"예상 소진 시간 > 30분"** 같은 조건으로 건다.

### ② 이벤트 추적

> **알림 확인율, 클릭률, 실제 앱 사용으로 이어지는 비율** 같은 메트릭은 사용자를 이해하는 데 중요하다. (…) 보통 알림 시스템을 만들면 **데이터 분석 서비스와도 통합**해야만 한다.

```
발송(sent) → 전달(delivered) → 열람(opened) → 클릭(clicked) → 전환(converted)
```

**항목 2의 책임 경계가 다시 등장한다.** 우리가 직접 아는 건 `sent`까지뿐이다.

| 이벤트 | 어떻게 아는가 |
|---|---|
| sent | **우리가 직접 기록** (서드파티 2xx 응답) |
| delivered | 서드파티 **웹훅** |
| opened | 이메일은 **추적 픽셀**, 푸시는 **앱 SDK 보고** |
| clicked | 링크에 **추적 파라미터**를 붙여 우리 서버 경유 |
| converted | 앱/웹 분석 도구 연계 |

### 채널마다 측정 가능한 것이 다르다 — 두 개의 독립적인 축

**축 ① 서드파티가 전달 결과를 알려주는가 → `delivered` 가능 여부**

| 채널 | 알려주나 | 이유 |
|---|---|---|
| 이메일 (Sendgrid) | **⭕** | 수신 메일 서버가 "받았다/반송(bounce)"을 응답 → Sendgrid가 웹훅으로 전달 |
| SMS (Twilio) | **⭕** | 통신사가 전달 확인(delivery receipt)을 주는 프로토콜 존재 |
| 푸시 (APNS/FCM) | **❌** | 애플·구글이 개별 단말 전달 결과를 **정책적으로 알려주지 않음.** 우리가 받는 건 "요청 접수함"까지 |

> 푸시가 안 되는 건 기술적 한계가 아니라 **정책**이다. 단말이 꺼져 있으면 나중에 배달할 수도 있고, 그 결과를 발신자에게 일일이 알려주지 않는다.

**축 ② 매체 안에 추적 장치를 심을 수 있는가 → `opened` 가능 여부**

| 채널 | 심을 수 있나 | 방법 |
|---|---|---|
| 이메일 | **⭕** | HTML이므로 **추적 픽셀**(1×1 투명 이미지). 메일을 열면 이미지를 불러오며 우리 서버에 요청 |
| SMS | **❌** | **순수 텍스트**라 아무것도 못 심음 |
| 푸시 | **⭕** | 우리 앱에 **SDK를 심어** "알림 탭했다"를 서버로 보고 |

**두 축을 합치면**

|  | delivered | opened | clicked |
|---|---|---|---|
| **이메일** | ⭕ 웹훅 | ⭕ 추적 픽셀 | ⭕ 추적 링크 |
| **SMS** | ⭕ 통신사 확인 | ❌ 불가 | ⭕ 추적 링크 |
| **푸시** | ❌ 불가 | ⭕ 앱 SDK | ⭕ 앱 SDK |

> **푸시와 SMS가 정반대**다. SMS는 **도착은 아는데 읽었는지 모르고**(통신사는 알려주지만 문자에 뭘 못 심음), 푸시는 **도착은 모르는데 읽으면 안다**(애플은 안 알려주지만 우리 앱이 알려줌).

`clicked`가 세 채널 모두 가능한 이유: **링크는 어디에나 넣을 수 있고 그 링크가 우리 서버를 경유**하기 때문.
```
원본 링크:  https://shop.com/product/123
추적 링크:  https://track.our.com/c/abc123
              → 우리 서버가 클릭 기록 후 원본으로 리다이렉트
```
(항목 9에서 나온 "추적 링크(tracking link)"가 이것이다.)

**설계 함의**: 채널별로 측정 가능한 지표가 다르므로 **"알림 성과"를 하나의 잣대로 비교할 수 없다.** 이메일 오픈율과 푸시 오픈율은 측정 방식 자체가 달라 나란히 놓고 비교하면 안 된다.

**추적 픽셀의 한계**: 요즘 메일 클라이언트가 이미지를 기본 차단하거나, **Apple Mail Privacy Protection**은 아예 모든 이미지를 미리 로드해버려서 정확도가 크게 떨어졌다.

### 설계 단계에서 정해야 할 것

**① 이벤트를 어디로 보낼 것인가**
```
알림 시스템 DB에 같이 저장?
  → 알림 로그가 이벤트로 폭발. 하루 1600만 알림 × 5개 이벤트 = 8000만 행/일

별도 분석 파이프라인으로?
  → Kafka로 흘려보내고 데이터 웨어하우스에 적재
```
**항목 6의 "Kafka는 전사 이벤트 버스로 쓸 때 유리하다"** 가 여기서 다시 나온다. 알림 이벤트를 분석 파이프라인에도 보내야 한다면 Kafka의 다중 소비자 구조가 값어치를 한다.

**② 추적 링크용 리다이렉트 서비스**: 클릭 추적을 하려면 리다이렉트 서버가 필요하고, 이는 **알림 시스템과 별개 컴포넌트**다. 최종 아키텍처에 넣을지 결정해야 한다.

### 실제 세계 (도구 · 제품 · 논문)
- **Datadog, Prometheus + Grafana**: 큐 모니터링 표준 조합. RabbitMQ는 Prometheus 익스포터를 공식 제공.
- **Amplitude, Mixpanel, Firebase Analytics**: 이벤트 추적용 분석 서비스. 책이 "데이터 분석 서비스와 통합해야 한다"고 한 것이 이것들.
- **알림 시스템의 SLO**: "알림의 99%가 30초 내 전송" 같은 목표를 세우려면 **전송 소요 시간(요청 접수 → SENT)** 을 측정해야 하고, 알림 로그에 `created_at`, `sent_at`이 필요하다 (항목 7의 스키마).
- **모니터링의 재귀 문제**: 항목 12와 동일 — 알림 시스템을 감시하는 알람은 알림 시스템을 쓰면 안 된다.

### 내 말로 정리

큐 깊이를 볼 때 절대값만 보면 안 되는 이유는, 큐가 비슷하게 꽉 차 있어도 메시지 처리 속도가 빨라서 10초 안에 소진된다면 상관이 없기 때문이다. 그러므로 **메시지 처리 속도까지 고려**해서 확인해야 한다. 초당 10개 처리하는데 10000개가 차 있으면 큰 문제다.

채널별로 delivered/opened를 알 수 있는지가 갈리는 이유는 두 가지 축 때문이다. ① **서드파티가 전달 결과를 알려주는가** — 이메일·SMS는 알려주지만 푸시(APNS/FCM)는 정책적으로 안 알려준다. ② **매체 안에 추적 장치를 심을 수 있는가** — 이메일은 추적 픽셀, 푸시는 앱 SDK를 심을 수 있지만 SMS는 순수 텍스트라 불가능하다. 그래서 SMS는 도착은 알지만 읽었는지 모르고, 푸시는 도착은 모르지만 읽으면 안다.

## 15. 지역별 서드파티 대체 서비스 (JPush · PushY)
- **유형**: 본문 name-drop + 관련 심화

### 무엇인가 · 왜 중요한가

책이 딱 한 문장으로 지나간 부분이다.

> 또 하나 고려해야 할 것은, 어떤 서비스는 다른 시장에서는 사용할 수 없을 수도 있다는 것이다. 가령 **FCM은 중국에서는 사용할 수 없다.** 따라서 중국 시장에서는 **제이푸시(JPush), 푸시와이(PushY)** 같은 서비스를 사용해야만 한다.

그런데 이 한 문장이 **항목 6에서 RabbitMQ + 직접 워커를 선택한 결정적 근거**였다. SNS를 쓰면 이 요구를 만족시킬 수 없기 때문이다.
→ **책에서 가장 짧게 언급됐지만 아키텍처 선택에 가장 큰 영향을 준 문장.**

### 동작 원리

**왜 FCM이 중국에서 안 되는가** — 기술 문제가 아니라 **접근 차단**이다.

FCM은 구글 서버(`fcm.googleapis.com`)와 지속 연결을 유지해야 작동하는데 중국에서는 구글 서비스 전반이 차단돼 있다.
```
중국 내 안드로이드 폰
  → Google Play Services가 아예 미설치 (샤오미·화웨이·오포 등은 자체 스토어 사용)
  → FCM 수신 자체가 불가능
```
**"느리다"가 아니라 "아예 안 온다"** — 재시도로도 해결되지 않는다.

**iOS는 다르다.** APNS는 중국에서도 작동한다(애플이 중국 내 인프라를 두고 정식 서비스). → 같은 "중국 시장"이라도 **안드로이드만 문제**다.

**대체 서비스**

| 서비스 | 특징 |
|---|---|
| **JPush(极光推送)** | 중국 최대 서드파티 푸시. 여러 제조사 채널을 하나로 묶어줌 |
| **PushY** | 글로벌 서비스지만 중국 지원. 자체 프로토콜로 연결 유지 |
| **제조사 자체 푸시** | 샤오미(MiPush), 화웨이(HMS Push), 오포(ColorOS Push), 비보 등 — **각 제조사가 자기 OS에 심어둔 푸시 채널** |

**중국 시장의 진짜 복잡함**: 서구권은 안드로이드 = FCM 하나면 끝이지만, 중국은 **제조사마다 다른 푸시 채널**을 쓴다. 샤오미 폰은 MiPush, 화웨이 폰은 HMS Push를 써야 알림이 확실히 도착한다.

→ JPush가 존재하는 이유가 이것 — **여러 제조사 채널을 하나의 API로 묶는 중개자**. 우리가 만드는 알림 시스템이 제3자 서비스를 추상화하는 것과 같은 구조다.

### 설계 반영 — 데이터와 코드 두 축

**핵심 질문: "어느 서비스로 보낼지"를 무엇으로 결정하는가?**

```
① 사용자의 국가 (country_code)   → 항목 3의 user 테이블에 이미 있음
② 단말 제조사·OS                  → device 테이블에 추가 필요
③ 앱이 등록한 푸시 채널 종류       → device 테이블에 추가 필요
```

**축 ① 데이터 — device 테이블 확장**

```sql
device
  id                bigint
  user_id           bigint
  device_token      varchar
  platform          varchar   -- ios / android
  push_provider     varchar   -- apns / fcm / jpush / mipush / hms   ← 추가
  last_logged_in_at timestamp
```

`push_provider`를 **컬럼이 아니라 값으로** 관리하므로 새 서비스가 생겨도 스키마 변경이 없다 (항목 1의 알림 설정과 같은 패턴).

> **`push_provider`를 우리가 추측하지 않는다.** 앱이 실행될 때 "나는 어느 푸시 채널에 등록했다"를 토큰과 함께 알려주는 것이 정확하다. 앱은 자기가 어느 제조사 폰에서 도는지, 어느 SDK가 초기화됐는지 안다.

**축 ② 코드 — 인터페이스 분리**

데이터만으론 부족하다. `push_provider = 'mipush'` 라는 값이 DB에 있다고 알림이 나가진 않는다. **실제로 MiPush API를 호출하는 코드**가 필요하다.

항목 4에서 저자가 말한 확장성 요구가 코드 수준에서는 이렇게 나타난다.

> 제3자 서비스와의 통합을 진행할 때 유의할 것은 **확장성(extensibility)** 이다. **쉽게 새로운 서비스를 통합하거나 기존 서비스를 제거할 수 있어야 한다**는 뜻이다.

```java
interface PushSender {
    void send(Notification notification, Device device);
}

class ApnsSender   implements PushSender { ... }
class FcmSender    implements PushSender { ... }
class JPushSender  implements PushSender { ... }
class MiPushSender implements PushSender { ... }
```

워커는 `push_provider` 값을 보고 구현체를 선택한다.
```java
PushSender sender = senderRegistry.get(device.pushProvider());
sender.send(notification, device);
```

**새 서비스 추가 = 값 하나 + 구현체 하나. 워커 코드는 무변경.**

```
데이터 (DB):        push_provider = 'mipush'   ← 무엇으로 보낼지
코드 (인터페이스):   MiPushSender               ← 실제로 어떻게 보낼지
```

항목 1(알림 설정 컬럼→행), 항목 6(exchange 라우팅)과 **같은 사고방식** — **변경이 한 곳에만 닿게 한다.**

### 지역 차이는 SMS·이메일에도 있다

| 채널 | 지역 이슈 |
|---|---|
| **SMS** | 국가마다 통신사 규제가 다름. 한국은 **발신번호 사전 등록** 필수, 인도는 **DLT 등록** 필수. Twilio가 모든 나라를 커버하지 않아 지역별로 다른 사업자가 필요할 수 있음 |
| **이메일** | 중국에서는 Gmail 접근이 제한적 → QQ메일·163메일 등 현지 서비스 대응 필요. GDPR 적용 지역은 데이터 처리 방식 자체가 달라짐 |

> 일반화하면 **`(채널 × 지역)` 조합마다 다른 서드파티가 붙을 수 있다.**

### 실제 세계 (도구 · 제품 · 논문)
- **화웨이 HMS**: 미국 제재로 구글 서비스를 못 쓰게 된 뒤 화웨이가 자체 구축한 생태계. **중국 밖에서 팔리는 화웨이 폰도 FCM이 안 되므로** 글로벌 앱도 HMS Push를 고려해야 한다.
- **UnifiedPush**: 유럽에서 진행 중인 오픈소스 푸시 표준화 시도. 구글·애플 종속을 벗어나려는 움직임.
- **국내 상황**: 한국은 FCM/APNS가 정상 작동하지만 **카카오 알림톡**이 사실상 제4의 채널로 자리잡았다. SMS보다 비용이 싸고 도달률이 높아 실무 알림 시스템에 거의 필수로 들어간다 — 이것도 "지역별 채널"의 한 사례.

### 내 말로 정리

정해진 알림 제공자를 무조건 사용할 수 있는 게 아니라 그때그때 달라지는 서드파티에 대응할 수 있어야 한다. DB에 컬럼으로 추가하면 그때그때 컬럼을 계속 추가해야 하므로, 스키마를 변경하지 않고 확장성에 대응하려면 **데이터(값)로 관리**해야 한다.

**아키텍처 선택에 준 영향**: SNS로는 불가능하다. SNS는 연동되는 서드파티가 정해져 있기 때문이다(APNS/FCM/Baidu 정도). 그래서 중국 샤오미 폰 사용자에게 MiPush로 보내야 한다면 SNS로는 안 되고, 전송 계층을 우리가 직접 구현해야 한다.

**코드 수준 확장성**: 인터페이스를 두고 여러 구현체를 둬야 한다. 그래서 필요한 서드파티가 있을 때마다 **인터페이스를 구현하는 구현체 코드만 추가**하면 된다.
