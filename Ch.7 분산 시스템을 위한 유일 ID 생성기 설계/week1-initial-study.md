# Ch.7 분산 시스템을 위한 유일 ID 생성기 설계 — 학습 정리

## 한눈에 보기

분산 환경에서 유일하고(unique), 숫자로만 구성되고, 64비트에 담기고, 시간순 정렬 가능한 ID를 초당 10,000개씩 만드는 문제. 단일 DB 서버라면 `AUTO_INCREMENT`로 공짜로 해결되지만, 처리량/가용성 한계로 여러 서버로 쪼개는 순간 "조율 없는 유일성"과 "시간순 정렬"을 동시에 만족시키기가 핵심 난제가 된다.

```
다중 마스터 복제  → 조율 필요(k값 동기화), 정렬 불가
UUID             → 조율 불필요, 정렬 불가·128비트·비숫자
티켓 서버         → SPOF, 이중화하면 결국 다중 마스터 복제로 회귀
트위터 스노우플레이크 → 타임스탬프+데이터센터ID+서버ID+일련번호로 5가지 요구사항 전부 충족
                   (숨겨진 전제: 모든 서버 시계가 동기화돼 있어야 함 → NTP로 보완)
```

## 1. 문제 정의와 요구사항
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가
단일 DB 서버라면 `AUTO_INCREMENT`만으로 유일 ID 생성이 끝나는 문제다. 분산 시스템에서 이 문제가 어려워지는 이유는 처리량(초당 10,000개)과 그에 딸린 비즈니스 로직·데이터 저장량을 단일 서버가 감당하지 못해 여러 서버로 쪼개야 하기 때문이다. 서버가 여러 대가 되는 순간, "다음 값 하나 증가"라는 공짜 유일성이 깨진다.

책의 면접 시나리오에서 확정된 5가지 요구사항:
- ID는 유일해야 한다
- ID는 숫자로만 구성되어야 한다
- ID는 64비트로 표현 가능해야 한다
- ID는 발급 날짜순으로 정렬 가능해야 한다 (반드시 1씩 증가할 필요는 없음)
- 초당 10,000개의 ID를 생성할 수 있어야 한다

이 요구사항들이 뒤에 나오는 4가지 후보안(다중 마스터 복제, UUID, 티켓 서버, 스노우플레이크)을 평가하는 기준선이 된다.

### 동작 원리 (요구사항 간의 긴장 관계)
가장 까다로운 지점은 "정렬 가능"과 "숫자/64비트" 두 요구사항이 아니라, **여러 서버가 서로 조율(coordination) 없이 독립적으로 ID를 생성하면서도 시간순 정렬이 가능해야 한다**는 조합이다.

- 정렬 가능 자체는 어렵지 않다 — 타임스탬프를 ID에 넣으면 된다.
- 문제는 여러 서버가 정확히 같은 밀리초에 각자 ID를 만들 때 발생한다. 서버끼리 통신하지 않으므로 서로 무엇을 만들었는지 모르는 채로 유일성을 지켜야 한다.
- 해법의 실마리는 "각 서버에 미리 고유 번호(ID)를 부여"해두는 것 — 타임스탬프만으로는 부족하지만 타임스탬프 + 서버 고유 번호를 합치면 실시간 통신 없이도 충돌을 피할 수 있다. 이 아이디어가 뒤에 나오는 스노우플레이크 구조(타임스탬프 + 데이터센터 ID + 서버 ID + 일련번호)의 뼈대다.

UUID를 예로 들면: UUID는 "유일성"과 "조율 없는 독립 생성"은 쉽게 만족하지만, 숫자로만 구성되지 않고(하이픈·문자 포함) 값 안에 시간 정보가 없어 정렬이 불가능해 이번 요구사항에서 탈락한다. 128비트를 64비트로 임의로 자르는 것도 해법이 아닌데, birthday paradox(생일 문제) 때문에 ID 공간을 줄이면 충돌 확률이 인원(생성 개수)의 제곱에 비례해 급격히 커지기 때문이다.

### 실제 세계 (도구 · 제품 · 논문)
- **Twitter Snowflake**: 이 챕터가 최종적으로 채택하는 해법 — "타임스탬프 + 서버 고유 번호" 아이디어의 실제 구현체
- **Instagram ID 생성 방식** (2012년 엔지니어링 블로그): PostgreSQL 샤드 환경에서 정렬 가능하고 유일한 64비트 ID가 필요했던 동일한 문제 상황
- **Sonyflake(Sony), Discord Snowflake 변형**: 동일한 요구사항(분산 환경, 시간 정렬, 고처리량)을 가진 실제 프로덕션 시스템

### 내 말로 정리
결국 요구사항에는 초당 10,000개의 유일한 ID를 생성할 수 있어야 하는데, 문제는 이 ID만 생성하는 게 아니라 그에 따른 비즈니스 로직을 실행해야 하는 부가적인 부분이 있기 때문에 DB 하나만으로는 이걸 감당하지 못하므로, 하나의 DB 서버만 이용하는 것은 불가능하다. 그런데 하나의 서버만 이용하지 않으면(여러 서버를 쓰면) 순서대로 유일한 ID를 생성하는 것에도 문제가 생기므로, 이 문제를 풀면서도 다중 서버를 사용해야 한다.

다섯 가지 요구사항 중 가장 까다로운 건 처리량(초당 10,000개)이 아니라, 여러 서버가 조율 없이 동시에(같은 밀리초에) ID를 만들어도 정렬 가능하고 유일해야 한다는 부분이다. UUID는 숫자로만 이루어져 있지 않고, 무엇이 먼저 만들어졌는지도 알 수가 없다 — 시계열 개념이 없으니까. 이 경우 각 서버에게 어떤 유일한 수를 미리 부여해두면, 통신 없이도 충돌 없이 정렬 가능한 ID를 만들 수 있을 것 같다.

## 2. 다중 마스터 복제 (multi-master replication)
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가
일반 `AUTO_INCREMENT`는 다음 ID를 만들 때 이전 값에 1을 더한다. 다중 마스터 복제는 1 대신 **k**(현재 사용 중인 데이터베이스 서버의 수)를 더해서, 각 서버가 서로 다른 "번호대"만 사용하게 만드는 방식이다.

예: 서버가 2대(A, B)라면
- 서버 A: 1, 3, 5, 7, ...
- 서버 B: 2, 4, 6, 8, ...

서버를 늘리면 초당 생성 가능한 ID 수도 늘어나므로 처리량 문제는 어느 정도 해결된다. 이 방식은 item 1에서 도달했던 "각 서버에 고유 번호를 부여하자"는 아이디어를 DB 기존 기능(`AUTO_INCREMENT`)으로 가장 단순하게 구현한 첫 번째 후보안이다.

### 동작 원리 (단점)

**단점 1: 여러 데이터 센터로 확장하기 어렵다 — k값 전환 문제**

k(서버 수)는 고정 상수가 아니라 서버 증설/삭제에 따라 바뀐다. 문제는 k가 바뀌는 순간, 이미 돌아가는 모든 서버가 동시에 새 k값으로 갈아타야 한다는 점이다.

```
t0: A, B, C가 모두 k=3으로 운영 중
    A: 1, 4, 7   B: 2, 5, 8   C: 3, 6, 9

t1: 서버 D 추가 결정 → k를 3에서 4로 바꿔야 함
    "새 k=4"를 모든 서버에 전파 시작 (분산 환경 → 즉시 전파 불가)

t2: ⚠️ 전파 중 (서버마다 k에 대한 인식이 다른 구간)
    A ── 이미 k=4로 전환 ──→ 다음 ID = 13
    B ── 아직 k=3 ─────────→ 다음 ID = 11
    C ── 아직 k=3 ─────────→ 다음 ID = 12
    D ── k=4로 새로 합류 ──→ 다음 ID = 4

    이 구간에서는 서버마다 "전체 서버 수"에 대한 합의가 안 끝나서
    오프셋이 어긋나 충돌 위험이 생김

t3: 모든 서버가 k=4로 수렴 완료
    A: ...13,17   B: ...14,18   C: ...15,19   D: ...16,20
```

즉 k값 자체는 미리 알 수 있지만, **그 값이 바뀔 때 모든 서버가 일관되게 전환하는 것**이 분산 합의(consensus) 문제가 되어버린다 — 원래 이 방식이 피하려던 "서버 간 조율"이 서버 수 변경 시점에는 오히려 필요해지는 것. 클라우드(AWS Auto Scaling 등)처럼 트래픽에 따라 서버가 수시로 늘고 줄면 이 전환 구간이 반복적으로 자주 발생해 충돌 위험이 상시화된다. (→ 단점 3 "서버 추가/삭제 시 어렵다"와 같은 뿌리의 문제)

**단점 2: 시간순 정렬을 보장할 수 없다**

각 서버가 처리하는 속도가 다르므로, ID 값의 크기와 실제 생성 시각의 순서가 어긋날 수 있다.

```
실제 시간 흐름 (B가 A보다 처리 속도가 빠른 경우)

  B: ID=2 → ID=4 → ID=6 → ID=8 → ID=10   (먼저, 빠르게 생성)
  A:                                ID=1 → ID=3 → ID=5   (한참 뒤에 생성)

  ID 값 기준 정렬:     1 < 3 < 5 < 6 < 8 < 10
  실제 생성된 시각 순:  2,4,6,8,10 (먼저) → 1,3,5 (나중)

  ⇒ A가 나중에 만든 ID=5가, B가 먼저 만든 ID=6보다 값은 작음
  ⇒ ID 값만 보고는 생성 시각 순서를 알 수 없음
```

**단점 3: 서버 추가/삭제 시 잘 동작하도록 만들기 어렵다** — 단점 1과 같은 원인(k값 전환 시 전역 일관성 필요)

### 실제 세계 (도구 · 제품 · 논문)
- **MySQL Multi-Master Replication**의 `auto_increment_increment` / `auto_increment_offset` 설정이 정확히 이 방식이다 — 각 마스터가 서로 다른 offset에서 시작해 step(=k)만큼 증가시킨다.
- 데이터센터 확장이 잦지 않은 소규모 서비스의 DB 이중화에는 쓸 만하지만, 서버 수가 자주 바뀌는 대규모/클라우드 환경에서는 한계 때문에 잘 쓰이지 않는다.

### 내 말로 정리
k값을 전역적으로 동기화하는 게 어려운 이유는, k값 자체는 미리 알고 있어도 그게 바뀔 때(서버 추가/삭제) 모든 서버가 동시에 새 k값으로 전환됐는지 확인할 방법이 없기 때문이다. AWS 같은 클라우드 서비스를 사용하면 서버 수 증설 및 삭제가 훨씬 용이하니까, 그때그때 k값을 바로바로 동기화하는 게 더 어려워진다.

시간순 보장이 안 되는 이유는 각 서버가 k값만큼 증가하는 ID를 생성할 텐데, 서버마다 처리하는 속도가 다르기 때문에 ID 값이 크다고 해서 꼭 시간적으로 나중에 만들었다고 장담할 수 없다. A서버가 5를 생성하고 B서버가 6을 생성했다고 해도, 실제로는 6이 먼저 생성됐을 수 있다.

## 3. UUID (참고문헌 [1] UUID 위키피디아 포함)
- **유형**: 핵심 개념 + 참고문헌

### 무엇인가 · 왜 중요한가
UUID(Universally Unique Identifier)는 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 **128비트** 수다. `09c93e62-50b4-468d-b9d8-c07e1040bfb2`처럼 32개의 16진수(hex)와 하이픈으로 표현된다.

충돌 가능성은 극히 낮다 — 위키피디아를 인용하면 "중복 UUID가 1개 생길 확률을 50%로 끌어올리려면 초당 10억 개씩 100년을 계속 만들어야 한다." 이 인용의 역할은 "UUID가 정말 안 겹칠까?"라는 의심을 수치로 차단해두는 데 있다. 즉 **저자가 UUID를 탈락시키는 이유는 충돌 위험 때문이 아니라는 것**을 명확히 하기 위한 근거다 — 유일성은 완벽히 검증됐고, 탈락 이유는 순전히 구조적 문제(128비트, 정렬 불가, 비숫자)라는 걸 강조한다. (128비트라는 거대한 공간 덕분에 birthday paradox 관점에서도 이 정도 생성량엔 충돌 확률이 무시할 수준으로 유지된다.)

### 동작 원리
각 서버(또는 클라이언트)가 완전히 독립적으로 UUID를 생성한다. 다른 서버와 통신도, 중앙 조율자도 필요 없다.

**장점**
- 생성이 단순하다 — 서버 간 조율이 필요 없어 동기화 이슈가 없다 (다중 마스터 복제의 k값 동기화 문제가 애초에 존재하지 않음)
- 각 서버가 알아서 만드는 구조라 규모 확장이 쉽다

**단점**
- 128비트로 길다 (요구사항은 64비트)
- 시간순으로 정렬할 수 없다
- 숫자가 아닌 값(16진수 문자, 하이픈)이 포함된다

### 실제 세계 (도구 · 제품 · 논문)
- **UUID v4**: 대부분 무작위 값 — Java `UUID.randomUUID()`, Python `uuid.uuid4()`, JS `crypto.randomUUID()` 등 표준 라이브러리 내장
- **UUID v1**: 타임스탬프 + MAC 주소 기반이지만 MAC 주소가 앞이 아닌 뒤쪽 비트에 있어 사전식 정렬이 시간순과 다름 — 정렬 키로 부적합
- **UUID v7** (2024년 RFC 9562로 표준화): 타임스탬프를 앞쪽 비트에 배치해 정렬 가능한 UUID를 만든 최신 버전. 다섯 요구사항과 대조하면:

  | 요구사항 | UUID v7 |
  |---|---|
  | 유일해야 함 | ✅ |
  | 초당 10,000개 생성 | ✅ |
  | 발급 날짜순 정렬 가능 | ✅ (해결됨) |
  | 64비트로 표현 가능 | ❌ (여전히 128비트) |
  | 숫자로만 구성 | ❌ (여전히 16진수+하이픈) |

  즉 v7은 "정렬 불가" 단점 하나만 해결했고, 나머지 두 구조적 단점은 그대로 남아 이 챕터의 요구사항에는 여전히 부적합하다. (책은 2020년경 집필되어 애초에 v7을 고려할 수 없었던 시기이기도 함)
- **분산 DB의 PK 사례**: MongoDB `ObjectId`(12바이트, 타임스탬프 포함), Cassandra `TimeUUID` 등도 "조율 없는 독립 생성 + 어느 정도 시간 정보"를 절충한 사례

### 내 말로 정리
UUID는 중복되지 않는 ID를 만들어내는 알고리즘이고, 16진수를 사용해서 128비트의 숫자 + 하이픈 + 문자열을 사용해서 ID를 만들어내는 알고리즘이다. 유일성과 초당 10,000개 생성은 만족하고, 2026년 현재는 이전과 다르게(UUID v7 덕분에) 발급 날짜순으로 표현이 가능하지만, 설계 요구사항의 64비트로 구현하는 것과 숫자로만 구성하는 것에는 부합하지 않는다.

## 4. 티켓 서버 (ticket server) (참고문헌 [2] Flickr Ticket Servers 포함)
- **유형**: 핵심 개념 + 참고문헌

### 무엇인가 · 왜 중요한가
`AUTO_INCREMENT` 기능을 가진 데이터베이스 서버 **하나**를 중앙 집중형으로 두고, 이를 "티켓 서버"라 부른다. 모든 애플리케이션 서버는 새 ID가 필요할 때마다 이 티켓 서버 하나에 요청해서 ID를 받아온다. Flickr가 분산 기본 키(distributed primary key)를 만들기 위해 실제로 사용한 기법이다.

지금까지 나온 두 후보(다중 마스터 복제=여러 서버가 조율, UUID=완전 독립)와 달리, 아예 중앙에 하나만 두는 정반대 극단의 발상이다.

### 동작 원리

**장점**
- 유일성이 보장되는, 숫자로만 구성된 ID를 쉽게 만들 수 있다
- 구현이 쉽고 중소 규모 애플리케이션에 적합하다

**단점 — SPOF(Single Point of Failure)**
- 서버가 하나뿐이므로 이 서버에 장애가 나면 이를 이용하는 모든 시스템이 영향을 받아 서비스 전체가 마비될 수 있다.
- 이를 피하려고 티켓 서버를 여러 대 두면, 그 여러 대 사이에서 ID가 겹치지 않도록 동기화해야 하는 문제가 생긴다 — 이는 결국 **다중 마스터 복제에서 겪었던 "여러 서버 간 조율" 문제**로 되돌아가는 것과 본질적으로 같다.
- (참고: 실제로 잘 튜닝된 단일 DB는 초당 10,000개 정도의 처리량은 충분히 감당 가능하므로, 여러 대가 필요한 진짜 이유는 처리량이 아니라 가용성/SPOF 회피다.)

**Flickr의 실제 구현 — REPLACE INTO 트릭**

```sql
CREATE TABLE Tickets64 (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  stub CHAR(1) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  UNIQUE KEY stub (stub)
);

REPLACE INTO Tickets64 (stub) VALUES ('a');
SELECT LAST_INSERT_ID();
```

`REPLACE INTO`는 MySQL 전용 문법으로, UNIQUE 키(`stub='a'`)가 충돌하면 기존 행을 UPDATE하는 게 아니라 **DELETE 후 새로 INSERT**한다.
- 1번째 호출: `stub='a'`인 행이 없으므로 일반 INSERT처럼 동작 → `id=1`
- 2번째 호출: 기존 `id=1` 행을 DELETE하고 새로 INSERT → `AUTO_INCREMENT`가 다시 작동해 `id=2` (삭제돼도 카운터는 되돌아가지 않고 계속 전진)

이 방식의 장점: 테이블에는 항상 딱 1개의 행만 존재해 테이블 크기가 절대 커지지 않고, 동시성 제어를 애플리케이션이 직접 구현할 필요 없이(`UPDATE counter SET id=id+1` 방식이면 레이스 컨디션을 직접 신경 써야 함) MySQL 엔진에 이미 검증된 `AUTO_INCREMENT` 락 메커니즘을 그대로 재사용한다.

**Flickr의 SPOF 회피 — 다중 마스터 복제의 축소판**

Flickr는 티켓 서버를 정확히 **2대** 운영했다: `auto_increment_increment=2`로 설정해 한 서버는 홀수(1,3,5...), 다른 서버는 짝수(2,4,6...)만 발급하도록 했다. 이는 사실상 item 2의 다중 마스터 복제를 **k=2로 고정**해서 쓴 것과 동일하다. 서버 수를 고정함으로써 다중 마스터 복제의 최대 약점("k값이 바뀔 때 전역 동기화 필요")은 피하면서, 한쪽이 죽어도 서비스는 계속되는(잠시 홀수/짝수 한쪽만 발급) 절충안을 얻었다.

### 실제 세계 (도구 · 제품 · 논문)
- **Flickr Ticket Servers** (참고문헌 [2]): "Ticket Servers: Distributed Unique Primary Keys on the Cheap" — 제목의 "on the Cheap"이 시사하듯, 새 분산 시스템을 만드는 대신 이미 운영 노하우가 쌓인 MySQL을 재활용한 실용적 선택. `Tickets32`/`Tickets64` 테이블을 만들어 사진뿐 아니라 여러 리소스가 공통으로 재사용
  - 책에는 없는 실무적 단점: ID 하나 만들 때마다 애플리케이션 서버가 티켓 서버로 **네트워크 왕복**을 해야 해서, 로컬에서 즉시 생성하는 UUID/스노우플레이크 대비 지연이 누적됨
- **Zookeeper의 시퀀셜 노드(sequential znode)**: 중앙 코디네이터가 순번을 매겨주는 방식으로 개념적으로 유사한 발상
- **Redis `INCR`을 ID 생성기로 쓰는 패턴**: 단일 Redis 인스턴스를 중앙 카운터로 쓰는 실무에서 흔한 티켓 서버 변형

### 내 말로 정리
티켓 서버는 요구사항을 거의 만족하지만, 서버를 하나만 두면 그게 SPOF가 되어 서비스 전체가 마비될 수 있기 때문에 여러 대를 둬야 한다. 그런데 티켓 서버를 여러 대 두면 결국 다중 마스터 복제 문제와 동일해진다.

## 5. 트위터 스노우플레이크 (twitter snowflake) 접근법 (참고문헌 [3] Announcing Snowflake 포함)
- **유형**: 핵심 개념 + 참고문헌

### 무엇인가 · 왜 중요한가
지금까지의 세 후보 — 다중 마스터 복제(조율 필요, 정렬 불가), UUID(조율 불필요, 정렬 불가·64비트 초과), 티켓 서버(SPOF, 결국 다중 마스터로 회귀) — 중 5가지 요구사항을 전부 만족시키는 것이 없었다. 스노우플레이크는 이 제약을 모두 동시에 만족시키는 트위터의 해법이다. item 1에서 스스로 도출했던 "각 서버에 미리 고유 번호를 부여해두면 통신 없이도 충돌을 피할 수 있다"는 아이디어가 정확히 이 방법의 뼈대다.

바로 ID를 만드는 대신 각개격파(divide and conquer) 전략으로 64비트 ID를 여러 절(section)로 나눈다.

```
1비트    41비트         5비트           5비트      12비트
[sign] [timestamp]  [datacenter ID]  [server ID]  [sequence]
```

- **사인(sign) 비트** (1비트): 지금은 쓰지 않고 나중을 위해 유보. 양수/음수 구별용
- **타임스탬프** (41비트): 기원 시각(epoch) 이후 몇 밀리초가 지났는지. 트위터는 epoch로 `1288834974657`(2010-11-04 01:42:54 UTC) 사용
- **데이터센터 ID** (5비트): 2⁵ = 32개 데이터센터 지원
- **서버 ID** (5비트): 데이터센터당 2⁵ = 32개 서버 지원
- **일련번호(sequence)** (12비트): 같은 서버가 같은 밀리초 안에 여러 ID를 만들 때만 0보다 커짐 (1밀리초 지날 때마다 0으로 초기화)

### 동작 원리 (5가지 요구사항을 어떻게 만족시키는가)

**조율 없는 유일성**: 데이터센터ID와 서버ID는 시스템 시작 시 미리 정해지는 고정값이다. 서버 A와 서버 B가 정확히 같은 밀리초에 각자 ID를 하나씩 만들어도, 타임스탬프·일련번호가 우연히 같더라도 두 서버에게 미리 부여된 서버ID(및 데이터센터ID)가 다르기 때문에 최종 64비트 값은 절대 같을 수 없다 — 실시간 통신 없이도 보장된다.

**시간순 정렬**: 다중 마스터 복제는 시간이 지나면 값이 대체로 커지긴 해도, 어느 서버에서 무엇이 먼저 만들어졌는지 값만으로 알 수 없었다(A서버의 5가 B서버의 6보다 값은 작아도 실제로는 더 늦게 만들어졌을 수 있음). 스노우플레이크는 타임스탬프가 sign 비트 바로 다음, 즉 **41비트 중 가장 왼쪽(최상위 비트)** 을 차지한다. 정수를 비교할 때 최상위 비트가 결과를 가장 먼저 결정하므로, 데이터센터ID·서버ID·일련번호 값이 무엇이든 상관없이 **타임스탬프가 클수록 전체 ID 값도 항상 크다** — 구조적으로 시간순 정렬이 보장된다.

**64비트 + 숫자만**: 1+41+5+5+12 = 64비트 정수 하나로 완성.

**처리량**: 일련번호 12비트로 밀리초당 최대 4096개(0~4095) 생성 가능 → 초당 약 400만 개까지 가능해 초당 10,000개 요구사항을 여유 있게 충족.

**워커 ID 할당의 1회성 조율 (실제 트위터 구현)**: "조율이 아예 없다"가 아니라, 조율이 필요한 순간을 워커(=ID 생성기 인스턴스) 시작 시점 딱 한 번으로 몰아넣고 그 이후 반복적인 ID 생성에서는 조율을 완전히 없앤 것이다. 트위터의 실제 구현은 각 워커가 시작할 때 **ZooKeeper**(분산 코디네이션 서비스)의 ephemeral sequential znode 기능을 이용해 자동으로 겹치지 않는 워커 ID를 할당받는다 — 사람이 설정 파일에 서버ID를 수동 입력하다 실수로 중복시키는 위험을 없앤 것. 워커가 죽으면 해당 znode가 사라지고 그 ID는 재사용 가능해진다. 이후 ID를 생성할 때마다는 이미 배정된 워커 ID + 로컬 타임스탬프/일련번호만 조합하면 끝이라 더 이상 조율이 필요 없다. (다중 마스터 복제는 서버가 추가/삭제될 때마다 반복적으로 전역 조율이 필요했다는 점과 대비됨)

### 실제 세계 (도구 · 제품 · 논문)
- **참고문헌 [3] "Announcing Snowflake" (트위터 공식 엔지니어링 블로그, 2010)**: 이 참고문헌은 트위터 자신의 Snowflake 이야기만 다룬다. 트윗 저장소를 여러 MySQL 샤드로 쪼개면서 기존 `auto_increment` 방식이 더 이상 통하지 않게 된 배경, UUID를 검토했으나 "대략적인 시간순 정렬(k-ordering)"이 안 된다는 이유로 기각한 과정, Scala + Thrift로 만든 전용 ID 생성 서비스 구조, "눈송이는 세상에 두 개도 같은 게 없다"는 이름의 유래, GitHub(`twitter/snowflake`) 오픈소스 공개까지 포함
- **Discord Snowflake**: 트위터 방식을 거의 그대로 차용, epoch만 Discord 창립 시점(2015-01-01)으로 변경. 이는 참고문헌 자체가 아니라 트위터 공개 이후 다른 회사가 변형해 채택한 사례
- **Instagram ID 생성 방식**: 41비트 타임스탬프 + 13비트 샤드ID + 10비트 시퀀스로 절 구성만 다르게 한 변형
- **Sonyflake (Sony)**: 39비트 타임스탬프(10ms 단위) + 8비트 시퀀스 + 16비트 머신ID로 절 길이를 다르게 최적화한 변형 — 챕터 마무리에서 언급하는 "절의 길이 최적화" 논의를 실제로 구현한 사례

### 내 말로 정리
스노우플레이크는 책에 나온 5가지 요구사항을 모두 만족하기 위해 나온 방법이다. 64비트로 숫자로만 이루어져 있고 각 부분을 중복되지 않게 구성했다.

```
1비트    41비트         5비트           5비트      12비트
[sign] [timestamp]  [datacenter ID]  [server ID]  [sequence]
```

sign 부분은 음수/양수를 나타내는 부분이고, timestamp는 기준으로 잡은 시각부터 현재까지 몇 밀리초가 흘렀는지 나타내는 숫자고, datacenterID는 말 그대로 데이터센터 ID, 서버 ID는 이 ID를 생성하는 워커(이 로직이 실행되는 서버)에 부여되는 ID고, sequence는 동일한 밀리초에 여러 개가 생성되면 그 여러 개에 순서대로 부여되는 숫자다.

같은 밀리초에 두 서버가 동시에 ID를 만들어도 다른 부분은 다 같을 수 있지만 부여된 서버 ID가 있기 때문에 절대 같은 숫자를 가질 수 없다.

다중 마스터 복제도 시간이 지남에 따라 숫자가 커지긴 하지만 어느 서버에서 어떤 게 먼저 만들어졌는지 알 수가 없다 — 숫자 6이 더 크긴 해도 id가 5인 것보다 더 빨리 만들어졌을 수 있기 때문이다. 스노우플레이크에서는 타임스탬프가 가장 왼쪽에 위치해 있기 때문에 시간이 숫자의 크기 여부를 가장 먼저 결정한다.

그리고 한 밀리초에 최대 4095개(4096개)를 생성할 수 있으므로 초당 만 개는 충분히 생성한다.

## 6. 스노우플레이크 64비트 ID 구조 상세
- **유형**: 핵심 개념

### 무엇인가 · 왜 중요한가
item 5에서 41비트 타임스탬프 필드가 있다는 구조는 배웠지만, 이 필드가 실제 시각과 어떻게 상호 변환되는지, 그리고 41비트라는 크기의 한계가 무엇인지는 실무에서 매우 중요한 질문이다: ① ID만 보고 생성 시각을 역산할 수 있는가, ② 이 ID 체계는 영원히 쓸 수 있는가.

### 동작 원리

**① Epoch(에포크)와 타임스탬프 계산**

Epoch는 시간을 측정하는 **기준점(0)**이다. 컴퓨터는 날짜를 직접 저장하지 않고 보통 "기준 시각으로부터 몇 밀리초가 지났는가"라는 숫자로 시간을 표현한다. 가장 유명한 예가 Unix epoch(1970-01-01 00:00:00 UTC)다.

트위터는 이 기준점을 1970년이 아니라 자체 기준점 `1288834974657`(2010-11-04 01:42:54.657 UTC의 Unix 밀리초 값)으로 새로 잡았다. 이 값은 시스템 클럭을 바꾸는 게 아니라 코드에 박아두는 **상수**일 뿐이다.

ID를 생성할 때마다 다음을 계산해 41비트 타임스탬프 필드에 넣는다:
```
timestamp_field = 현재_Unix_밀리초() - EPOCH(2010년 값)
```
따라서 이 기준점이 되는 정확한 순간(2010-11-04 01:42:54.657 UTC)에 ID를 만들었다면 41비트는 전부 0이 되고, 1밀리초가 지날 때마다 1씩 증가한다.

**② 타임스탬프 디코딩 (책의 그림 7-7 예시)**

64비트 ID의 41비트 타임스탬프 부분만 떼어내 실제 시각으로 복원하는 과정:

```
0-00100010101001011010011011000101101011000-01010--000000000000
  └────────── 41비트 타임스탬프 ──────────┘  └DC┘  └───seq───┘

1단계: 41비트를 10진수로 변환 → 297616116568 (EPOCH 기준 경과 ms)
2단계: EPOCH 상수(1288834974657)를 더함 → 1586451091225 (Unix 기준 절대 ms)
3단계: Unix ms를 UTC로 변환 → Apr 09 2020 16:51:31 UTC
```
역으로도 가능하다 — 임의의 UTC 시각을 거꾸로 적용하면 41비트 타임스탬프 값으로 변환할 수 있다.

**③ 41비트의 한계 — 왜 하필 2010년을 기준으로 잡았나**

41비트로 표현 가능한 최댓값은 `2⁴¹ - 1 = 2,199,023,255,551` ms ≈ **약 69.7년**이다. 이 69.7년이라는 창(window)의 길이는 어느 기준점을 잡든 고정된 값이다.

- 기준점을 **1970년**(Unix epoch)으로 그대로 썼다면: 트위터가 시스템을 만든 2010년 시점에 이미 "1970년부터 경과한 ms"가 약 40년치(약 1조 2,600억 ms)나 쌓여있어, 69.7년짜리 창의 상당 부분을 시작 전부터 써버린 셈이 된다. 남는 여유는 약 29~30년뿐 → 오버플로 시점이 **2040년경**으로 앞당겨짐.
- 기준점을 **2010년**(자체 EPOCH)으로 새로 잡으면: 경과 시간이 0부터 시작하므로 69.7년 전체를 온전히 미래를 위해 쓸 수 있음 → 오버플로 시점이 **2080년경**으로 늦춰짐.

즉 "기준점을 서비스 시작 시점에 최대한 가깝게 잡는 것"은, 41비트라는 한정된 예산을 이미 지나간 과거로 낭비하지 않고 앞으로 쓸 미래를 위해 아껴두는 전략이다. 69.7년이 지나면 기원 시각을 다시 앞으로 당기거나(비트 재활용) 다른 ID 체계로 마이그레이션해야 한다.

### 실제 세계
- 이 오버플로 문제는 **Y2K38 문제**(32비트 Unix 타임스탬프가 2038년에 오버플로되는 문제)와 정확히 같은 종류의 이슈다 — 비트 수를 유한하게 정해두고 시간을 표현하면 언젠가는 반드시 한계에 부딪힌다.
- **Discord Snowflake**는 epoch을 자사 창립 시점(2015-01-01)으로 설정해 오버플로 시점을 트위터보다 5년 뒤로 미뤄둔 사례 — "epoch을 서비스 시작에 최대한 가깝게" 전략을 그대로 따름.

### 내 말로 정리
트위터는 타임스탬프의 시작 기준을 2010년으로 설정했다. 즉 현재 유닉스 밀리초에서 2010년 epoch 값을 빼서, 시간 시작 기준을 2010년으로 설정함으로써 오버플로 데드라인을 늦췄다. 타임스탬프 최대 표현값이 69년인데, 이걸 진짜 유닉스 타임스탬프(1970년) 기준으로 하면 1970년부터 69년밖에 못 쓰기 때문에(2010년 시점엔 이미 40년치를 써버린 상태이기 때문에), 그 데드라인을 늦추기 위해서 2010년을 기준으로 한 것이다.

## 7. 시계 동기화 (clock synchronization) / NTP (참고문헌 [4] Network Time Protocol 포함)
- **유형**: 핵심 개념 + 참고문헌

### 무엇인가 · 왜 중요한가
스노우플레이크가 "조율 없는 유일성"과 "시간순 정렬"을 해결했다는 결론에는 숨겨진 전제가 하나 있다: **모든 ID 생성 서버가 정확히 같은 시계를 쓴다**는 가정이다. 책은 설계를 마무리하며 이 가정이 항상 유효하지 않다고 명시적으로 짚는다 — 하나의 서버가 여러 코어에서 실행되는 경우, 여러 서버가 물리적으로 독립된 장비에서 실행되는 경우 모두 이 가정이 깨질 수 있다.

### 동작 원리 (문제 상황과 해결책)

**문제**: 실제 분산 시스템에서는 서버마다 독립된 하드웨어 클럭을 가지고 있고, 시간이 지나며 조금씩 어긋난다(clock drift). 타임스탬프가 ID의 최상위 비트를 차지하므로, ID 값의 대소 비교는 사실상 "각 서버가 자기 시계 기준으로 언제라고 생각했는지"의 비교가 된다.

- 서버 A의 시계가 실제보다 빠르게 가고 있다면, A가 B보다 나중에 만든 ID인데도 더 이른 시각으로 착각해 더 작은 타임스탬프를 매길 수 있다 → 정렬 보장이 깨짐
- 더 심각하게는, 한 서버의 시계가 갑자기 과거로 되돌아가면(NTP 보정, 재부팅 등) 이미 사용한 타임스탬프보다 작은 값을 다시 쓰게 되어 시간 값이 아예 작아져서 다른 ID 값과 **중복**이 될 수 있음

**해결책 — NTP(Network Time Protocol)**: 네트워크로 연결된 컴퓨터들의 시계를 기준 시각 서버(원자시계·GPS 기반)에 맞춰 지속적으로 동기화하는 프로토콜.

**계층 구조(Stratum)**:
- Stratum 0: 원자시계·GPS 수신기 자체 (네트워크에 직접 연결 안 됨)
- Stratum 1: Stratum 0이 직접 꽂힌 1차 기준 서버
- Stratum 2, 3...: 상위 계층에서 네트워크로 동기화받는 서버들 (일반 서버/PC는 보통 Stratum 3~4)

**동작 방식**: 각 서버의 NTP 데몬(`ntpd`/`chronyd`)이 주기적으로 NTP 서버에 요청을 보내, 4개의 타임스탬프(요청 보낸 시각·서버 수신 시각·서버 응답 시각·응답 받은 시각)로 네트워크 왕복 지연을 상쇄하며 시계 오차(offset)를 계산한다. 이 offset을 한 번에 점프시키지 않고 **서서히(slew) 보정**하는데, 급격한 되돌림은 앞서 말한 ID 중복 문제를 그대로 재현하기 때문이다.

### 실제 세계
- **참고문헌 [4] Network Time Protocol**: 1985년부터 존재하는 인터넷에서 가장 오래되고 널리 쓰이는 프로토콜 중 하나. Linux `ntpd`/`chronyd`, Windows Time Service 등 대부분 OS에 기본 내장
- **Google TrueTime API**: Google Spanner가 사용, GPS+원자시계를 결합해 시계 오차의 **불확실성 구간(uncertainty bound)** 자체를 API로 노출 — "정확한 시각"이 아니라 "시각의 오차 범위"를 명시적으로 다뤄 분산 트랜잭션 순서를 보장하는 더 정교한 접근
- **AWS Time Sync Service**: EC2 VPC 내부에서 마이크로초 단위 정밀도로 시각 동기화를 제공하는 클라우드 인프라 서비스 (`169.254.169.123` 링크로컬 주소로 제공)
- 실무 Snowflake 구현체들은 보통 "생성 시각이 마지막 사용 타임스탬프보다 **과거**면 즉시 에러를 던지거나 대기"하는 방어 로직을 넣어 NTP 보정으로 인한 ID 역행/중복을 막음

### 실질적인 구현 방법 (인프라 + 애플리케이션 두 겹 방어)

**① 서버(OS) 레벨 — NTP 클라이언트 설정**

리눅스 서버는 보통 `chrony`(최신 배포판 기본) 또는 `ntpd` 데몬을 띄우고, 동기화할 NTP 서버를 설정 파일에 지정한다.

```
# /etc/chrony.conf 예시
server 169.254.169.123 prefer iburst minpoll 4 maxpoll 4   # AWS Time Sync Service
server ntp.internal.company.com iburst                      # 또는 자체 내부 NTP 서버
```

- `169.254.169.123`은 AWS가 모든 EC2 인스턴스에 VPC 내부적으로 제공하는 링크로컬 주소 — 인터넷 접속 없이도 초저지연·고정밀 동기화 가능
- `systemctl enable --now chronyd`로 상시 구동, `chronyc tracking`으로 현재 offset·동기화 상태 확인
- 컨테이너(Docker/Kubernetes)는 보통 별도 시계를 갖지 않고 호스트 노드의 시계를 그대로 공유하므로, 호스트 노드만 NTP로 잘 동기화되어 있으면 됨

**② 애플리케이션(ID 생성기) 레벨 — 방어 코드**

OS 레벨 동기화만으로는 동기화 순간의 미세한 되돌림까지 완전히 막을 수 없어, ID 생성 로직 자체에도 방어 코드를 넣는 게 실무 표준이다.

```
generateId():
    now = 현재시각(밀리초)

    if now < lastTimestamp:
        # 시계가 과거로 되돌아감 (NTP 보정, 재부팅 등)
        throw ClockMovedBackwardsException(lastTimestamp - now, "ms 만큼 역행")
        # 또는: 예외 대신 now가 lastTimestamp를 따라잡을 때까지 대기

    if now == lastTimestamp:
        sequence = (sequence + 1) & 4095
        if sequence == 0:
            now = 다음 밀리초까지 대기
    else:
        sequence = 0

    lastTimestamp = now
    return ID 조립
```

즉 실질적인 구현은 **인프라 레벨(NTP로 클럭을 최대한 정확하게 유지) + 애플리케이션 레벨(그래도 역행이 감지되면 절대 진행하지 않고 막는 방어 코드)** 두 겹으로 이루어진다. 인프라만 믿지 않고 코드에서도 마지막 안전장치를 두는 게 핵심이다.

### 내 말로 정리
각 서버마다 서버의 시간 자체가 동일하지 않을 수 있기 때문에, 시간 자체가 다르면 시간순으로 나열하는 것에 오류가 있을 수 있다. 그래서 NTP라는 방법으로 여러 개 서버가 동일한 서버 시각을 바라보고 동기화할 수 있게 한다. 만약 시계가 과거로 되돌아가면 시간값이 아예 작아져서 다른 ID 값과 중복이 될 수 있다.
