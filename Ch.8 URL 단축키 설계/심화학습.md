## 1. Base-62 변환
- **출처**: 본문 상세 설계 (2가지 해시 함수 구현 기법 중 하나)

### 무엇인가 · 왜 중요한가
DB의 auto-increment 정수 ID를 URL에 붙일 짧은 문자열로 바꾸는 진법 변환. URL 단축기의 존재 이유 자체가 "긴 URL을 짧게"이므로, 같은 ID를 표현하는 문자열의 길이를 최소화하는 것이 핵심 요구사항이다. 10진법(10개 기호)보다 62진법(62개 기호)을 쓰면 같은 크기의 수를 훨씬 적은 자릿수로 표현할 수 있다 (10진 13자리 → 62진 7자리).

### 동작 원리
62개 기호(`0-9`→0~9, `a-z`→10~35, `A-Z`→36~61)를 사용하는 위치기수법. 10진수를 62로 반복해서 나눈 나머지를 역순으로 읽어 변환한다.
예: `11157 → 62)179...59('X') → 62)2...55('T') → 62)0...2('2')` → `2TX`
base-64가 아닌 이유: base-64에 추가되는 `+`, `/` 문자가 URL에서 특수한 의미를 가져 URL-safe하지 않기 때문.

가역적(reversible) 변환이라 별도 매핑 테이블 조회 없이 단축 URL → 원래 ID 복원이 가능하다. 이 점이 "해시 후 충돌 해소" 방식과의 근본적 차이다:
- 해시 후 충돌 해소: 입력값이 `longURL`(유일성 미보장) → 충돌 발생 가능 → 충돌 시 DB 재질의 필요, 부하 증가
- base-62 변환: 입력값이 유일 ID 생성기가 만든 **유일한 숫자 ID**(유일성 보장됨) → 표현만 바꾸는 것이므로 충돌 원천 불가능

### 실제 세계 (도구 · 제품 · 논문)
Bitly, TinyURL 등 실제 URL 단축 서비스가 유사한 방식을 사용. Instagram 엔지니어링 블로그("Sharding & IDs at Instagram")에서도 64비트 ID를 base-62/64로 짧게 표현하는 기법을 다룸 — "긴 숫자 ID를 짧은 문자열로 노출"하는 범용 패턴.

### 차주 설계와의 연결
base-62를 선택하면 **유일 ID 생성기**(항목 5, 7장)가 반드시 선행 조건이 된다. 표 8-3(두 접근법 비교)의 트레이드오프가 이번 챕터 설계의 핵심 결정 포인트.

### 내 말로 정리
> base-62는 같은 숫자 값을 더 많은 기호(62개)로 표현해서 자릿수를 줄이는 진법 변환. 매 자리마다 62개의 기호로 표현할 수 있다.
> 해시 방식은 해시함수를 통해서 longURL을 해시값으로 변환하는 것이고(입력값 = longURL, 유일성 미보장), base-62는 유일 ID 생성기가 만든 유일한 ID를 바탕으로 그 유일 ID를 더 적은 자릿수의 문자열로 표현만 바꾸는 것(입력값 = 유일 ID, 유일성 보장됨 → 충돌 불가능).

## 2. CRC32 / MD5 / SHA-1 해시 함수 비교
- **출처**: 본문 name-drop (표 8-2에서 결과만 제시하고 설명 없이 넘어감)

### 무엇인가 · 왜 중요한가
셋 다 임의 길이 입력 → 고정 길이 출력을 만드는 해시 함수지만 설계 목적이 다르다.

| 함수 | 출력 길이 | 원래 목적 | 안전성 |
|---|---|---|---|
| CRC32 | 32비트 | 오류 검출(체크섬) | 없음 — 충돌이 자연스러움 |
| MD5 | 128비트 | 암호학적 해시였으나 현재 깨짐 | 없음 — 의도적 충돌 생성 가능(2004~) |
| SHA-1 | 160비트 | 암호학적 해시 | 취약 — 2017 SHAttered로 실제 충돌 발견 |

### 동작 원리
- CRC32: 다항식 나눗셈 방식의 체크섬. 우연한 비트 오류 검출이 목적이라 의도적 조작 방어력이 없음.
- MD5/SHA-1: 블록 단위 반복 비선형 연산으로 다이제스트 생성. 한때 "지문"으로 여겨졌으나 계산 자원 발전으로 충돌 공격이 실용화됨.

**URL 단축기 맥락의 핵심**: 원래 해시 함수의 출력 길이(32/128/160비트)와 무관하게, 표 8-2처럼 **앞 7글자만 잘라 쓰는 순간** 출력 공간이 62⁷(또는 16⁷)로 강제로 줄어든다. 이는 비둘기집 원리(pigeonhole principle)에 의해 서로 다른 원본 URL이 같은 7자 문자열로 겹칠 수 있다는 뜻이며, 생일 문제(birthday paradox) 때문에 공간이 완전히 채워지기 훨씬 전부터 충돌 확률이 급격히 올라간다. 즉 **어떤 해시 함수를 쓰든 7자로 자르면 충돌은 피할 수 없다** — 이것이 "해시 후 충돌 해소" 전략이 별도의 충돌 해소 절차를 필요로 하는 근본 이유.

### 실제 세계 (도구 · 제품 · 논문)
- CRC32: ZIP, Ethernet 프레임, PNG 등 오류 검출용으로 현역
- MD5: 비보안 목적 파일 무결성 체크에만 사용 (비밀번호/서명에는 사용 금지)
- SHA-1: Git 커밋 해시로 쓰였으나 SHAttered(2017, Google+CWI) 이후 SHA-256 계열로 전환 진행 중

### 차주 설계와의 연결
표 8-3의 "해시 후 충돌 해소" vs "base-62" 비교에서, 전자의 근본적 약점(충돌 불가피)을 뒷받침하는 지식. 이 이해가 있어야 base-62(충돌 원천 불가능)가 실무적으로 선호되는 이유를 설득력 있게 설명할 수 있다.

### 내 말로 정리
> CRC32는 오류 검출용이라 충돌이 잘 나고, MD5랑 SHA-1은 암호학적으로 깨져서 안전하지 않아.
> 7글자로 잘라 쓰면 자릿수가 고정되어 있기 때문에 원래 해시값은 다를 수 있어도 7자리로 자른 해시값은 중복(충돌)이 될 수 있어.

## 3. 블룸 필터 (Bloom Filter)
- **출처**: 참고문헌 [2]

### 무엇인가 · 왜 중요한가
"이 원소가 집합에 있는가?"를 아주 빠르고 공간 효율적으로 답하는 확률적 자료구조. "해시 후 충돌 해소" 방식에서 충돌 여부를 매번 DB에 질의하면 부하가 크므로, DB 앞단에서 대부분의 "없음" 케이스를 걸러내는 용도로 쓰인다.
- "없다" → 100% 확실히 없다 (false negative 없음)
- "있다" → 있을 수도, 없을 수도 있다 (false positive 가능)

### 동작 원리
`m`비트 배열(초기 전부 0) + `k`개의 서로 다른 해시 함수로 구성.
- **삽입**: 원소 x를 k개 해시 함수에 넣어 나온 각 결과값을 배열 크기로 나눈 나머지를 인덱스로 사용해, 그 k개 위치의 비트를 1로 켠다.
- **조회**: 같은 방식으로 y의 k개 위치를 확인 → 하나라도 0이면 확실히 없음, 전부 1이면 있을 가능성 높음(단 다른 원소들의 해시 위치가 우연히 전부 겹쳤을 수도 있음 = false positive).

false positive가 생기는 이유: 배열 값은 0/1뿐이라 "누가 그 비트를 켰는지" 기록이 없다. 여러 원소가 같은 인덱스를 공유(해시 충돌)하면서 흔적이 겹친다. 반대로 0인 칸은 그 인덱스를 켤 만한 원소가 단 하나도 없었다는 반박 불가능한 증거이므로 "없음"은 항상 확정적이다.
`m`, `k`를 늘리면 false positive율은 낮아지지만 메모리 사용량이 증가하는 트레이드오프가 있다.

### 실제 세계 (도구 · 제품 · 논문)
- Google Chrome Safe Browsing (악성 URL 로컬 필터링)
- Cassandra/HBase/RocksDB 등 LSM-tree 스토리지 엔진 (디스크 I/O 전 사전 필터)
- Bitcoin BIP 37 (라이트 클라이언트 트랜잭션 필터링)
- Redis: RedisBloom 모듈

### 차주 설계와의 연결
"해시 후 충돌 해소" 방식 채택 시 DB 부하를 줄이는 실전 최적화 기법. 다만 false positive 때문에 DB를 완전히 대체하지 못하고, DB 앞단의 "빠른 사전 필터" 역할만 한다는 한계를 함께 언급해야 한다.

### 내 말로 정리
> 결국 블룸 필터 안의 공간에 해당하는 인덱스의 값과 해시 나머지 값이 똑같으면 그 칸에 1을 할당하는데, 그게 우연히 겹칠 수 있기 때문에 "있다"는 확실하지 않은 거고, 그 칸이 0이라면 무조건 아무 데이터도 해시되어서 그 값이 나오지 않은 거니까 "없다"는 확실한 거다.
> (활용) 블룸 필터는 해시 충돌 해소 방법을 사용할 때 유용하다. 블룸 필터에서 "없다"가 나오면 100% 없는 것이므로 바로 DB에 insert할 수 있고, "있다"가 나오면 DB를 한 번 질의해서 확실히 확인해야 한다. 그래서 DB에 질의하기 전 필터링 용도로 사용해서 성능을 높일 수 있다.

## 4. 301 vs 302 리다이렉트
- **출처**: 본문 상세 설명 (심화 확장)

### 무엇인가 · 왜 중요한가
단축 URL 클릭 시 서버가 응답하는 HTTP 상태 코드 선택 문제. 핵심 차이는 **브라우저 캐싱 여부**이고, 이게 서버 부하와 클릭 분석(analytics) 가능 여부를 가르는 트레이드오프로 이어진다.

### 동작 원리
- **301 Moved Permanently**: 기본적으로 캐시 가능(heuristically cacheable)한 상태 코드로 정의됨. 브라우저가 "단축 URL → 원래 URL" 매핑을 로컬에 캐싱해, 두 번째 클릭부터는 서버에 요청조차 가지 않고 곧장 원래 URL로 이동.
- **302 Found**: 기본적으로 캐시 불가능(non-cacheable)한 상태 코드로 정의됨. 서버가 명시적으로 캐시 헤더를 주지 않는 한 캐싱되지 않아, 클릭할 때마다 매번 서버를 거침.

**서버가 요청을 "볼 수 있는지"가 핵심**: 브라우저 캐시는 사용자 로컬 기기 안에 있어 서버가 전혀 접근할 수 없다. 캐시 히트 시 네트워크 요청 자체가 발생하지 않으므로, 서버 입장에서는 "요청이 왔다가 캐시로 처리된 것"이 아니라 애초에 아무 일도 일어나지 않은 것과 동일하다 — 로그에 남길 대상 자체가 없음. (CDN 엣지 캐시는 서비스 소유 인프라라 히트율 통계 제공이 가능하지만, 브라우저 캐시는 통제 범위 밖이라 그런 채널이 없음)

**트레이드오프**: 301은 서버 요청이 최초 1회로 줄어 부하는 낮지만 클릭 통계를 정확히 셀 수 없다. 302는 매번 서버를 거쳐 부하는 늘지만 모든 클릭을 관찰할 수 있어 정확한 analytics(클릭 수/지역/시간대)가 가능하다. 301은 한 번 캐싱되면 되돌리기 어렵다는 실무적 리스크도 있다.

### 실제 세계 (도구 · 제품 · 논문)
- Bitly, TinyURL 등 클릭 분석이 핵심 가치인 서비스는 대부분 302 사용
- 영구적 브랜드/도메인 이전에는 SEO 관점(검색엔진의 링크 자산 이전)에서 301 사용

### 차주 설계와의 연결
URL 단축기가 analytics 기능(항목 9)을 제공한다면 302가 사실상 필수. 짧지만 명확한 트레이드오프를 보여줄 수 있는 설계 논의 포인트.

### 내 말로 정리
> 캐싱이 됐다면 DB를 직접적으로 질의하지 않으므로 아무 기록도 남지 않을 것이기 때문에 분석용도로는 가치가 없다. 302는 캐싱이 되지 않으므로 사용자가 얼마나 URL 요청을 했는지 알 수 있다. 핵심 차이는 캐싱을 하냐 안 하냐이고, URL 단축 서비스는 클릭 통계를 얻으려면 캐싱을 쓰면 안 된다.
> (추가 확인) 브라우저 캐시는 사용자의 로컬 기기 안에 있어서 서버가 전혀 알 수 없다 — 캐시 히트 시 서버로 요청 자체가 안 가기 때문에 애초에 관찰 대상이 없는 것. 단축 URL 서비스는 도착 페이지(원래 URL)를 소유하지 않으므로 그 페이지에 추적 코드를 심을 수 없고, 자기 서버를 반드시 거치게 만드는 것(302)만이 유일한 관찰 지점이다.

## 5. 유일 ID 생성기 (7장 재연결)
- **출처**: 본문 상세 설계 (7장 참고 명시)

### 무엇인가 · 왜 중요한가
Base-62 변환(항목 1)의 입력값인 "유일한 숫자 ID"를 만드는 방법. 7장에서 다룬 4가지 후보(다중 마스터 복제/UUID/티켓 서버/스노우플레이크) 중 하나를 그대로 재사용한다.

### 동작 원리 (8장에서 달라지는 지점)
7장의 5가지 요구사항 중 URL 단축기에 실제로 필요한 건 **유일성**과 **처리량**뿐이며, "시간순 정렬"은 필수가 아니다. 대신 표 8-3에서 책이 짚은 새로운 제약이 추가된다:

> ID가 1씩 증가하는 값이면 다음에 쓸 수 있는 단축 URL을 쉽게 예측할 수 있어 **보안 문제**가 될 수 있음

7장에서는 ID가 내부 DB 기본 키로만 쓰였지만, 8장에서는 ID를 base-62로 인코딩한 값이 그대로 **외부에 공개되는 URL**이 된다. 순차 증가하는 ID(스노우플레이크 포함 — 타임스탬프가 최상위 비트를 차지해 시간순으로 예측 가능)를 그대로 노출하면, 공격자가 인접한 값들을 스캔해 아직 공개되지 않았어야 할 다른 사용자의 단축 URL을 전수조사(enumeration)할 수 있다.

**완화 방법 (책에 없는 실무 확장)**: ID 생성은 그대로 순차적으로 하되(스노우플레이크의 정렬성·성능 유지), base-62 인코딩 직전에 **가역적 뒤섞기**를 끼워 넣는다.
```
순차 ID(64비트 전체) → 가역적 뒤섞기(XOR/순열) → base-62 인코딩 → 단축 URL
```
XOR은 "같은 키로 두 번 적용하면 원래 값으로 복원되는" 자기 역함수 성질(`A⊕B⊕B=A`)을 가지므로, 리다이렉션 시 같은 키로 역-XOR하면 원래 ID를 정확히 복원해 DB 조회가 가능하다. **64비트 전체를 통짜로 섞어야** 하며, sequence 부분만 섞으면 상위 비트(타임스탬프)가 여전히 예측 가능해 방어 효과가 떨어진다.

### 실제 세계 (도구 · 제품 · 논문)
- **Hashids / Sqids**: 순차 정수 ID를 겉보기엔 무작위인 짧은 문자열로 가역 변환하는 오픈소스 라이브러리
- **Optimus**(PHP): 곱셈 기반 가역 해싱으로 동일 목적 구현
- Instagram 등에서 ID 생성 후 외부 노출 전 난독화 계층을 별도로 두는 사례

### 차주 설계와의 연결
7장 결과물(스노우플레이크 등)을 그대로 재사용하되, "예측 가능성이 보안 문제가 되는가"라는 8장만의 새 평가 기준을 추가로 고려해야 한다.

### 내 말로 정리
> 스노우플레이크는 섹션마다 숫자를 어느 정도 예상할 수 있기 때문에, 예측이 되면 공개되면 안 되는 URL도 예측이 될 수 있다.
> 결국 스노우플레이크로 만든 값(64비트 전체)을 가역적으로(XOR 등으로) 섞고, 그걸 다시 base-62로 인코딩한다. sequence 부분만이 아니라 전체를 섞어야 타임스탬프 같은 상위 비트도 예측 불가능해진다.

## 6. 처리율 제한 장치 (Rate Limiter, 4장 재연결)
- **출처**: 마무리 추가학습

### 무엇인가 · 왜 중요한가
"엄청난 양의 URL 단축 요청이 밀려들 경우 무력화될 수 있다"는 잠재적 보안 결함을 막기 위한 장치. 4장에서 알고리즘·배치 위치·저장소를 이미 깊이 다뤘으므로, 8장에서는 **"어느 엔드포인트에 왜 우선 적용해야 하는가"**가 새로운 질문이다.

### 동작 원리 (8장 적용 지점)
- **단축 엔드포인트**(`POST /shorten`): 쓰기 연산이라 DB/ID 생성기 자원을 소모하고, 악용 시 저장 용량 계획(3650억 개 추정)이 무너질 수 있어 우선순위가 가장 높음
- **리다이렉션 엔드포인트**(`GET /shortUrl`): 원래 읽기 위주지만 봇 트래픽이 몰리면 캐시/DB 부하 발생 가능
- 제한 기준(key): IP 기반이 기본이지만 로그인 사용자가 있다면 사용자 ID 기반을 결합하는 게 더 견고함(IP는 NAT 공유·우회 가능)

### 실제 세계 (도구 · 제품 · 논문)
Stripe API 등 공개 API가 흔히 토큰 버킷을 기본 정책으로 채택 — 정상적인 버스트 사용 패턴을 허용하면서도 버킷 크기로 최대 악용량을 제한.

### 차주 설계와의 연결
알고리즘을 처음부터 다시 고르기보다, "이 시스템의 두 엔드포인트 중 어디에 왜 우선 필요한지"를 짧게 짚는 것으로 4장 지식 재활용을 보여주면 충분.

### 내 말로 정리
> 토큰 버킷을 쓸 것 같다. 순간적으로 몰리는 요청도 어느 정도 허용하니까. (버킷 크기로 최대 버스트량이 제한되므로, 정상적인 버스트는 허용하면서 악용 규모는 통제 가능하다는 점도 확인함)
